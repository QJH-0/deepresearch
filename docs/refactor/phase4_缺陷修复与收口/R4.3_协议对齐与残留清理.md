## 3. 详细设计

### 3.1 report_review reject 分支补齐（推荐：补齐而非移除）

**决策依据**：报告评审三态（采纳/修订/否决）是 HITL 设计的自然完备集；plan_approval 已有 approve/revise/reject 三分支（简历口径），report_review 只有两态属于实现缺口而非设计冗余。补齐使两处 HITL 交互模型一致。

**补齐内容**：

1. **后端 schema**（`schemas/research.py`）：

```python
class ReportReviewResumePayload(BaseModel):
    # 以现有字段为基线，action 枚举扩展（若现有为 decision 字段则对齐现有命名）
    action: Literal["approve", "revise", "reject"]
    feedback: str = ""            # reject 时的否决理由（可选）
    sub_questions: list[str] = []  # revise（再深入）时的追加子问题（沿用现有字段名）
```

> 执行时先读现有 `ReportReviewResumePayload` 的真实字段名与枚举值，**在其基础上扩展**，不另起炉灶。

2. **write 节点处理**（`nodes/write.py`）：

```
approve → 现有采纳逻辑不变（结束 / 输出 final）
revise  → 现有再深入逻辑不变（Command(goto="plan") + 追加子问题）
reject  → 新增：将 feedback 记入 state（如 user_feedback / revision_note），
          Command(goto="plan") 带否决上下文重走规划与撰写
```

reject 与 revise 的区别：revise 保留现有报告内容继续深化；reject 表示报告不合格需要换方向重做（plan 节点的 prompt 上下文带上否决理由）。

3. **前端**（`ReportReviewCard.vue`）：增加第三个按钮「否决」，点击弹出理由输入框（必填），提交 emit `{kind:'report_review', action:'reject', feedback}`；与 plan_approval 卡的三按钮交互保持视觉一致。

4. **协议文档**：`docs/event-protocol.json` 中 report_review 的 resume 载荷描述补上 reject（action 枚举 + feedback 字段说明）。

### 3.2 残留壳文件清理

**判别流程**（逐文件执行，禁止无判据删除）：

```
对 app/mult_agents/memory/ 下每个文件 f：
  1. grep 全仓（app/ 与 agent_front/src/）引用：import 路径含 "mult_agents.memory" 或相对引用
  2. 有引用 → 读引用方代码，确认是「活代码依赖」还是「死引用」
     - 活依赖：保留文件（记录到执行日志：为何保留）
     - 死引用（引用方本身也是壳/未被调用）：连同引用方一并评估
  3. 无引用 → 确认为壳文件，删除
```

**删除操作规范**：批量删除前列出完整清单（文件 + 判据 + 引用检查结果），若涉及目录整体删除（如整个 `memory/` 目录），属于「破坏性递归删除」类操作——清单输出到执行日志后执行 `git rm`（走 git 便于回滚），**不用文件系统 rm**。

**同类排查扩展**（顺手但克制）：清理时同时 grep 项目内是否有其他明显残留（如探索报告提过的 `workflow_service.py` 旧文件若仍存在且无引用）。只处理无引用的确定壳，存疑保留并记录。

### 3.3 一致性收口检查

建立一张三方对照表并核验（结果记入执行日志，发现不一致即修）：

| 事件类型 | EVENT_REGISTRY（后端） | event-protocol.json | 前端 types/events.gen.ts | useEventStream dispatch |
| --- | --- | --- | --- | --- |
| 10 种事件逐一行 | data model 字段 | 字段描述 | TS 类型 | 处理分支 |

核验项：

- 事件类型集合一致（10 种，无多无少）
- 每种事件的 data 字段名与类型一致（重点：`message.thinking` 的 `message_id/text`；`sources.found` 的 `sources[].source_type` 枚举 `web|kb`）
- 前端 `events.gen.ts` 若为手写（非自动生成），确认其生成方式——`docs/event-protocol.json` 若有生成脚本则重跑，无脚本则手工对齐后记录「手工同步」现状

## 6. 风险与回滚

- **风险 1**：reject 分支与 revise 在 plan 节点的行为区分不清导致重走流程相同。缓解：reject 的 feedback 注入 plan 上下文（读 plan 节点现有 prompt 上下文注入方式对齐）。
- **风险 2**：壳文件误删破坏隐性依赖（如 conftest mock 注册表、动态 import）。缓解：grep 全仓 + 全量回归双保险；git rm 保留回滚能力。
- **风险 3**：前端三按钮交互改变用户习惯。缓解：与 plan_approval 卡一致（已有三按钮先例）。
- **回滚**：reject 分支为纯增量（不改变现有两态行为）；壳文件删除走 git revert。
