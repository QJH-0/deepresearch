# R4.1 日志重复输出修复

> 阶段四 · 缺陷修复与收口 | 对应落地修复清单 #12（部分）：修复日志重复输出（logger handler 重复挂载）
> 前置阅读：`docs/refactor/00_重构总览与执行指南.md`

## 1. 目标

修复**日志重复输出**缺陷：控制台/文件中出现同一条日志打印多次。根因是 root logger 的 handler 被**两套初始化代码重复挂载**（`app_main.py` 与 `research_logger.py` 的 `setup_logging()` 各自为政，守卫标记互不识别）。收口为**单一日志初始化入口**。

**验收标准**：

- [ ] 日志初始化只有唯一入口，任何调用顺序下 handler 不重复挂载
- [ ] 重复挂载守卫统一：进程内多次调用任何 setup 函数均为幂等（第二次调用零副作用）
- [ ] 复现路径验证：修复前每次触发 `setup_logging()` 控制台输出翻倍的场景，修复后保持单份
- [ ] 现有日志能力不回退：控制台 + 轮转文件 + TRACE 通道 + 按 thread_id 的研究 JSON 日志全部保留
- [ ] 单元测试全部通过，全量回归无破坏

## 2. 现状分析（动手前先完整阅读以下文件）

| 文件 | 现状要点 |
| --- | --- |
| `app/app_main.py`（约 46–98 行） | root logger 初始化：`_deepresearch_root` 属性标记守卫；`StreamHandler(sys.stdout)` + `RotatingFileHandler`（轮转）+ TRACE 专属 `RotatingFileHandler`（`[TRACE]` 过滤器）；uvicorn 等日志级别设置。**此为正确的守卫实现** |
| `app/mult_agents/research_logger.py`（`setup_logging()`，约 131–165 行） | 第二套 root logger 挂载：console 守卫条件是 `any(isinstance(h, logging.StreamHandler) for h in root_logger.handlers)`——**识别不了 `app_main.py` 已挂载的 handler**（它们的 `_deepresearch_root` 标记不被 isinstance 检查捕获）；file handler（`logs/app_YYYYMMDD.log`，`FileHandler` 非 `RotatingFileHandler`，文件名模式也与 app_main 不同）**完全没有守卫**——每次调用追加一个 |
| 调用点 | 执行时 grep `setup_logging(` 找齐全部调用方（模块 import 时？每次请求时？）。探索报告显示该函数存在且可被触发；调用频次是重复倍数的放大器 |

**缺陷机理**：

```
app_main.py 启动：root 挂 3 个 handler（带 _deepresearch_root 标记）
    ↓
research_logger.setup_logging() 被调用（import 或运行时）：
    - console：isinstance(StreamHandler) 检查 → app_main 的 stdout handler 也是 StreamHandler → 不重复加 console（侥幸）
    - file：无任何守卫 → 每调用一次加一个 FileHandler → 文件日志重复 N 份
    - 且两套 file handler 文件名不同（app_YYYYMMDD.log vs 轮转文件）→ 同一条日志写进两个文件
    ↓
若 setup_logging 被多次调用 → file handler 线性累加 → 每条日志重复 N 次
```

> 执行提示：先用 3.1 节复现步骤实测确认重复路径（console 是否也重复取决于 `StreamHandler` 判断细节——`RotatingFileHandler` 不是 StreamHandler 子类，若 app_main 的 console handler 存在则 console 侥幸不重复；但**修复不依赖侥幸**，统一守卫后两种情况都正确）。

## 3. 详细设计

### 3.1 修复方案：删除第二套挂载，统一入口

**核心原则（纯净原则：不打补丁）**：root logger 的 handler 管理只允许存在一处——`app_main.py`。`research_logger.setup_logging()` 中的 handler 挂载逻辑**整体删除**，函数退化为「级别设置委托」或直接删除函数并清理调用点。

改造后的 `research_logger.py`：

```python
# 删除 setup_logging() 中：
#   - root_logger.addHandler(console_handler) 及其构造（整块）
#   - root_logger.addHandler(file_handler) 及其构造（整块）
#
# 两种收口选择（执行时依据调用点数量二选一，记录决策）：
# 选择 A（推荐）：setup_logging() 整函数删除 + 全部调用点删除
# 选择 B：setup_logging() 保留为空操作兼容层（仅 logger.setLevel），调用点不动
```

**选择 A 的操作清单**：

1. 删除 `setup_logging()` 函数
2. grep `setup_logging` 全部调用点（预期在 `research_logger.py` 自身或 `mult_agents` 模块 import 链上），逐一删除调用行
3. 若有测试断言了 `setup_logging` 行为，改为断言「调用后 root handlers 数量不变」

### 3.2 守卫强化（防御性统一）

为防未来再次出现两套初始化，`app_main.py` 的守卫从「检查 `_deepresearch_root` 标记」升级为「幂等整套初始化」：

```python
# app_main.py 现有逻辑已经是「标记存在则跳过」，保持。
# 追加一个自检（模块加载末尾）：
assert not any(
    isinstance(h, logging.StreamHandler) and not getattr(h, "_deepresearch_root", False)
    for h in _root_logger.handlers
), "检测到未带 _deepresearch_root 标记的 StreamHandler，存在重复挂载风险"
```

> 该 assert 用 `assert` 会随 `-O` 优化失效——改用启动期 `logger.warning` 提示更稳妥（异常只在 DEBUG 需求时抛）。落地时用 warning 提示即可，不阻塞启动。

### 3.3 TRACE 通道与研究日志确认项

- `app_main.py` 的 TRACE handler（`[TRACE]` 过滤）保留不动
- `research_logger.py` 的 `ResearchLogger`（按 thread_id 的 JSON 事件日志）**不动**——它是独立文件写入体系，与 root handler 无关（执行时确认其写入方式确实不经 root logger）

## 4. 实施步骤

### 步骤 1：复现与定位

- grep `setup_logging` 找齐调用点；写临时脚本（验证后删除）连续调用两次 `setup_logging()`，统计 root handlers 数量与控制台输出份数
- 产出：执行日志记录「重复倍数、触发路径」

### 步骤 2：删除重复挂载

- 按 3.1 执行选择 A（或 B）；删除 `logs/app_YYYYMMDD.log` 相关 FileHandler 构造
- 验证：`python -c "import app.app_main"` 无报错；grep `setup_logging` 只剩（或不再有）预期残留

- 按 3.2 在 app_main 增加未标记 handler 的 warning 自检

## 6. 风险与回滚

- **风险 1**：某些代码路径依赖 `logs/app_YYYYMMDD.log` 文件存在（如排障习惯/外部采集）。缓解：该文件本就是重复缺陷的产物，主轮转日志（app_main 的 RotatingFileHandler）承接全部内容；在执行日志中标注文件路径变化。
- **风险 2**：`setup_logging()` 删除后 import 链上的调用点遗漏导致 NameError。缓解：grep 全仓 + `python -c "import app.app_main"` + 全量回归三重验证。
- **回滚**：单 commit revert 即可回到双挂载现状（回到缺陷态无意义，回滚仅用于紧急阻断）。
