## 3. 详细设计（排查驱动的修复路线）

本任务为**缺陷修复**，设计以「复现 → 定位 → 最小修复」的排查路线给出，执行模型必须先复现拿到根因，再对照下方高概率根因清单实施修复。

### 3.0 复现环境

```
docker compose -f docker-compose.middleware.yml up -d
uvicorn app.app_main:app --port 8000
cd agent_front && npm run dev
# 浏览器打开前端，按 E3/E4/E5 场景操作，DevTools Console + Network(EventStream) 全开
```

### 3.1 E3 排查路线（无回复气泡）

按序检查，命中即修：

1. **事件是否到达前端**：Network 面板看 EventStream 帧序列。有 `run.started` + `agent.status` + `message.delta`+ `run.completed` → 前端渲染问题，转 2；只有 `run.error` → 后端问题，转 4
2. **dispatch 分发是否正确**：Console 里临时 `console.log` 每帧 env（修复后删除）；确认 `message.start` / `message.delta` 进入 chat store 的 action
3. **chat store 消息列表初始化**：确认 `message.start` 创建消息对象的 action 中，新 thread 的消息数组已初始化（常见 bug：`state.messages[threadId]` 未初始化时 push 到 undefined）；确认 ChatView 的消息渲染 v-for 绑定的响应式引用无误
4. **后端 run.error 场景**：日志 grep `NoFinalOutput` 或检索失败 warning。若为「检索失败 → 无证据 → final 空」：
   - 检查 `web_search_records` 的 DDG 失败路径（阶段一 R1.1 的降级链是否已生效/网络环境是否被墙）
   - 检查 local_rag 的知识库为空时 `search_records` 的行为
   - 修复方向：检索双路全空时 deep_dive/analyze 节点应产出「基于有限信息的报告」而非空 final（读 `nodes/write.py` 与 `_fallbacks.py` 的兜底逻辑，缺失则补：final 至少包含「本次研究未能获取足够外部证据」的说明文本 + 已有来源列表）

### 3.2 E4 排查路线（Vue recursive updates 冻结）

「Maximum recursive updates exceeded」的标准成因与对应检查：

1. **watch 循环**：`interrupt.ts` store 的 `raise()` 写入响应式 Map → ChatView 某 `watch(currentInterrupt)` 回调内又写 interrupt/chat store → 循环。检查所有 `watch(` 与 `watchEffect(` 的写入方向
2. **computed 副作用**：`currentInterrupt` computed 内调用 store 方法（compute 应纯读）
3. **v-if 与 store 写入联动**：中断卡 `v-if="currentInterrupt?.kind === 'plan_approval'"` 渲染触发的组件 mounted/updated 钩子里写 store（检查 PlanApprovalCard 的生命周期钩子）
4. **消息渲染与中断卡互斥区的响应式大对象**：`interrupt.payload` 含整个研究状态（plan 数组），Vue 深层响应式代理在 v-for + 卡片双向绑定（如反馈输入框 v-model 绑定 payload 内层字段）时易触发递归。修复方向：卡片内输入用**本地副本**（`ref` 初始化自 payload，提交时 emit），不直接 v-model 绑定 store 里的 payload 字段
5. 定位手段：Vue 报错栈中的组件名 + 「at reactiveEffect」调用链直接指向循环源

### 3.3 E5 排查路线（取消阻塞）

E4 修复后复验。若仍异常：

1. 前端调 `POST /cancel` 后 UI 卡在 streaming 态：检查 chat store 的 cancelled 状态与 `run.cancelled` 事件处理（`dispatch` 的 `run.cancelled` 分支 → 清 streaming 态）
2. 后端 `registry.cancel` 未命中（任务不在本进程/已 done）：R3.2 已补广播，此处确认单机场景返回值语义
3. abort 后 `consumeSSE` 的 AbortError 分支正确调 onDone（现有代码已处理，验证即可）

### 3.4 E2E 固化

修复验证通过后，将 E1–E5 场景固化为 `agent_front/e2e/` 下的 Playwright 脚本（若项目已有 Playwright 基建则扩展；没有则建立最小配置）：

```
agent_front/e2e/
├── playwright.config.ts        # baseURL 指向本地前端 dev server
└── research.spec.ts            # E1 页面可达 / E2 健康检查 / E3 提问建流回复 / E4 HITL 审批卡 / E5 取消
```

E3/E4 依赖后端真实 LLM 响应：测试中通过 mock 后端 SSE（page.route 拦截 /api 请求返回脚本化事件序列）保证确定性——mock 脚本事件序列要与 `docs/event-protocol.json` 一致。
