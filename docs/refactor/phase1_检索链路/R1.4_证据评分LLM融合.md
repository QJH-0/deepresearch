# R1.4 证据评分 LLM 结构化评估融合

> 阶段一 · 检索链路 | 对应落地修复清单 #11：静态域名分数升级为「先验 + LLM 结构化评估」融合打分
> 前置阅读：`docs/refactor/00_重构总览与执行指南.md`

## 1. 目标

将证据可靠性评分从**纯静态规则**（域名分档先验）升级为「**域名信誉先验 + LLM 结构化评估**」融合：LLM 批量评估证据的内容质量与主题相关性，输出结构化分数与理由；先验与 LLM 分数加权融合为最终 `reliability_score`。LLM 评估失败时静默回退纯先验分数，主流程零影响。

**验收标准**：

- [ ] `_score_evidence` 保留为先验通道（现行为不变）
- [ ] 新增 LLM 批量评估：一次调用评估一批证据（上限 20 条），输出 `[{source_id, score, reason}]` 结构化 JSON
- [ ] 融合公式：`final = 0.4 * prior + 0.6 * llm`（权重可配置），融合后写入 `reliability_score`，LLM 理由写入 `reliability_reason`（格式：`{llm_reason}（先验{prior_score}）`）
- [ ] LLM 输出解析容错：JSON 解析失败 / 字段缺失 / 越界分数（clamp 到 [0,1]）均不抛异常，缺失项回退先验
- [ ] LLM 失败（异常/超时/Key 无效）整批回退先验，只记 warning
- [ ] `audit_flags`（low_confidence < 0.6）逻辑基于融合后分数，行为兼容
- [ ] 单元测试全部通过，全量回归无破坏

## 2. 现状分析（动手前先完整阅读以下文件）

| 文件 | 现状要点 |
| --- | --- | 
| `app/mult_agents/nodes/_evidence.py` | `_score_evidence(record) -> tuple[float, str]`：local 0.92 / 官方域名 0.88 / 主流媒体 0.72 / 普通域名 0.58 / 无来源 0.45；`_is_official_domain` 判断 .gov/.edu 等；`_assign_source_ids`、`_dedupe_sources` 等工具函数 |

| `app/mult_agents/nodes/deep_dive.py` | deep_dive 节点（探索报告称产出证据池与审计标记，先读确认其与 `_fallback_audit` 的调用关系——审计逻辑在哪条路径上生效） |

**现状问题**：同域名下不同质量的页面拿到完全相同分数；内容与主题强相关但域名普通的证据被低估；LLM 的语义判断能力未参与评分。

## 3. 详细设计

### 3.1 EvidenceScorer（新增类，放在 `_evidence.py`）

```python
class EvidenceScorer:
    """证据评分融合：域名信誉先验 + LLM 结构化评估。

    LLM 批量评估一批证据（≤20 条），输出与先验加权融合。
    任何失败路径都静默回退纯先验，保证主流程零感知。
    """

    BATCH_SIZE = 20
    PRIOR_WEIGHT = 0.4
    LLM_WEIGHT = 0.6
    TIMEOUT_SECONDS = 20.0

    def __init__(self, llm, prior_weight: float = PRIOR_WEIGHT):
        self._llm = llm                    # 复用节点现有的 ChatTongyi / agent LLM
        self._prior_weight = prior_weight

    def score_batch(self, records: list[dict]) -> list[dict]:
        """批量评分入口：返回带 reliability_score / reliability_reason 的新记录列表（不改入参）。"""
        if not records:
            return []
        scored = []
        for start in range(0, len(records), self.BATCH_SIZE):
            batch = records[start : start + self.BATCH_SIZE]
            llm_scores = self._llm_score_batch(batch)     # 失败返回 {}
            for record in batch:
                prior, prior_reason = _score_evidence(record)
                llm_result = llm_scores.get(record.get("source_id", ""), None)
                if llm_result is None:
                    score, reason = prior, prior_reason
                else:
                    score = self._prior_weight * prior + self._LLM_WEIGHT * llm_result["score"]
                    score = min(1.0, max(0.0, score))
                    reason = f"{llm_result['reason']}（先验{prior:.2f}）"
                item = dict(record)
                item["reliability_score"] = score
                item["reliability_reason"] = reason
                scored.append(item)
        return scored
```

### 3.2 LLM 批量评估 prompt（中文，输出 JSON）

```python
EVIDENCE_SCORE_PROMPT = """你是一名证据质量评审专家。请针对研究问题，评估每条证据的内容质量与主题相关性。

研究问题：{query}

证据列表：
{evidence_list}

要求：
1. 对每条证据输出 0~1 之间的相关性/可靠性分数（0 完全不可信或无关，1 高度可信且高度相关）
2. 分数参考维度：内容与问题的相关性、信息具体性、是否存在明显偏见或营销倾向、时效性
3. 只输出 JSON 数组，不要输出任何其他文字

输出格式（每条一个对象）：
[{{"source_id": "证据ID", "score": 0.85, "reason": "不超过30字的中文理由"}}]
"""
```

`_llm_score_batch(batch) -> dict[str, dict]` 实现：

- 构造 `evidence_list`：每条 `[{source_id}] {title} | {domain 或 doc_id} | {snippet前200字}`
- `response = self._llm.invoke(prompt)`；从 `response.content` 中提取 JSON（先直接 `json.loads`，失败用正则截取首个 `[...]` 子串再解析）
- 逐条校验：`source_id` 存在于本批、`score` 可转 float 并 clamp 到 [0,1]、`reason` 转 str；不合法项丢弃
- 任何异常 `except Exception` → 记 warning、返回 `{}`（整批回退先验）

### 3.3 接入点改造（`_fallbacks.py`）

`_fallback_audit(state)` 现有逐条 `_score_evidence` 的循环改为：

```python
# 伪代码 — 保持函数签名与返回结构完全不变
evidence_input = state.get("web_evidence", []) + state.get("local_evidence", [])
scorer = _get_evidence_scorer(state)      # 从 state/runtime 拿 LLM；拿不到则返回 None
if scorer is not None:
    evidence_pool = scorer.score_batch([dict(r) for r in evidence_input])
else:
    evidence_pool = [先验逐条评分的旧逻辑]  # 保持兼容
```

LLM 获取方式（执行时先读 `_fallbacks.py` 与 deep_dive/`runtime.py` 确认节点如何拿到 LLM）：

- 若 `_fallback_audit` 有 agent 入参路径 → 用该 agent 的 LLM（推荐，与节点温度策略一致：证据评审温度 0.2）
- 若无 → 从 `get_research_service()` 的 AgentBundle 取评审 agent（注意避免循环 import，必要时惰性导入）

**评分温度**：证据评审属判别任务，LLM 调用温度必须为 0.2（与项目「8 角色按职责分温度」约定一致；若拿到的 LLM 温度不符，记录到执行日志）。

### 3.5 性能与预算保护

- 批量评估：每批 ≤20 条，证据池通常 10~40 条 → 1~2 次 LLM 调用
- 该评分在 deep_dive 证据池构建后同步执行（在节点内，非 service 层），单批 20s 超时由 LLM 客户端自身超时兜底
- 迭代回环（reflect → 检索）会再次进入评分：对 `source_id` 已评分过的记录**跳过重复评估**——`_evidence.py` 维护按 `source_id` 的已评分缓存（dict，进程内），或直接依赖调用方只传新证据；执行时读 deep_dive 实际数据流后选择（倾向：每次只评估新增证据，旧证据沿用已写入 state 的分数）

## 6. 风险与回滚

- **风险 1**：LLM 评分增加 deep_dive 节点延迟（1~2 次调用 × 数秒）。缓解：批量 + 超时 + 失败整批回退先验，延迟上界可控。
- **风险 2**：JSON 输出不稳导致频繁回退。缓解：正则截取 + 字段级容错，仅剔除坏项。
- **回滚**：`evidence_llm_fusion=false` 一键回退纯先验；代码单 commit 可 revert。
