# R3.1 RabbitMQ 死信队列与消费幂等

> 阶段三 · 可靠性与运维 | 对应落地修复清单 #7：配置死信交换机，重试超限入 DLQ；消费端按 content hash 幂等
> 前置阅读：`docs/refactor/00_重构总览与执行指南.md`

## 1. 目标

补齐文档向量化异步管道的**可靠投递闭环**：消费失败消息不再被 `nack(requeue=False)` 直接丢弃，而是进入**死信队列（DLQ）**；消费端实现**幂等去重**（同一 chunk 消息重复投递不产生重复向量化）；DLQ 提供告警日志与人工重放入口。

**验收标准**：

- [ ] 业务队列声明时绑定 DLX（dead-letter-exchange）与死信路由键
- [ ] 消费失败（向量化异常）按「重试上限 → DLQ」处理，不再直接丢弃
- [ ] 重试计数：同一消息（按 delivery_tag 累计）失败超过上限（默认 3 次）后 `nack(requeue=False)` 路由进 DLQ
- [ ] 消费幂等：处理前查询该 chunk 的向量化状态，`indexed`（或已处理）状态直接 ACK 跳过
- [ ] DLQ 告警：消息进入 DLQ 时记 error 日志（含 doc_id / chunk_id / 失败原因）
- [ ] 人工重放：提供脚本或管理接口将 DLQ 消息重新投回业务队列
- [ ] ⚠️ 队列结构变更（DLX 声明）需在执行前告知用户重建队列的影响，经确认后执行
- [ ] 单元测试全部通过，全量回归无破坏

## 2. 现状分析（动手前先完整阅读以下文件）

| 文件 | 现状要点 |
| --- | --- |
| `app/backend/infra/mq_client.py` | `MQProducer`：声明 topic exchange `chunk-sync`、持久化队列 `chunk-sync.queue`、binding key `chunk.sync.#`；`publish_chunks(messages)` 逐条 `delivery_mode=2`、routing key `chunk.sync.{doc_id}`，返回成功/失败 |
| `app/backend/infra/chunk_consumer.py` | `ChunkSyncConsumer`：启动时 `_compensate_pending_messages()`（outbox 补偿重投）；`prefetch_count=1`、`auto_ack=False`；成功 `basic_ack`；失败 `basic_nack(requeue=False)`——**注释自己写明「实际生产中应配置死信队列 (DLX) 接收失败消息」**，即当前失败消息直接丢弃 |
| `app/backend/infra/postgres_client.py` | `chunk_sync_messages`（outbox 本地消息表：status/retry_count/sent_at）；`document_chunks`（content_hash 有索引、按 id ON CONFLICT 幂等插入）；ChunkRepository 的状态回写方法（执行时确认 chunk 级 `pending → indexed/failed` 的现有方法名） |
| `app/backend/service/document_service.py` | 上传主链路：MinIO → 解析切块 → `insert_document_with_chunks`（PG 本地事务含 outbox 消息）→ `publish_chunks` → `mark_messages_sent`；上传前算 `content_hash = md5(file_content)` |
| 消费向量化的实现位置 | 执行时在 `chunk_consumer.py` 内确认 `_process_message` 的实际处理逻辑（向量库写入 + 状态回写 PG 的代码位置） |

**现状问题**：向量化失败 = 消息直接蒸发（nack 不 requeue 也不进 DLQ），且无告警；MQ 层重复投递（outbox 补偿重投 + 手动 ACK 前崩溃的经典重复源）没有消费侧幂等闸门，可能重复向量化同一 chunk。

## 3. 详细设计

### 3.1 队列拓扑（DLX 声明）

```
业务拓扑：
  exchange: chunk-sync (topic)
  queue:   chunk-sync.queue    ──绑定──> routing_key: chunk.sync.#
                                  │
                                  │ 消费失败重试超限 nack(requeue=False)
                                  ▼
死信拓扑（新增声明）：
  exchange: chunk-sync-dlx (topic)               ← 业务队列的 x-dead-letter-exchange
  queue:   chunk-sync-dlq                         ← 绑定 routing_key: chunk.sync.dead
          （业务队列的 x-dead-letter-routing-key = chunk.sync.dead）
```

**声明代码**（生产者 `MQProducer.connect()` 与消费者 `ChunkSyncConsumer._run()` 都要声明，保持与现有「两侧各自声明」的风格一致）：

```python
# 死信交换机与队列（幂等声明，参数见 3.2 的迁移注意）
channel.exchange_declare(exchange="chunk-sync-dlx", exchange_type="topic", durable=True)
channel.queue_declare(
    queue="chunk-sync-dlq",
    durable=True,
    arguments={"x-queue-mode": "lazy"},   # DLQ 磁盘型，防内存膨胀
)
channel.queue_bind(queue="chunk-sync-dlq", exchange="chunk-sync-dlx", routing_key="chunk.sync.dead")

# 业务队列声明改为带 DLX 参数
channel.queue_declare(
    queue="chunk-sync.queue",
    durable=True,
    arguments={
        "x-dead-letter-exchange": "chunk-sync-dlx",
        "x-dead-letter-routing-key": "chunk.sync.dead",
    },
)
```

> **⚠️ 迁移注意（需向用户说明并确认）**：已存在的 `chunk-sync.queue` 参数不能原地修改（RabbitMQ 会报 PRECONDITION_FAILED）。需要：停消费者 → 删除旧队列（`rabbitmqadmin delete queue` 或管理台）→ 以新参数重新声明 → 未消费消息会丢失（个人项目量级可接受，或先将队列消费完再删）。该步骤为**需用户确认**操作。

### 3.2 消费失败处理与重试计数

`ChunkSyncConsumer` 的消息处理回调改造：

```python
RETRY_LIMIT = 3   # 同一 delivery 的重试上限（config.json: chunk_retry_limit）

def _handle_delivery(self, ch, method, properties, body):
    delivery_tag = method.delivery_tag
    try:
        self._process_message(body)          # 现有处理逻辑（向量库写入 + PG 状态回写）
        ch.basic_ack(delivery_tag=delivery_tag)
        self._retry_counts.pop(delivery_tag, None)     # 成功清理计数
    except Exception as exc:
        count = self._retry_counts.get(delivery_tag, 0) + 1
        self._retry_counts[delivery_tag] = count
        logger.warning("[chunk-consumer] 处理失败(%d/%d) | error=%s", count, RETRY_LIMIT, exc)
        if count >= RETRY_LIMIT:
            logger.error("[chunk-consumer] 重试超限进 DLQ | delivery=%s | body=%s | error=%s",
                         delivery_tag, body[:200], exc)      # DLQ 告警（error 级）
            self._retry_counts.pop(delivery_tag, None)
            ch.basic_nack(delivery_tag=delivery_tag, requeue=False)   # → DLX → DLQ
        else:
            ch.basic_nack(delivery_tag=delivery_tag, requeue=True)   # 重回队列重试

# 重试计数改为以「消息内容」为 key（delivery_tag 在 requeue 后会变化！）
# 修正：self._retry_counts 的 key 用消息内容 hash（body 的 md5），并设置过期淘汰（dict 超 1000 条清最旧）
```

> **关键陷阱**：`requeue=True` 后消息重新入队，`delivery_tag` 是**递增不复用**的——重试计数必须以**消息体 hash** 为 key，不能用 delivery_tag。设计修正为 `_retry_counts[md5(body)]`。计数器为进程内存态（重启清零，可接受：重启本身也是新一次重试机会）。

> 另一个陷阱：`requeue=True` + prefetch=1 + 持续失败 = 无限快速循环。两个缓解措施任选其一（推荐 a）：
> a. 失败后短暂 `time.sleep(min(count * 2, 10))` 再 nack（消费线程内的简单退避）
> b. 直接不做 in-queue 重试：失败即计数（消息不 requeue，靠 outbox 补偿机制在消费者重启时重投实现「重试」）——执行时读 `_compensate_pending_messages` 的语义后选择与现有 outbox 补偿不冲突的方案，并记录决策

### 3.3 消费幂等（处理前状态检查）

`_process_message(body)` 开头插入幂等闸门：

```python
def _process_message(self, body: bytes):
    payload = json.loads(body)
    chunk_id = payload.get("chunk_id")           # 以实际 payload 字段为准
    # 幂等检查：该 chunk 已成功向量化 → 直接返回（外层 ACK）
    status = self._repo.get_chunk_status(chunk_id)      # 新增 repo 方法，执行时若已有等价方法则复用
    if status == "indexed":
        logger.info("[chunk-consumer] chunk 已向量化，幂等跳过 | chunk=%s", chunk_id)
        return
    ...原有向量化逻辑（失败时回写 failed 状态）...
```

补充**向量化级幂等**（可选增强，P1）：向 Milvus 写入前按 `content_hash + doc_id` 查询是否已存在等价向量（成本高，若 Milvus 侧写入本身幂等——同 content upsert 覆盖——则跳过本层）。执行时确认 Milvus 写入语义，决策记入执行日志。

### 3.4 DLQ 人工重放

新增脚本 `scripts/replay_dlq.py`（沿用 `scripts/` 现有脚本风格）：

```
用法：python scripts/replay_dlq.py [--limit N] [--dry-run]
行为：
  1. 从 chunk-sync-dlq 取（basic_get）最多 N 条消息（默认全部）
  2. --dry-run：只打印 doc_id/chunk_id 与首次失败原因（x-death 头），不重投
  3. 正式模式：将消息以原 routing key（chunk.sync.{doc_id}）重新 publish 到 chunk-sync 业务交换机，
     publish 成功后 ACK DLQ 中的该消息
  4. 结束打印：重放 N 条、成功 M 条、失败 K 条
```

## 6. 风险与回滚

- **风险 1**：旧队列删除丢失未消费消息。缓解：删除前消费到空或确认 outbox 补偿可重投（PG 本地消息表是事实源，消息可由补偿重建——这正是 outbox 设计的价值）。
- **风险 2**：requeue 快速循环打满 CPU。缓解：3.2 的退避或方案 b（依赖 outbox 补偿重试）。
- **风险 3**：幂等检查依赖 chunk 状态回写的正确性——若 `_process_message` 在向量库写入成功后才回写状态、回写失败会导致下次重投重复向量化。缓解：状态回写失败视为整条处理失败（抛异常走重试），保证「成功状态 ⇒ 已向量化」不变式。
- **回滚**：DLX 参数只影响失败消息去向；`rabbitmqctl` 删除带参队列恢复旧声明即可（消息丢失风险见风险 1 的 outbox 兜底）。
