# R2.2 断线重连与续流

> 阶段二 · 流式与交互 | 对应落地修复清单 #4（后半）：前端断线检测 + 指数退避 + resume 续流；事件重放幂等
> 前置阅读：`docs/refactor/00_重构总览与执行指南.md`；建议在 R2.1 之后执行

## 1. 目标

实现完整的断线恢复链路：**网络异常断开 → 前端指数退避自动重连 → 调用 resume 接口从最后 checkpoint 续流 → 事件重放不丢不重**。用户主动取消（AbortError）不触发重连。

**核心机制说明（执行前必须理解）**：

1. SSE 连接断开时，FastAPI 会 cancel 流式 generator → `stream_research` 内 `CancelledError` → graph 任务终止，但 **LangGraph Checkpointer 已保存节点级 checkpoint**（正在执行的节点会整体重跑，已完成的节点不重跑）
2. 因此前端重连后调用 `POST /api/v1/research/resume` `mode=continue`（`astream(None, config)` 从最后 checkpoint 续跑）即可恢复
3. `run_id` 每次不同 → `message_id = f"{run_id}:{node}"` 变化 → 续流产生的 token 挂在新 message_id 下，**前端必须先清掉旧的半截 streaming 消息**，否则文本重复

**验收标准**：

- [ ] 前端 `useEventStream` 增加重连流程：非 AbortError 的网络错误触发，指数退避（1s/2s/4s/8s/16s，上限 30s），最多 5 次
- [ ] 每次重连前先调 `GET /threads/{thread_id}/state`：`resumable=true` 才继续；`awaiting_input`（HITL 中断态）停止重连并保留中断现场；`idle 且不可恢复` 停止
- [ ] 重连前调消息同步接口对齐本地消息（清除旧的半截 streaming 消息），再调 resume 续流
- [ ] 前端事件处理幂等：`sources.found` 按 url+title 去重、`message.start` 新 message_id 到达时同 node 旧 streaming 消息被替换
- [ ] 用户主动取消不触发重连（AbortError 分支）
- [ ] 重连全程 UI 有可见状态提示（reconnecting），失败次数用尽后正常报错
- [ ] 后端 `resume_stream` 无需结构性改动（已支持 mode=continue）；仅补充必要的幂等保证
- [ ] 前后端测试全部通过

## 3. 详细设计

### 3.1 前端：useEventStream 重连状态机

```ts
// 新增模块内状态（每个 thread 一份或全局单例如现有实现风格一致）
const RECONNECT_MAX_ATTEMPTS = 5
const RECONNECT_BASE_DELAY_MS = 1000
const RECONNECT_MAX_DELAY_MS = 30000

let reconnectAttempts = 0

async function runWithReconnect(threadId: string, payload: RunPayload): Promise<void> {
  try {
    const resp = await postStream(url, payload)
    await consumeSSE(resp, onEvent, onDone)
    reconnectAttempts = 0            // 成功结束，重置
  } catch (err) {
    if (isAbortError(err)) {          // 用户主动取消：不重连
      return
    }
    if (isUserCancelled()) {          // chat store 已置 cancelled（后端 cancel 已确认）：不重连
      return
    }
    if (reconnectAttempts >= RECONNECT_MAX_ATTEMPTS) {
      chat.markError(new Error('连接已断开，自动恢复失败'))
      return
    }
    await scheduleReconnect(threadId)
  }
}

async function scheduleReconnect(threadId: string): Promise<void> {
  reconnectAttempts += 1
  const delay = Math.min(RECONNECT_BASE_DELAY_MS * 2 ** (reconnectAttempts - 1), RECONNECT_MAX_DELAY_MS)
  chat.setReconnecting(true)          // 新增 store 状态：UI 显示"连接中断，正在恢复…"
  await sleep(delay)

  // ① 状态检查：决定是否继续重连
  const state = await rest.fetchThreadState(threadId)
  if (state.status === 'awaiting_input') {
    // HITL 中断态：中断卡片会通过 interrupt store 重建，停止重连
    chat.setReconnecting(false)
    reconnectAttempts = 0
    return
  }
  if (!state.resumable) {
    // 已结束或不可恢复：拉一次消息对齐后停止
    await syncThreadMessages(threadId)
    chat.setReconnecting(false)
    return
  }

  // ② 消息对齐：清除旧的半截 streaming 消息，用服务端事实重建
  await syncThreadMessages(threadId)

  // ③ resume 续流（mode=continue）
  try {
    const resp = await postStream(resumeUrl, { thread_id: threadId, mode: 'continue' })
    await consumeSSE(resp, onEvent, onDone)
    reconnectAttempts = 0
    chat.setReconnecting(false)
  } catch (err) {
    if (isAbortError(err) || isUserCancelled()) { chat.setReconnecting(false); return }
    await scheduleReconnect(threadId)   // 递归重试（受 attempts 上限保护）
  }
}
```

实现要点：

- `resume`（HITL 主动恢复入口）**不套重连状态机**——保持现状语义；只有 run 主入口套 `runWithReconnect`。若探索发现 run/resume 共用内部函数，在公共函数上加 `reconnectable: boolean` 参数区分
- `isUserCancelled()`：读 chat store——用户点停止按钮时前端已置 `cancelled`（乐观取消，项目现有行为）
- `sleep` 期间用户可能切换 thread / 发起新 run：重连前检查「当前 thread 仍是发起重连的 thread 且仍处于 streaming 态」，否则放弃

### 3.2 前端：syncThreadMessages（消息对齐）

```ts
async function syncThreadMessages(threadId: string): Promise<void> {
  const messages = await rest.fetchThreadMessages(threadId)   // GET /threads/{id}/messages
  chat.replaceThreadMessages(threadId, messages)               // 新增 store action：整体替换
}
```

`replaceThreadMessages` 语义：以服务端返回为唯一事实，整体替换该 thread 的消息列表，清掉所有 streaming/thinking 中间态。若后端 `GET /threads/{thread_id}/messages` 路由不存在（执行时确认），在 `research_router.py` 补一个只读路由（service.get_thread_messages 已实现，直接包装，响应格式与前端期望对齐）。

### 3.3 前端：事件幂等（chat / sources store 改造）

| 事件 | 现状风险 | 幂等策略 |
| --- | --- | --- |
| `sources.found` | append 型，断点在 web_search 节点重跑时重复追加 | store 内按 `url + title`（web）/ `chunk_id`（kb）去重后再追加 |
| `message.start` / `message.delta` | resume 后新 message_id，旧半截消息残留 | 3.2 的 replace 已清；防御性补充：`message.start` 到达时若同 `node` 存在 `streaming=true` 的旧消息，先移除旧消息再插入新消息 |
| `agent.status` | 状态覆盖型 | 天然幂等，不改 |
| `run.completed` 等终态 | 重复到达 | store 终态字段为覆盖写，天然幂等，确认后不改 |

### 3.4 后端小改动

1. **（若缺）补只读路由**：`GET /threads/{thread_id}/messages` → `research_service.get_thread_messages(thread_id)`（先 grep research_router.py 确认是否已存在）
2. **resume_stream 幂等补充**：`resume_stream` 开头发现 `get_state().status == awaiting_input` 时直接返回 `run.error(code="AwaitingInput")`？**不做**——前端已在前置检查拦截，后端保持宽容（resume mode=continue 对 awaiting_input 的行为是 `astream(None)` 重放 interrupt，`interrupt.raised` 会再次发出，前端 interrupt store 幂等覆盖，无害）
3. **state 接口确认**：`get_state()` 返回 `resumable` 与 `status` 字段（代码已实现，见 672–732 行），确认路由已暴露；未暴露则补

## 6. 风险与回滚

- **风险 1**：重连风暴（服务端宕机时 5 次×多 thread 重试）。缓解：退避上限 30s + 最多 5 次 + resumable 前置检查。
- **风险 2**：断点恰在 write 节点中途 → 重跑整节点，LLM 重复计费。接受（节点级 checkpoint 是 LangGraph 固有粒度），文档口径即为「从最后存档续跑」。
- **风险 3**：与用户手动操作竞态（重连过程中用户发新问题）。缓解：3.1 的「thread 一致性 + streaming 态」双重检查。
- **回滚**：前端改动为主，revert 即可；后端仅补只读路由，无行为变更。
