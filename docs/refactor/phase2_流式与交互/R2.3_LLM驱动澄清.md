# R2.3 LLM 驱动需求澄清

> 阶段二 · 流式与交互 | 对应落地修复清单 #5：clarify 节点由规则判定升级为「LLM 置信度自评 + 澄清问题生成」，规则仅作快速通道
> 前置阅读：`docs/refactor/00_重构总览与执行指南.md`

## 1. 目标

将 clarify 节点的「是否需要澄清」判定从**纯规则**（query 太短 / 含模糊词）升级为**双层设计**：

- **第一层（规则快速通道）**：现有规则命中 → 直接判定需要澄清，零 token 成本（保持现有行为）
- **第二层（LLM 精判）**：规则未命中时，LLM 对需求做置信度自评；置信度不足则生成**带选项的澄清问题**，最多 2 轮；用户回答充分性同样由 LLM 判定，充分则进入 plan，不充分且未超轮次则继续追问

**验收标准**：

- [ ] 规则快速通道保留且行为不变（短 query / 模糊词直接触发澄清）
- [ ] LLM 判定输出结构化 JSON：`{"needs_clarification": bool, "confidence": float, "reason": str, "questions": [{"question": str, "options": [str]}]}`
- [ ] 澄清问题带 2~4 个选项（供前端渲染选择）；questions 数量 1~3 个
- [ ] 澄清轮次上限 2（可配置 `hitl_config.clarify_max_rounds`），超限直接放行进入 plan
- [ ] 回答充分性由 LLM 判定：充分 → 进入 plan；不充分 → 追问（受轮次限制）
- [ ] LLM 调用失败/解析失败：**静默放行进入 plan**（宁可不澄清也不能卡死研究流程），记 warning
- [ ] 前端 ClarifyCard 支持渲染选项（点击选项填入输入框；仍允许自由输入）
- [ ] 单元测试全部通过，全量回归无破坏

## 3. 详细设计

### 3.1 clarify_node 双层判定流程

```python
def clarify_node(state, agent, agent_name, writer):
    query = state["query"]
    rounds = state.get("clarify_rounds", 0)          # 新增 state 字段，见 3.4
    clarifications = state.get("clarifications", [])  # 已有回答记录

    # ① 规则快速通道（零成本短路）
    if _rule_needs_clarification(query):
        return _raise_clarify_interrupt(state, writer, questions=_rule_questions(query))

    # ② 轮次上限检查（防无限追问）
    if rounds >= _max_rounds(state):                 # 默认 2
        return _goto_plan(state)

    # ③ LLM 精判（agent 为 None 时直接放行）
    if agent is None:
        return _goto_plan(state)
    verdict = _llm_clarify_verdict(agent, query, clarifications)
    if verdict is None:                               # LLM 失败 → 静默放行
        return _goto_plan(state)

    if not verdict["needs_clarification"]:
        return _goto_plan(state)                     # 置信度足够，直接规划

    # ④ 发起澄清中断（LLM 生成的带选项问题）
    return _raise_clarify_interrupt(state, writer, questions=verdict["questions"])
```

恢复路径（interrupt resume 后的二次进入）：

```python
# 用户提交 answers 后 Command(resume=...) 回到 clarify 节点继续执行：
# ⑤ 回答充分性判定
answers = state["clarifications"][-1]["answers"]     # 本次回答
if rounds >= _max_rounds(state):
    return _goto_plan(state)                         # 追问上限，放行
sufficiency = _llm_answer_sufficiency(agent, query, clarifications)
if sufficiency is None or sufficiency["sufficient"]:
    return _goto_plan(state)                          # 判定失败按充分处理（放行），不卡死
# 不充分 → rounds += 1，用 sufficiency["followup_questions"] 继续发起澄清中断
```

> 执行提示：以上为流程语义。clarify_node 实际的 interrupt/resume 控制流以现有代码为准（现有代码已实现「resume 后 goto plan / 再问」的骨架），本任务是把「是否再问」「问什么」两处决策点换成 LLM 驱动，**不改变中断与 Command 机制本身**。

### 3.2 LLM 判定 prompt（两段，均输出纯 JSON）

**判定 prompt（③）**：

```python
CLARIFY_VERDICT_PROMPT = """你是研究需求分析专家。判断以下研究问题是否需要向用户澄清才能开展有效研究。

研究问题：{query}

{clarified_context}

评估维度：范围是否明确、术语是否可指代消歧、时间范围是否清楚、输出物要求是否明确。

要求：
1. confidence 为你对「已可开展研究」的置信度，0~1 小数
2. needs_clarification 为 true 时必须给出 1~3 个澄清问题，每个问题附 2~4 个选项
3. 只输出 JSON，不要其他文字

输出格式：
{{"needs_clarification": true, "confidence": 0.35, "reason": "时间范围不明确",
  "questions": [{{"question": "研究的时间范围是？", "options": ["近一年", "近三年", "不限"]}}]}}
"""
```

**充分性判定 prompt（⑤）**：

```python
CLARIFY_SUFFICIENCY_PROMPT = """你是研究需求分析专家。用户已对研究问题做出澄清回答，判断信息是否充分。

研究问题：{query}
澄清问答记录：
{qa_pairs}

要求：
1. sufficient 为 true 表示信息已足够开展研究
2. 不充分时给出 1~2 个追问问题（附选项），只针对仍缺失的关键信息
3. 只输出 JSON，不要其他文字

输出格式：
{{"sufficient": false, "reason": "仍缺目标用户定位",
  "followup_questions": [{{"question": "...", "options": ["...", "..."]}}]}}
"""
```

`_llm_clarify_verdict` / `_llm_answer_sufficiency` 实现规范：

- `agent.invoke(...)`（同步，与其他节点一致——先读一个现有节点如 intent 确认调用方式）
- 解析：`json.loads(content)`，失败则正则截取 `{...}` 再试，仍失败返回 `None`
- 字段校验：`confidence` clamp [0,1]；`questions` 每项必须有非空 `question`；`options` 缺省容忍为 `[]`；全部不合法返回 `None`
- 任何异常 `except Exception` → warning 日志 + 返回 `None`

### 3.3 agent 注入

- `runtime.py` 的 `build_agents` 增加 clarify agent：模型 qwen-turbo（轻量判定任务，无需主力模型）、温度 0.0（判定类任务）、无 tools

## 6. 风险与回滚

- **风险 1**：LLM 判定拖慢首响应（clarify 在 intent 之后、plan 之前，增加一次 qwen-turbo 调用约 1~2s）。缓解：qwen-turbo + 失败放行；规则快速通道先拦截明显场景。
- **风险 2**：LLM 输出不稳定导致 JSON 解析失败。缓解：双重解析 + 失败放行（最坏情况等于旧行为——不澄清直接研究）。
- **风险 3**：误放行/误拦截抖动（同一 query 两次判定不一致）。缓解：温度 0.0。
- **回滚**：判定函数返回 None 即回退旧链路；整体 revert 单 commit。配置 `clarify_max_rounds=0` 时 LLM 通道仍可用于首轮判定——若需完全回退规则版，revert 代码。
