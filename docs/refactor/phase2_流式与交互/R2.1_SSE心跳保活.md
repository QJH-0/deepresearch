# R2.1 SSE 心跳保活（注释帧）

> 阶段二 · 流式与交互 | 对应落地修复清单 #4（前半）：补注释帧心跳（15s），防中间代理空闲超时断连
> 前置阅读：`docs/refactor/00_重构总览与执行指南.md`

## 1. 目标

为 SSE 流式输出增加**注释帧心跳**：当流超过 15 秒没有任何事件产出时，服务端下发 SSE 注释帧 `: ping\n\n` 保活。心跳不占用事件类型（不是 `data:` 帧，不进 `EVENT_REGISTRY`），前端现有解析逻辑天然忽略注释行，无需协议变更。

**验收标准**：

- [ ] `stream_research` 与 `resume_stream` 两条流式链路均支持心跳
- [ ] 心跳间隔可配置（`config.json` → `sse_heartbeat_seconds`，默认 15，`0` 表示关闭）
- [ ] 有事件正常流动时不发心跳（只在空闲超时后发）
- [ ] 心跳帧格式严格为 `": ping\n\n"`，不破坏事件流（两条 data 帧之间插入注释帧后前端解析不受影响）
- [ ] 心跳发送期间上游被取消（CancelledError）时正确终止并发出 `run.cancelled`
- [ ] 单元测试全部通过，全量回归无破坏

## 2. 现状分析（动手前先完整阅读以下文件）

| 文件 | 现状要点 |
| --- | --- |
| `app/backend/service/research_service.py` | `stream_research()`（约 210–347 行）与 `resume_stream()`（约 817–943 行）均为 `async for mode, chunk in self._app.astream(...)` 直接迭代：`custom` 通道处理 token/progress/sources，`updates` 通道处理 `__interrupt__` 与节点完成。**无任何超时/心跳机制**——deep_dive 等长节点（LLM 检索评审耗时可 >30s）期间连接完全静默 |

**现状问题**：浏览器/代理（Nginx、公司网关）对长连接通常有 30~60s 空闲超时；deep_dive 与多轮检索期间静默，极易被掐断，表现为「研究到一半前端报网络错误」。

## 3. 详细设计

### 3.1 心跳包装器（research_service.py 模块级新增）

核心思路：**不改动两条链路的业务逻辑**，只把「从 astream 取下一个 chunk」这个动作包上空闲超时：

```python
HEARTBEAT_FRAME = ": ping\n\n"

async def _astream_with_heartbeat(
    astream_iter,          # self._app.astream(...) 返回的 async iterator
    interval: float,       # 0 表示关闭心跳
):
    """逐项产出 astream chunk；超过 interval 秒无产出时先产出心跳帧标记。

    产出物为 ("heartbeat", None) 或 (mode, chunk)，调用方据此 yield 心跳注释帧。
    """
    aiter = astream_iter.__aiter__()
    while True:
        if interval <= 0:
            chunk_mode, chunk = await anext(aiter)      # 直接透传
            yield chunk_mode, chunk
            continue
        try:
            # 等待下一个 chunk，最多等 interval 秒
            get_next = asyncio.ensure_future(anext(aiter))
            done, _ = await asyncio.wait({get_next}, timeout=interval)
            if get_next in done:
                chunk_mode, chunk = get_next.result()
                yield chunk_mode, chunk
            else:
                yield "heartbeat", None                 # 超时：发心跳，任务继续等
                yield await get_next                    # 继续等（不取消！）
        except StopAsyncIteration:
            return
```

> 实现提示：上面是设计语义示意。落地时注意三点：
> 1. `asyncio.wait` 超时后**不得 cancel** `get_next`，下一轮循环直接 `await` 同一个 future；
> 2. `anext(aiter)` 需要处理 `StopAsyncIteration` 结束整条流；
> 3. 被 `CancelledError` 打断时 future 要 `cancel()` 清理，异常向外传播由外层 `except asyncio.CancelledError` 统一处理（现有逻辑已正确发 `run.cancelled`）。

### 3.2 两条链路接入

`stream_research` 与 `resume_stream` 中现有：

```python
async for mode, chunk in self._app.astream(input_state, config, stream_mode=["custom", "updates"]):
```

改为：

```python
heartbeat_interval = _get_heartbeat_interval()   # 读配置，见 3.3
async for mode, chunk in _astream_with_heartbeat(
    self._app.astream(input_state, config, stream_mode=["custom", "updates"]),
    heartbeat_interval,
):
    if mode == "heartbeat":
        yield HEARTBEAT_FRAME
        continue
    # ……原有 if mode == "custom" / "updates" 逻辑完全不变……
```

> 更简单的备选实现（允许采用）：用 `aiter = self._app.astream(...).__aiter__()` + `asyncio.wait_for(anext(aiter), timeout=interval)` 循环，`asyncio.TimeoutError` 时 yield 心跳。注意 `wait_for` 超时会 cancel 内部任务——**所以必须用 `asyncio.wait({task}, timeout=)` 方案**，`wait_for` 不可用（会杀掉正在执行的 graph step）。此为已知陷阱，编码时务必避开。

### 3.3 配置

`config.json`：

```json
{
  "sse_heartbeat_seconds": 15
}
```

`BusinessSettings` 增加字段：

```python
sse_heartbeat_seconds: int = 15
```

`_get_heartbeat_interval()` 从 BusinessSettings 读取（参考 `research_service.py` 中现有读取 runtime 配置的方式，如 `self._build_runtime_config` 或直接 `get_settings()`；以代码现状为准），≤0 视为关闭。

### 3.4 前端兼容性确认（不改代码，加测试固化）

- `consumeSSE` 的切帧逻辑：`buffer.split('\n\n')` → `": ping"` 单独成帧 → `line.startsWith('data:')` 为 false → 跳过。行为正确

## 6. 风险与回滚

- **风险 1**：错误使用 `asyncio.wait_for` 导致 graph step 被 cancel、研究任务被误杀。缓解：设计已明确禁用 `wait_for`，测试 T2.1-02 专门覆盖「超时后仍能拿到完整 chunk」。
- **风险 2**：心跳与 `run.completed` 竞态（心跳帧在结束事件后发出）。缓解：心跳只在 astream 迭代内部产生，结束后链路自然收尾，不会晚于终止事件。
- **回滚**：`sse_heartbeat_seconds=0` 关闭心跳即回到旧行为；代码单 commit 可 revert。
