# R2.4 thinking 深度思考流式透传

> 阶段二 · 流式与交互 | 对应落地修复清单 #6：接入 qwen-plus 深度思考输出，节点推送 message.thinking 事件（前端已具备渲染能力）
> 前置阅读：`docs/refactor/00_重构总览与执行指南.md`

## 1. 目标

打通**深度思考（reasoning）流式透传**链路：撰写类节点（write / deep_dive / analyze 中输出长文本的节点）启用 qwen-plus 深度思考，LLM 流式输出中的 `reasoning_content` 增量经 StreamWriter → `astream custom` 通道 → `message.thinking` SSE 事件 → 前端思考面板（可折叠/渐隐预览，前端已实现渲染与 store 分发，仅缺事件源）。

**验收标准**：

- [ ] 深度思考按节点可配置开关（`config.json` → `thinking_nodes`，默认 `["write", "deep_dive", "analyze"]`，空数组关闭）
- [ ] LLM 构建方式支持 `enable_thinking` 参数（DashScope 兼容模式），不影响现有非思考调用
- [ ] reasoning 增量以 custom 事件 `{"type": "thinking", "node": ..., "text": ...}` 推送到 StreamWriter
- [ ] `research_service.py` 的 custom 通道新增 `thinking` 分支，转发为 `message.thinking` 事件（`MessageThinkingData(message_id, text)` schema 已存在，禁止改 schema）
- [ ] thinking 与正文 token 的 message_id 区分：thinking 流复用同节点 message_id（前端按事件类型分流到思考面板，确认前端 store 行为后对齐）
- [ ] 模型不支持 enable_thinking 时调用不报错（参数不生效或被忽略均可），正文流正常
- [ ] 单元测试全部通过，全量回归无破坏

**现状问题**：`message.thinking` 事件「已定义、未发射」——前端思考面板永远是空的；用户无法看到模型的推理过程，深度研究体验缺失关键一环。

## 3. 详细设计

### 3.1 LLM 层：enable_thinking 接入

DashScope qwen-plus 深度思考的两种接入路径（执行时二选一，**先做步骤 1 的实测确认**）：

**路径 A：ChatOpenAI 兼容模式 + extra_body**（推荐，若项目 LLM 构建可切换）

```python
from langchain_openai import ChatOpenAI

llm = ChatOpenAI(
    api_key=api_key,
    model="qwen-plus",
    base_url="https://dashscope.aliyuncs.com/compatible-mode/v1",
    temperature=temperature,
    extra_body={"enable_thinking": True},     # qwen-plus 深度思考开关
)
```

**路径 B：ChatTongyi 原生**（若 ChatTongyi 支持透传 DashScope 参数）

```python
ChatTongyi(model="qwen-plus", temperature=temperature, enable_thinking=True)
```

> ChatTongyi 是否接受 `enable_thinking` 需实测：不支持会抛 TypeError——捕获后记录并改走路径 A。**不允许**给 ChatTongyi 传参后静默吞掉的实现（参数没生效却以为开了思考）。

**验证生效的判据**：流式响应的 chunk 中出现 `additional_kwargs["reasoning_content"]`（或 chunk 对象的 `reasoning_content` 属性，以实际返回结构为准）。

### 3.2 构建工厂改造

`runtime.py`（及 `models.py` 若两处都需要）的 agent 构建：

```python
def build_agent(model, api_key, prompt_key, temperature, tools, enable_thinking: bool = False):
    # enable_thinking=True 时按 3.1 所选路径构建；False 时保持现状构建
    ...
```

`build_agents` 中按 `config.thinking_nodes` 列表决定哪些节点的 agent 开思考：

```python
thinking_nodes = {"write", "deep_dive", "analyze"}   # 来自 config.json，默认值见 3.5
agents[prompt_key] = build_agent(..., enable_thinking=(prompt_key in thinking_nodes))
```

> 注意：开启 thinking 的节点建议 temperature 保持各节点现值不变（thinking 模式下部分模型会强制覆盖 temperature，属模型侧行为，不做代码干预）。

### 3.3 节点层：reasoning 增量捕获与推送

节点流式输出处（执行时以实际流式捕获代码为准，典型形态）：

```python
async for chunk in agent.astream(...):
    reasoning = getattr(chunk, "reasoning_content", None) or \
                chunk.additional_kwargs.get("reasoning_content", "") \
                if hasattr(chunk, "additional_kwargs") else None
    if reasoning:
        writer({"type": "thinking", "node": agent_name, "text": str(reasoning)})
    content = chunk.content
    if content:
        writer({"type": "token", "node": agent_name, "text": str(content)})
```

> 若节点的流式捕获在 service 层（`stream_mode="messages"` 的 chunk 遍历），则在 service 层同一位置加 thinking 分支——**哪里拿到 token 就在哪里拿 reasoning**，两处不会重复实现。执行时先 grep `writer(` 与 `astream` 定位全部推流点。

### 3.4 service 层：custom 通道 thinking 分支

`stream_research` 与 `resume_stream` 的 custom 处理中，`token` 分支旁新增：

```python
elif evt_type == "thinking":
    node = chunk.get("node", "")
    text = chunk.get("text", "")
    mid = f"{run_id}:{node}"
    # 与 token 分支共用 message_id：前端按事件类型分流（thinking → 思考面板，delta → 正文）
    # message.start 想必在 token 首帧触发；若 thinking 先于 token 到达（深度思考先输出），
    # 需把 seen_nodes 的 message.start 触发逻辑同样套在 thinking 分支上（复用同一 mid）：
    if node not in seen_nodes:
        seen_nodes.add(node)
        yield sse(event("message.start", message_id=mid, node=node))
    yield sse(event("message.thinking", message_id=mid, text=text))
```

（resume_stream 中无 seen_nodes 机制则按其现状对齐——执行时读代码后保持两条链路行为一致。）

## 6. 风险与回滚

- **风险 1**：thinking 开启显著增加首 token 延迟（模型先思考后输出）。缓解：只对撰写类节点开启（检索/意图节点不参与）；`thinking_nodes` 可配置随时关闭。
- **风险 2**：reasoning 输出极长导致前端内存与渲染压力。缓解：前端已有折叠/渐隐交互（简历口径）；thinking 文本上限截断（单消息 thinking 累计 32k 字符后停止推送，记 info 日志）。
- **风险 3**：ChatTongyi 与 ChatOpenAI 构建方式不一致引入回归。缓解：非 thinking 节点构建路径完全不动，只有 thinking_nodes 内的节点走新构建。
- **回滚**：`thinking_nodes: []` 一键关闭全部思考；代码单 commit 可 revert。
