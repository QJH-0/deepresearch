# 三个问题修复计划

> 2026-09-06 综合排查与修复计划

## 问题 1：历史会话列表不显示

### 根因分析

通过完整阅读前端代码，发现以下问题链：

1. **`App.vue` 与 `ChatView.vue` 的 `load()` 时序冲突**：`App.vue` 的 `onMounted` 调用 `void load()`，`ChatView.vue` 的 `onMounted` 也调用 `void threads.load()`。两者同时发起相同请求，可能产生竞态——后返回的空结果覆盖先返回的正确结果。

2. **`ChatView.vue` 的 `watch(route.params.threadId)` 立即执行 (`{ immediate: true }`)**：路由无 threadId 时创建新会话 `threads.startNewThread()`，此时 `currentThreadId` 变为 `thread_xxx` 前缀。然后 `watch(threads.currentThreadId)` 触发 `openThread(id)`，但因为 `thread_xxx` 前缀被跳过（`if (threadId.startsWith('thread_')) return`），这个跳过本身没问题，但 watch 的连锁触发导致不必要的 re-render。

3. **CSS 布局导致 `.thread-groups` 被挤出可视区域**：`.app-sidebar` 设置了 `overflow-y: auto` 和 `height: 100%`，内部 `.sidebar-history` 设置了 `flex: 1; min-height: 0`。但 `.thread-history` 组件本身的 `.thread-groups` 也有 `overflow-y: auto; min-height: 0`，多层嵌套滚动容器在 flex 布局中可能导致内部内容高度坍缩为 0——如果 `.thread-history` 没有 `flex: 1` 撑满父容器，列表就不显示。

4. **`ThreadHistory.vue` 的 `threads` 数据来自 Pinia store 的解构**：`const { threads } = useThreadsStore()` 直接解构 ref，模板中 `threads.value` 访问正确。但 `visibleGroups` 计算依赖 `threads`（已解构的 ref），当 store 内部更新 `threads.value` 时，解构出来的 `threads` 变量指向同一个 ref 对象，Vue 模板中 `threads.length` 能正确触发响应式更新。这一点没问题。

5. **真正根因**：后端 `GET /api/v1/research/threads?user_id=default_user&limit=100` 接口依赖于 PostgreSQL 中 `chat_threads` 表有数据。如果后端 PG 未启动或表为空，返回空列表是正常的。但用户反馈"一直不显示"——需要检查前端 `fetchThreads` 是否正确请求到后端、后端是否正确返回了数据。**CSS 的 `.thread-history` 缺少 `flex: 1; min-height: 0` 撑满父容器**，导致 `.thread-groups` 在 flex 布局中被压缩为 0 高度。

### 修复方案

放弃当前的前端 `ThreadHistory.vue` 组件的 CSS 布局问题修补，改为参考 Vercel `ai-chatbot` 和 LangChain `chat-langchain` 的成熟实现模式重写：

1. **确保 `ThreadHistory.vue` 根元素 `flex: 1; min-height: 0; overflow: hidden`**，让列表区域在 flex 布局中正确占据剩余空间
2. **统一 `load()` 调用入口**：只在 `App.vue` 的 `onMounted` 中调一次，`ChatView.vue` 不再重复调用
3. **`thread-groups` 容器使用 `flex: 1; overflow-y: auto; min-height: 0`** 确保滚动区域正确

## 问题 2：DashScope rerank API 403 Forbidden

### 根因分析

通过安装 `dashscope` SDK (v1.27.4) 并直接调用 API 确认：

| 模型名 | 状态码 | 结论 |
|--------|--------|------|
| `gte-rerank` | 403 AccessDenied | **模型已下线/废弃，API Key 无权访问** |
| `gte-rerank-v2` | 200 OK | **可用** |
| `qwen3-rerank` | 200 OK | **可用** |

当前 `config.json` 和 `RAGConfig.rerank_model_name` 都使用 `"gte-rerank"`，该模型已被 DashScope 平台下线，导致每次 rerank 调用返回 403，降级到 LLMReranker（qwen-plus 生成式排序）。

### 修复方案

将默认模型名从 `gte-rerank` 改为 `gte-rerank-v2`（向后兼容更好，`qwen3-rerank` 是更新的模型但可能有额度限制差异）。

涉及文件：
- `config.json`：`rerank_model_name` 字段值
- `app/backend/config/settings.py`：`BusinessSettings.rerank_model_name` 默认值
- `app/mult_agents/rag/core.py`：`RAGConfig.rerank_model_name` 默认值

## 问题 3：web 检索到几十条数据但最终"证据不足"

### 根因分析

追踪完整数据流：

```
web_search_node
  → web_search_records (DuckDuckGo) 返回 N 条 raw_records
  → _dedupe_sources 去重
  → _minimal_record_filter 过滤空记录
  → _invoke_json_agent (LLM 整理证据) ← LLM 可能返回空 evidence 列表
  → _prune_evidence_to_allowed_sources (source_id 匹配过滤)
  → _enrich_evidence_from_raw (补充 url/title)
  → 最终 evidence 列表写入 state["web_evidence"]
```

然后在 `write_node` 中：

```python
_check_evidence_sufficiency(state)
  → web_evidence = state.get("web_evidence", [])  # ← 如果为 0 条
  → local_evidence = state.get("local_evidence", [])  # ← 如果也为 0 条
  → total = 0 → return False, "没有从任何来源检索到可用证据"
```

**核心问题在 `_invoke_json_agent`**：这个函数调用 LLM 来"整理"原始 web 搜索记录为结构化 evidence JSON。如果 LLM 返回的 JSON 格式不匹配（`payload.get("evidence")` 不是 list 或为空），虽然有 `fallback` 兜底，但 `_prune_evidence_to_allowed_sources` 会用 `allowed_source_ids` 过滤——如果 LLM 返回的 evidence 中的 `source_id` 与 raw_records 中的不匹配，所有 evidence 都会被过滤掉。

**具体场景**：
1. DuckDuckGo 返回 20-40 条原始记录（`raw_count` 高）
2. `_assign_source_ids` 为每条分配 `WEB1_1-1` 格式的 ID
3. LLM 整理证据时，可能丢失或改写了 source_id（如返回 `"WEB1_1-1"` 写成了 `"web1_1-1"` 大小写不同）
4. `_prune_evidence_to_allowed_sources` 严格匹配 source_id，大小写不匹配 → 全部被过滤
5. 最终 `evidence` 列表为空 → `web_retrieval_stats.kept_count = 0`
6. `state["web_evidence"]` 为空 → `_check_evidence_sufficiency` 判定"证据不足"

### 修复方案

1. **`_prune_evidence_to_allowed_sources` 改为大小写不敏感匹配**：source_id 统一 `upper()` 后比较
2. **LLM 返回空 evidence 时降级使用 fallback**：当 `_prune_evidence_to_allowed_sources` 过滤后为空但 raw_records 非空时，直接使用 fallback evidence
3. **`_check_evidence_sufficiency` 增加 raw_count 维度**：如果 `web_retrieval_stats.raw_count > 0` 但 `kept_count = 0`，说明是 LLM 整理环节出了问题，不应判定为"没有从任何来源检索到可用证据"

## 修复结果

### 问题 1 最终修复（2026-09-07）

**真正根因**：Pinia setup store 的 `ref` 属性直接解构会丢失响应式。

`ThreadHistory.vue` 中 `const { threads, ... } = useThreadsStore()` 直接解构了 store 的 `ref` 属性。在 Pinia 的 setup store 中，`store.threads` 返回的是**已解包的值**（非 ref 引用），解构后 `threads` 在组件 setupState 中变成了一个静态的空数组快照，不随后端数据更新而变化。

**修复内容**：

1. `ThreadHistory.vue`：使用 `storeToRefs()` 解构响应式状态（`threads`、`currentThreadId`、`loading`、`error`），方法直接从 store 实例解构
2. `AppSidebar.vue`：同样修复 `userId` 的解构
3. `ChatView.vue`：移除 `onMounted` 中的重复 `threads.load()` 调用（`App.vue` 已调用）
4. `ChatView.vue`：移除 `openThread` 中错误的 `threadId.startsWith('thread_')` 跳过逻辑（后端真实 ID 也是 `thread_` 开头）
5. `main.css`：`.thread-history` 增加 `flex: 1; overflow: hidden`，`.thread-groups` 增加 `flex: 1`，`.app-sidebar` 改为 `overflow: hidden`（避免整个侧边栏滚动，只让列表区域滚动）

### 问题 2 修复

已将 `rerank_model_name` 从 `gte-rerank` 更新为 `gte-rerank-v2`。

### 问题 3 修复

已修复 `_prune_evidence_to_allowed_sources` 的大小写不敏感匹配和 fallback 逻辑，以及 `_check_evidence_sufficiency` 的 `raw_count` 维度判断。
