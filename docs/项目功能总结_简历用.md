# DeepResearch 项目功能总结（简历素材 · 行业最佳实践口径）

> 本文档描述的是该系统**理论上采用行业最佳实践实现**的完整形态，供简历撰写与面试准备使用。
> 文末附「落地修复清单」：按此理论实现修复项目时需要补齐的工程项。

## 1. 项目一句话定位

**多智能体深度研报系统**：用户输入研究问题后，由 LangGraph 编排 8 类专业智能体协同完成「意图识别 → 需求澄清 → 研究计划 → 混合检索（Web + 本地知识库 RAG）→ 证据评审 → 分析 → 反思迭代 → 报告撰写」的完整研究闭环，全程 SSE 流式输出（心跳保活 + 断线重连 + 事件可重放），支持 3 处人机协同（HITL）中断、断点续研、时间旅行回滚与全链路引用溯源，并配套 Vue3 对话前端、知识库管理界面与基于事务性发件箱的异步文档向量化管道。

## 3. 核心功能模块详解（最佳实践实现）

### 3.1 多智能体研究工作流引擎（LangGraph）

- 基于 `StateGraph` 构建 10 节点有向图：`intent → (direct_answer | clarify → plan) → [web_search ∥ local_rag] → deep_dive → analyze → (reflect → 检索回环 | write) → END`

- 8 类专业角色智能体按职责分温度调优：意图路由 0.0 / 证据评审 0.2 / 规划与分析 0.3 / 检索与撰写 0.4，兼顾确定性与创造性

- 条件边实现动态路由：意图分流（简单问题走直答通道，避免多智能体开销）、`should_continue_research` 依据「是否仍有信息缺口 + 迭代上限」决定反思补搜还是收敛写报告

- 反思迭代闭环（Self-Reflection Loop）：analyze 产出 `needs_more_research` + `missing_gaps`，reflect 基于缺口生成定向补搜计划回流检索节点，`iteration` 计数 + 可配置 `max_iterations` 上限双保险防无限循环

- State 三组分类（会话 / 研究 / 进度）组合继承，证据、来源索引、审计标记等 17+ 字段挂 `operator.add` reducer，多通道并行写入时由 LangGraph 自动合并，节点无锁并发

- 意图识别采用「规则快速通道 + LLM 结构化精判」双层设计：规则命中即短路返回（零 token 成本），未命中再走 LLM 输出结构化意图标签

### 3.2 SSE 流式输出与事件协议

- 自定义 10 种事件类型的流式协议：`run.started / agent.status / message.start / message.delta / message.thinking / sources.found / interrupt.raised / run.completed / run.cancelled / run.error`

- 事件统一封装为 `EventEnvelope(type, ts, data)`，`EVENT_REGISTRY` 注册表 + Pydantic Schema 出口校验，非法事件无法流出服务端；协议文档（`docs/event-protocol.json`）由 schema 单一来源自动导出，前后端契约同源

- 后端纯 async generator + `graph.astream(stream_mode=["custom", "updates"])` 双通道消费：custom 通道承载节点内 StreamWriter 推送的 token / 进度 / 来源事件，updates 通道捕获节点级完成与 `__interrupt__` 中断

- 连接可靠性：每 15s 下发 SSE 注释帧（`: ping`）心跳保活，防中间代理空闲超时断连；客户端断开后凭 `thread_id` 调用 resume 接口，从最后 checkpoint 续流，事件幂等重放不丢不重

- 协议三不变式：流必以 completed/cancelled/error 之一终止；delta 顺序拼接即完整文本；前端忽略未知事件类型（前后向兼容）

### 3.3 HITL 人机协同（Human-in-the-Loop）

- 3 个中断点覆盖研究全流程关键决策：**需求澄清**（clarification）、**研究计划审批**（plan\_approval，approve / revise / reject，修改上限 3 次）、**报告评审**（report\_review，采纳 / 追加子问题再深入）

- 基于 LangGraph `interrupt()` 暂停图执行，中断现场（含全部研究状态）自动随 checkpoint 持久化；用户答复后经 `Command(resume=...)` 从中断点无损恢复

- 恢复载荷按中断类型做结构化校验（`ClarifyResumePayload / PlanApprovalResumePayload / ReportReviewResumePayload`），非法载荷 422 拒绝，杜绝状态机被畸形输入破坏

- 澄清环节由 LLM 驱动：模型自评需求置信度，置信度不足才主动生成带选项的澄清问题，最多 2 轮，回答充分性同样由 LLM 判定后进入规划

- 前端 interrupt store + 三张交互卡片（ClarifyCard / PlanApprovalCard / ReportReviewCard）条件渲染，页面刷新后通过 `GET /threads/{id}/interrupt` 重建中断现场

### 3.4 持久化、断点续研与时间旅行回滚

- PostgreSQL Checkpointer 为唯一事实源（`thread_id` 为持久化单元），每个超级步自动落盘；Redis 仅作热数据缓存层，构成三级降级链 `AsyncPostgresSaver → AsyncRedisSaver → InMemorySaver`

- 崩溃续研：`resume mode=continue` 以 `astream(None, config)` 从最后 checkpoint 无损续跑；服务重启时执行孤儿任务扫描（Redis 运行标记 + checkpoint 存活性判定），识别被重启打断的会话并标记，前端提示一键恢复

- 时间旅行回滚：`GET /threads/{id}/history` 暴露全部 checkpoint 历史快照，`POST /rollback`（`update_state` + `as_node`）回滚到任意历史状态并重载会话，研究过程可重放、可对照

- 独立 `chat_threads` 会话元数据表与会话消息解耦，支持列表、重命名、置顶、按时间分组、软删除（checkpoint 保留，可恢复）

### 3.5 分布式任务生命周期管理

- `TaskRegistry` 以 `thread_id → asyncio.Task` 注册表管理运行中任务：重复提交 409 拒绝、完成自动清理（done\_callback）、运行状态写 Redis 支撑多实例共享

- 取消即真正中断：`task.cancel()` 使 `CancelledError` 在 LLM await 点抛出，立即停止上游推理与 token 消耗；多实例部署下通过 Redis Pub/Sub 广播取消指令，任意 worker 上的任务一致性终止

- 前端乐观取消：调后端 cancel 后本地立即置 `cancelled` 状态，网络异常也不阻塞 UI；后端 `run.cancelled` 事件兜底对齐终态

### 3.6  混合检索 RAG 引擎

- **入库解析管道**：系统仅开放 MD、Word 两类文档解析能力，采用双层切分组合策略，先通过 `MarkdownHeaderTextSplitter` 依据标题层级完成语义粗切分，再依托 `RecursiveCharacterTextSplitter` 结合中文分隔符做递归精细化切分。文档清洗、内容提取与文本切分是 RAG 效果的核心基础，切分质量直接决定检索与问答精度，该配置可在保障系统运行性能的同时，最大化优化文本切片质量。

- **Parent-Child 大小块双层分块**：采用 small-to-big 分层切分机制，父块长度 2048、子块长度 512、切片重叠 64。通过子块生成向量 Embedding，保证语义聚焦、提升召回精准度；父块保留完整上下文信息，用于最终答案生成。检索命中精细子块后自动关联扩展对应父块内容，彻底解耦召回精度与上下文完整性两大核心痛点。
- **混合检索 + RRF 融合排序**：双路独立召回，一路通过 Milvus 稠密向量完成语义近似检索，`recall_k=20`，负责语义泛化匹配；另一路基于 PostgreSQL  关键词检索，同样 `recall_k=20`，针对专有名词、编码、型号等文本做字面精确匹配。两路召回结果在业务层执行 RRF（倒数排名融合）完成重排序，兼顾语义理解能力与关键词字面命中能力。
- **专用模型精排优化**：接入通义千问 `qwen3‑rerank` 专用重排模型，对 RRF 融合后的候选结果做精细化打分排序，最终截取 Top5 优质片段送入大模型生成回答。相比传统 LLM‑as‑reranker 方案，该模式兼具更低推理延迟与更优筛选效果。
- **智能查询改写**：通过大模型对用户原始提问进行语义增强，自动生成扩展、精简、反问句式三种检索变体，多维度覆盖检索视角，有效提升知识库内容召回覆盖率，解决提问表述偏差导致的漏召回问题。
- **可插拔多级联网搜索降级**：抽象统一 SearchProvider 搜索接口，搭建分层兜底机制，优先启用免费开源 ddgs 搜索，异常时自动降级切换至 Tavily、Bing 商用搜索 API，实现故障静默兜底，不阻塞主问答流程，兼顾系统稳定性与全网信息补充能力。

### 3.7 证据评审与引用溯源（反幻觉体系）

- 证据可靠性评分采用「域名信誉先验 + LLM 结构化评估」融合：本地知识库 / 官方政府 / 主流媒体 / 普通网页 / 无来源分档先验，LLM 结合内容质量与主题相关性给出结构化评分与理由

- `deep_dive` 节点产出证据池 + 三类审计标记（低置信 / 证据冲突 / 证据缺失），`analyze` 节点产出结论 `findings` 与 claim-source 映射（`claim_map`），每条论断可追溯到具体 source\_id

- `source_id` 全局编址体系（`WEB{iter}_{query}-{n}` / `LOC{iter}_{query}-{n}`），跨迭代、跨通道证据按多键（url+title / doc\_id+snippet）自动去重合并

- 幻觉引用四重防御：检索证据先登记 source\_id → 撰写仅允许引用合法集合 → 生成后正则校验并剔除非法引用角标 → 引用覆盖率统计（带角标论断占比）随报告输出暴露质量

- 参考资料区按正文实际引用顺序自动渲染，正文角标与文末来源一一对应

- 前端 citation 角标（`<sup data-source-id>`）支持点击定位来源，来源面板按 Web / 知识库双通道分组展示

### 3.8 长期记忆系统（langmem 双通道）

- langmem `create_memory_store_manager` + `AsyncPostgresStore` 向量存储（1024 维 text-embedding-v3，独立 schema 物理隔离），`namespace=(memories, {user_id})` 用户级隔离，支持多租户

- **双通道架构**（LangMem 官方推荐范式）：研究前**热路径检索**（top-5 相关记忆注入 plan 节点上下文）+ 任务完成后**后台异步提取**（`asyncio.create_task` 非阻塞，从对话中沉淀用户偏好与研究主题，异常只记日志零影响主流程）

- 长对话自动压缩：消息数超阈值时 LLM 生成滚动会话摘要 + 保留最近 N 条原文，上下文窗口恒定可控

- `GET /memories` 暴露记忆条目查询，记忆对用户可见、可审计

### 3.9 文档知识库异步管道（事务性发件箱）

- 上传主链路毫秒级返回：MinIO 对象存储（`{date}/{uuid}_{filename}`）→ 解析切块 → PostgreSQL 本地事务（documents + chunks + 本地消息表原子写入）

- **事务性发件箱（Transactional Outbox）保证最终一致**：业务数据与待发消息同一事务落库，MQ 投递失败消息保留在本地消息表，消费者启动期补偿扫描重投，杜绝「文档已存库但永远未被向量化」的不一致

- RabbitMQ 异步向量化：Topic Exchange + durable 队列 + 持久化消息 + 手动 ACK + prefetch=1；消费端以 content hash 幂等去重；失败进入\*\*死信队列（DLQ）\*\*并告警，重试超限不丢消息，支持人工重放

- 完整状态机：chunk 级 `pending → indexed / failed` 状态回写 PG，单文档失败可重试（重置状态 + 重建 Outbox 消息 + 立即投递）

- 优雅降级：MQ 不可用自动切同步向量化模式；向量库不可用仅存 MinIO + PG 并显式返回 failed，不丢原始文件

- 前端全流程可视化：拖拽上传 + XHR 字节级进度 + 解析/向量化阶段化状态 + 3s 轮询聚合进度 + 全库统计卡片

### 3.10 对话前端（Vue3）

- **手写 SSE 消费器**：fetch POST + ReadableStream + TextDecoder，`\n\n` 切帧 + 半帧 buffer 拼接处理跨 chunk 断包；单帧 JSON 解析失败跳过不中断整条流；AbortError 识别为用户主动取消；断线指数退避自动重连

- **事件驱动单向数据流**：`useEventStream` 统一 dispatch 10 种事件到 4 个 Pinia store（chat / interrupt / threads / documents），run 与 resume 复用同一消费链路，无重复逻辑

- **流式渲染**：token 逐字追加、深度思考过程可折叠展示（reasoning 流式透传 + 渐隐预览）、markdown-it + highlight.js + KaTeX 公式渲染、代码块一键复制、自动滚动

- 会话管理：历史按置顶/今天/昨天/近 7 天智能分组、checkpoint 回滚菜单、报告导出 Markdown / PDF（headless Chromium 渲染，保留排版与公式）

- 知识库管理页：文档表格（向量状态徽章 empty/processing/indexed/partial/failed）、批量删除二次确认、防抖搜索、失败重试

- XSS 防御：markdown-it 关闭原始 HTML 注入（`html: false`）+ 外链 rel 安全属性，检索回传内容不可注入脚本

### 4.1 完整版（适合项目经历重点段落）

**DeepResearch — 多智能体深度研报系统**（个人全栈项目）
技术栈：LangGraph / FastAPI / Vue3 / Pinia / PostgreSQL / Milvus / Redis / RabbitMQ / MinIO / Docker

- 基于 LangGraph StateGraph 设计 10 节点、8 角色智能体（意图路由/规划/Web 侦察/本地检索/证据评审/分析/反思/撰写）的研究工作流，条件路由 + 反思迭代循环实现「检索 → 分析 → 发现缺口 → 定向补搜」的自我纠错闭环，迭代计数与上限双保险防失控

- 设计 10 种事件类型的 SSE 流式协议（Pydantic Schema 出口校验 + 事件注册表），async generator + graph.astream 双通道实现 token 级流式输出；注释帧心跳保活防代理断连，断线后从 checkpoint 续流、事件幂等重放；前端基于 fetch + ReadableStream 手写 SSE 消费器（半帧缓冲、坏帧跳过、指数退避重连）

- 实现 3 处 HITL 人机协同中断（需求澄清/计划审批/报告评审），interrupt + Command 机制使中断现场随 checkpoint 持久化、结构化 payload 校验后无损恢复；页面刷新后从中断接口重建交互现场

- 基于 PostgreSQL Checkpointer 实现断点续研与时间旅行回滚：崩溃后从最后存档续跑，支持回滚到任意历史快照重放研究；分布式任务注册表管理全生命周期——asyncio 级真正取消（中断上游推理）、并发去重 409、Redis Pub/Sub 广播取消保证多实例一致性终止

- 构建混合检索 RAG 引擎：查询改写 → Milvus 稠密 + PostgreSQL 关键词双路召回 → RRF 融合 → qwen3-rerank 专用模型精排 → Parent-Child 上下文扩展（父 2048/子 512/重叠 64）；Web 搜索可插拔多级降级（ddgs→ 搜索 API）+ 退避重试 + Redis 缓存抗限流

- 设计反幻觉引用溯源体系：source\_id 全局编址、域名信誉先验 + LLM 结构化评估融合打分、claim-source 映射、生成后非法引用自动剔除、引用覆盖率统计，正文角标点击可溯源至原始出处

- 基于 langmem + PostgresStore（1024 维向量）实现长期记忆双通道：研究前热路径检索注入上下文、完成后后台异步提取用户偏好（用户级 namespace 隔离、不阻塞主流程），长对话自动摘要压缩控上下文窗口

- 设计文档向量化异步管道：MinIO 存储 + PostgreSQL 本地事务 + 事务性发件箱（Outbox）最终一致 + RabbitMQ 异步消费（手动 ACK、消费幂等、死信队列 + 补偿重放、MQ 不可用自动降级同步模式），上传毫秒级返回

- 工程化：按 thread\_id 的研究过程 JSON 日志 + 轮转日志 + TRACE 通道、双层配置热更新

## 6. 面试高频追问与回答要点

| 简历亮点         | 高频追问                        | 回答要点                                                                                                                                                |
| ------------ | --------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| SSE 协议       | 为什么用 SSE 不用 WebSocket？      | 单向推送场景；SSE 基于 HTTP 免升级、天然过代理；POST 请求体需用 fetch 流式读取而非 EventSource；心跳保活防代理空闲超时；断线不自动盲连，凭 checkpoint 通过 resume 接口续流，事件幂等重放不丢不重                         |
| 事件协议         | 如何保证前后端事件契约一致？              | Pydantic 定义 + EVENT\_REGISTRY + 单一 event() 工厂出口校验；协议文档由 schema 自动导出，单一事实源；三条不变式（流必终止、delta 可拼接、未知类型忽略）保证前向兼容                                        |
| HITL         | interrupt 之后图是怎么停下来的？       | interrupt() 抛出特殊异常被 LangGraph 拦截，当前全部状态写入 checkpoint 后线程终止；恢复时以 Command(resume=value) 重入，节点内拿到用户答复继续执行；中断不是错误，是状态机的一等公民                             |
| 断点续研         | 崩溃后如何知道从哪继续？                | 每个超级步自动 checkpoint 到 PG（thread\_id 为 key）；resume 用 astream(None, config) 从最后存档续跑；启动期孤儿扫描（Redis 运行标记 + checkpoint 存活性）识别被重启打断的会话                     |
| 取消           | 取消是怎么真正停掉 LLM 调用的？          | 不只断开 SSE；asyncio.Task.cancel() 在 await 点抛 CancelledError 中断上游推理请求；多实例下 Redis Pub/Sub 广播取消，任意 worker 上的任务一致性终止；状态机发 run.cancelled 收尾，前端乐观更新 + 事件兜底对齐 |
| 混合检索         | 为什么要稠密 + 关键词两路？怎么融合？         | 稠密抓语义近似（换说法也能召回），PG 关键词抓精确字面匹配（型号/专名/代码）；RRF 融合只依赖排名不依赖分数分布，对异构打分鲁棒，无需调权                                                                              |
| 重排           | 为什么用 qwen3-rerank 而不是让 LLM 排？ | 专用重排模型单次推理完成 pair 评分，延迟与成本远低于 LLM 逐条判断；重排是判别式任务，生成式模型属于能力错配                                                                                           |
| Parent-Child | 为什么分父块子块两套索引？               | 小块 embedding 语义集中、召回准；大块上下文完整、供 LLM 引用；检索用子块、生成用父块（small-to-big），解耦「召回精度」与「上下文完整性」                                                                  |
| Outbox       | 为什么需要事务性发件箱？                | 「PG 写入成功 + MQ 发送失败」会造成文档永远不被向量化；把业务数据与消息放进同一本地事务，后台补偿扫描保证至少一次投递，消费端 content hash 幂等去重，端到端最终一致                                                       |
| 死信队列         | 消费失败怎么办？                    | 手动 ACK 前处理；失败重试有上限，超限进 DLQ 并告警，不无限 requeue 造成消费风暴；DLQ 支持人工修复后重放，配合启动期补偿扫描双保险                                                                        |
| 记忆           | 为什么后台提取而不是同步？               | 记忆提取是一次额外 LLM 调用，同步会拖慢首 token；asyncio.create\_task 放后台，异常只记日志，主流程零感知；这是 langmem 官方推荐的热路径 + 后台双通道范式                                                  |
| 引用防幻觉        | 怎么防止模型编造引用？                 | 只允许引用检索阶段登记过 source\_id 的证据（生成约束）；生成后正则提取全部角标与合法集合比对，非法引用直接剔除；统计引用覆盖率随报告输出；正文角标与文末参考资料按出现顺序一一对应                                                     |
| 反思循环         | 怎么防止无限补搜？                   | iteration 计数 + max\_iterations 上限双保险；needs\_more\_research 为 false 或超限即收敛到 write 节点；预算（轮数/来源数/token/时长）在计划阶段即声明                                     |
