# DeepResearch 需求与架构方案 v2（行业最佳实践版）

> **定位**：新目录重开发的目标方案。以 v1（现状提炼）为功能底稿，按 2024–2026 行业成熟实现全面优化，**不受现有代码与技术选型约束**。
> **依据**：三路联网调研（来源 URL 见文末附录）——深度研究系统架构（open_deep_research / GPT Researcher / OpenAI / Gemini / STORM / Anthropic / Tongyi）、RAG 检索引用最佳实践、LLM 应用生产工程。
> **变更总原则**：固定流水线保可预测性，运行时决策暴露为工具；并行只用于检索，写作一次完成；上下文工程优先于提示工程。

## 1. 产品定位

多智能体深度研报系统：用户提出研究问题，系统经澄清与计划确认后，由 supervisor 动态编排多个并行研究子 agent 完成多源检索与证据核验，一次性产出**句级引用、事实支持率经过校验**的结构化研究报告。全程流式可观察、可中断、可转向、可恢复。

**用户角色**：普通用户（研究/知识库/会话管理）、管理员（配置与观测）。

## 2. 目标架构：三阶段混合编排

```
┌─ Scope ─────────────┐ ┌─ Research（动态委派）──────────────────┐ ┌─ Write ─────────────┐
│ clarify（澄清对话）   │ │ supervisor                            │ │ writer 一次性成文     │
│   ↓ 压缩             │ │   ├─ 拆子主题 → 并行派 N 个 researcher │ │   ↓                  │
│ research brief       │ │   │   子 agent（独立上下文，ReAct+工具）│ │ CitationAgent        │
│   ↓ HITL 计划批准    │ │   │   工具：web_search / kb_search /   │ │   句级事实支持率校验   │
└──────────────────────┘ │   │   fetch_url / 子主题清洗压缩回传   │ │   ↓                  │
                          │   └─ supervisor 判缺口 → 再派或收口   │ │ 质量门禁 → 导出       │
                          └──────────────────────────────────────┘ └──────────────────────┘
```

**架构规则**：

1. **阶段边界静态，研究内部动态**：Scope/Research/Write 三段是静态骨架；Research 内部由 supervisor 运行时决定并行度与轮次，无固定循环边。
2. **子 agent 独立上下文窗口**：每个 researcher 在自己的上下文内做 tool-calling ReAct 循环（检索、读原文、整理），结束前做一次「清洗压缩」调用，只回传结论与结构化 sources——token 重的工具反馈不污染 supervisor 上下文。
3. **并行只用于检索与阅读，写作不并行**。
4. **委派简报四要素**：supervisor 派生子 agent 必须给明确目标、边界、输出格式、来源指引（Anthropic 生产经验）。
5. **预算与上限**：总研究轮次、并行子 agent 数（建议默认 3–5）、单 agent 工具调用次数均设上限——成本控制之外，PwC 实测工具调用越多事实准确率越差，上限同时是质量约束。
6. **上下文工程**：对话压缩为 research brief 作全程「北极星」；超大产出落对象存储/文件，上下文内只传引用指针。
7. **checkpointer 保留**：阶段边界与 supervisor 决策点落检查点，支撑中断恢复与 HITL 挂起。

**与 v1 的映射**：clarify→保留；plan→并入 brief+计划批准；web_search/local_rag 节点→researcher 子 agent 的工具；retrieve_grader/deep_dive→子 agent 内部行为与工具；analyze→supervisor；write→保留+CitationAgent。

## 3. 功能需求

### F1 Scope 阶段：澄清与研究纲要

- 澄清对话（上限 2 轮），信息足够后压缩为 **research brief**（研究目标、范围、关键子问题、排除项），作为全程北极星。
- 简单问答仍走 direct answer 快路径（秒级响应）。
- **计划批准 HITL**：brief + 拟定研究计划交用户确认/修改后进入研究阶段（Gemini 模式）。

### F2 Research 阶段：supervisor 动态委派

- supervisor 按 brief 拆分子主题，动态派发并行 researcher 子 agent（默认 3–5，可配上限）。
- researcher 子 agent 工具集：`web_search`（多 provider 链式降级）、`kb_search`（本地混合检索）、`fetch_url`（原文深读）、`search_kb` 之外可扩展 MCP 工具。
- researcher 内部行为（不再是图节点）：检索 → CRAG 式质量自判 → 不足则换查询词补检（子 agent 内小循环）→ 可疑证据 fetch_url 读原文 → 清洗压缩回传「结论 + 证据 + sources 清单」。
- supervisor 汇总各子 agent 回传，判断知识缺口：有缺口且预算未耗尽 → 再派补充子 agent；否则收口进入 Write。
- **研究中干预**：用户可随时中断，或追加提示改变研究方向（OpenAI 模式）。

### F3 检索需求（工具实现层）

- **Web 检索**：多 provider 链式降级（顺序可配）、单查询超时、限流与结果缓存；全链失败降级空结果+告警。
- **本地混合检索**：向量 + 全文双路召回 → **RRF(k=60)** 融合（业界默认，保持）→ cross-encoder 重排（Qwen3-Reranker 或 Cohere）→ Parent-Child 上下文扩展；可选叠加 Contextual Retrieval（Anthropic 实测检索失败率再降 49–67%）。
- **查询多变体/分解**：保留（深研刚需）。
- 检索结果统一携带稳定 source_id（生成期编址规则保证跨轮次唯一）与来源元数据（域名、发布时间、来源类型）。

### F4 证据与引用（反幻觉体系升级）

- **证据可信度分层**：官方原文/一手数据 > 权威机构报告 > 权威媒体 > 普通转载 > 来源不明（排除）；评分 = 来源先验 + LLM 内容判断融合。
- **引用三段式**：
  1. 索引期：所有证据携带稳定 source_id；
  2. 生成期：writer 产出句级内联引用标记；
  3. 事后校验：**CitationAgent 逐条校验事实支持率**（NLI/AlignScore 或校准过的 LLM-judge），输出 supported / partially_supported / unsupported 三档；unsupported 的句子必须改写、补证或删除。
- 报告引用区与正文角标同源生成，悬挂引用自动剔除。

### F5 Write 阶段与导出

- 单一 writer 一次性成文（输入：brief + 全部子 agent findings），保证叙述连贯。
- 导出 MD（不阻断，逃生通道）与 PDF（先过质量门禁）。
- **质量门禁**（自动，替代原报告评审 HITL）：空报告/引用段缺失/正文长度/单源引用占比/引用事实支持率低于阈值 → error 阻断或 warning 放行；PDF 渲染后回读校验。

### F6 长期记忆

- LangMem（LangGraph 原生）：热路径只读（按用户注入相关记忆到 brief），**写入全部走后台**（研究完成后异步提取）。
- 记忆按用户 namespace 隔离；提供查看入口。

### F7 会话持久化、中断与恢复

- LangGraph checkpointer（PostgreSQL）落阶段边界与决策点。
- **长任务执行层评估 Temporal**：崩溃自动恢复、重试策略、HITL 长时间挂起、跨实例取消由 durable execution 承接；若不引入 Temporal，则自研层必须等价覆盖：同 thread 并发互斥（409）、幂等取消、重启孤儿任务扫描标记、运行看门狗。
- 历史快照回溯（时间旅行）保留。
- 会话摘要压缩：消息超阈值时 LLM 压缩，保留最近若干条原文。

### F8 SSE 流式与断线续流（升级为事件日志架构）

- **事件模型对齐 AG-UI 语义**：RUN_STARTED / RUN_FINISHED / RUN_ERROR、TEXT_MESSAGE_START/CONTENT/END、TOOL_CALL_START/ARGS/END、STATE_SNAPSHOT/STATE_DELTA、STEP_STARTED/FINISHED、自定义 HITL interrupt 事件。内部事件可保留，对外暴露建立 AG-UI 映射。
- **生成与投递解耦**：所有事件带单调递增序号写入持久事件日志（PG 表或 Redis Stream，按 run_id 分区，设保留期）；SSE 连接只是事件日志的可丢弃视图。
- **断线续流**：客户端记录最后收到的事件序号（或 Last-Event-ID），重连时 `?after=<seq>` 先重放缺口再继续跟随实时流；重放期间 run 仍在后台执行（任务与连接解耦）。
- 心跳保活（默认 15s 注释帧）保留；协议不变式保留：流必以终态事件结束，未知事件类型前端静默忽略。

### F9 知识库文档管道

- 上传校验（大小/数量/扩展名白名单+魔数）、原始文件对象存储。
- **事务性发件箱不变**：文档+切片+outbox 消息单事务；消费幂等；启动补偿扫描。
- **broker 评估 pgmq 替代 RabbitMQ**：摄入属中吞吐场景，PG 队列天然与发件箱同事务、减少一套中间件运维；若保留 RabbitMQ 则 DLQ + 重试上限语义不变。
- 文档管理：列表/统计/状态/重试/单删/批删（PG+对象存储+向量三处一致清理）。

### F10 HITL（收敛为两点 + 一自动）

1. **研究前**：澄清对话、计划批准。
2. **研究中**：中断、追加提示转向。
3. **研究后**：导出质量门禁（自动化，不阻塞成文）。

中断状态可重建（断线恢复）；resume 语义：continue（继续）/ answer（应答中断）/ steer（带新指令转向）。

### F11 认证与管理

- JWT 认证；身份只从令牌派生；资源归属守卫（非本人 404）；鉴权失败防账号枚举。
- 管理员配置热更，区分热生效/需重启字段；健康检查端点。

### F12 前端

- Vue3 + Pinia + Naive UI（或同级栈）；消费 AG-UI 语义事件的统一 reducer。
- 研究过程展示：计划审批卡片、子 agent 实时步骤与来源流（侧边栏式）、正文流式渲染（markdown/公式/代码）、句级引用角标。
- 研究中干预入口：停止、追加提示转向。
- 断线自动重连 + 事件重放补齐缺口。
- 知识库管理页、会话历史页（搜索/重命名/置顶/删除/回滚）。

## 5. 非功能需求

- **超时矩阵**：LLM 单次（可配，默认 60s/重试 2）、单查询检索 15s、单轮研究看门狗（默认 900s）、PDF 渲染 30s；run 与 resume 路径同防护。
- **预算上限**：总研究轮次、并行子 agent 数、单 agent 工具调用次数、证据条数与字符预算——成本与质量双重约束。
- **降级规则**：检索全链失败降级空结果+告警；rerank 失败降级；MQ 失败降级同步向量化；结构化输出失败节点级降级并留痕；**一切降级必须记日志，禁止静默**。
- **幂等**：取消、消息消费、事件重放（序号去重）、来源去重。
- **可观测性（新增）**：OTel GenAI 语义约定——每 run 一个 root span，LLM/检索/工具/重试 child span，记录 token 用量、TTFT、成本；traceparent 跨 MQ 传播；trace 脱敏。后端 Langfuse 自托管。
- **评测门禁（新增）**：
  - 离线：golden set 50–200 真实 case 进 CI；指标含检索 recall@k / nDCG@10、RAGAS faithfulness / context precision、**引用事实支持率**；改 prompt/模型/检索管线必跑阈值断言。
  - 线上：1–5% 流量 LLM-as-judge 抽样，judge 先与人工标注校准；失败 case 回流 golden set。
  - 确定性检查（schema 合法、PII、成本/延迟预算）每次输出都跑。
  - 对标参照（不作门禁）：DeepResearch Bench、BrowseComp、DeepSearchQA。
- **性能**：直接回答秒级；研究阶段子主题并行；SSE 首事件即时。

## 6. 安全需求（OWASP LLM Top 10 2025 落项）

| 条目 | 需求 |
| --- | --- |
| LLM01 间接注入 | 检索语料与 fetch_url 读回内容视为不可信输入：指令/数据分离、内容包装隔离；高风险动作走 HITL |
| LLM02 敏感信息外泄 | 系统提示词不放密钥；trace 与记忆落库前脱敏 |
| LLM05 输出不当处理 | MD/PDF 导出前消毒，防 XSS/下游注入 |
| LLM06 过度代理 | 工具最小权限；fetch_url 出站白名单、禁内网网段、响应大小/类型上限（SSRF） |
| LLM10 无界消耗 | 超时矩阵 + 预算上限（§5） |

凭据一律环境变量注入；缺失凭据 fail-closed 或显式降级记日志。

## 7. 技术选型建议（新目录自由选型）

| 层 | 推荐 | 备选/说明 |

| Embedding | Qwen3-Embedding / text-embedding-v3 | — |
| 消息队列 | 评估 **pgmq**（PG 队列） | 保留 RabbitMQ 亦可，发件箱模式不变 |

| 可观测 | Langfuse（自托管）+ OTel GenAI | LangSmith 备选 |
| 评测 | RAGAS + 自建 golden set | — |
| 前端 | Vue3 + Pinia + Naive UI + Vite + vitest | 栈不变 |

## 8. 验收基线

- 功能验收：澄清→计划批准→并行研究→中断/转向→恢复→导出 全链路用户路径逐条可验。
- 质量验收：golden set 阈值（recall@k、faithfulness、引用事实支持率）CI 达标；端到端报告人工抽检。
- 工程验收：断线重放零事件丢失；重启孤儿任务可标记可恢复；取消幂等；trace 全链路可查。

## 9. 范围外

- 端到端 RL 训练自研模型（OpenAI 路线，不可工程复现）。
- GraphRAG 全语料图谱索引（ROI 不足）。
- 多租户计费、开放 API 平台化。

## 10. 技术迁移说明（v1 → v2，面试口径）

> 本章用于解释「为什么重构」，可独立作为面试陈述材料。核心叙事：**v1 的静态图是功能验证期的正确选择，但它把决策冻结在拓扑里；当行业在 2025 年收敛出经过生产验证的目标形态后，架构级问题只能用架构级方案解决**。

### 10.1 迁移背景：v1 是什么、为什么会那样设计

v1 采用 LangGraph 静态有向图：10 个节点固定拓扑 + 两级循环（内层检索重检 ≤2 轮、外层反思续研 ≤3 轮），配合 PostgreSQL checkpointer、双路混合检索（向量+全文→RRF→重排）、事务性发件箱知识库管道、自研 10 事件 SSE 协议。

这个设计在项目初期是合理的：路由规则显式、每步可测、行为可预测、测试基线全绿（后端 780+/前端 70+ 用例）。它完整验证了「深度研究」这个产品命题。

### 10.2 迁移必要性：四类架构级问题

**问题一：决策被冻结在图拓扑里，无法按查询复杂度自适应。**
静态图意味着所有查询走同一条管线：简单问题被迫走完深读+反思全程（浪费延迟与 token），复杂问题被固定轮次上限卡死。检索充分性判断、原文深读、反思补检这些**本应根据中间结果动态决策**的环节，被硬编码为固定节点和固定循环边。2025 年 LangChain 官方复盘（bitter lesson）确认了这一点：open_deep_research 从静态 workflow 重写为 supervisor 动态委派，静态 plan-and-execute 实现被降格为参考实现。

**问题二：上下文膨胀，证据在同一 State 里无界累积。**
v1 所有检索证据累积进单一图 State，token 量大的网页原文、检索快照反复进入后续每个节点的上下文。行业共识（Anthropic 多智能体生产经验、Tongyi IterResearch）是：token 投入是研究质量的主变量，**上下文工程是第一性问题**——子 agent 独立上下文、回传前清洗压缩、大产出落存储只传引用。

**问题三：并行度被拓扑锁死。**
v1 的并行只有 web/local 两路固定扇出。Anthropic 实测子主题级并行使研究提速约 10 倍——而静态图无法在运行时按子问题数量动态扩展并行度。

**问题四：工程子系统自研负担超出项目规模。**
自研任务注册表 + Redis 取消广播 + 前端重连对齐的断线续流方案，语义存在盲区（resume 路径缺看门狗、无事件重放能力——连接即流，断线即丢失期间事件）。Grid Dynamics 在同场景（LangGraph+Redis 深度研究）最终因重试/状态/HITL 的维护成本迁移到 Temporal。

**同时期的外部证据**：PwC 2026 年实测主流深研 agent 的引用链接有效率 >94%，但事实支持率仅 39–77%，且工具调用越多事实准确率越差（调用 2→150 次时降 42%）——说明「引用格式正确」不等于「内容被证据支持」，引用校验必须升级到事实支持率层面，检索轮次上限同时是质量约束而不只是成本控制。

### 10.3 逐项迁移理由（旧设计 → 问题 → 新设计 → 收益）

| 迁移项 | v1 设计 | 暴露的问题 | v2 设计 | 收益 |
| --- | --- | --- | --- | --- |
| 编排架构 | 10 节点静态图 + 两级固定循环 | 策略僵硬、并行锁死、上下文膨胀 | Scope→Research→Write 静态骨架 + supervisor 动态委派 3–5 个并行 researcher 子 agent | 按查询复杂度自适应；子主题并行提速；子 agent 独立上下文隔绝 token 噪音；open_deep_research / Anthropic / Gemini 三方生产验证 |
| 检索判定 | retrieve_grader 图节点 | 每次判定一次结构化 LLM 调用，粒度太细 | CRAG 式质量自判收进 researcher 子 agent 内部行为 | 节点粒度符合「一节点=一项完整职责」；判定与检索在同一上下文内零成本联动 |
| 证据深读 | deep_dive 图节点 | 是否读原文是运行时才知道的决策，不该是固定流水线步骤 | fetch_url 降级为子 agent 工具，agent 自主决定 | 决策点移到信息最充分的位置 |
| 引用校验 | 链接有效性 + 格式校验 | 链接有效 ≠ 内容支持（事实支持率仅 39–77%） | 三段式：稳定 source_id → 句级内联标记 → CitationAgent 事后事实支持率校验（三档），unsupported 必须改写/补证/删除 | 引用从「形式正确」升级为「实质可归因」，这是深研系统质量的分水岭 |
| 写作 | 单一 writer（此项 v1 正确） | — | 保持一次性成文，明确禁止并行写作 | LangChain 复盘证实并行写作导致报告割裂 |
| 流式协议 | 自研 10 事件 SSE | 私有协议无生态；连接即流，断线丢失期间事件 | SSE 传输保留，事件语义对齐 AG-UI 标准；事件带单调序号落持久日志，`?after=<seq>` 重放续尾 | AG-UI 已被 Google ADK/Bedrock AgentCore 原生支持；生成与投递解耦后断线零事件丢失，前端逻辑大幅简化 |
| 任务执行 | 自研注册表 + Redis 取消广播 | 崩溃恢复/HITL 挂起/跨实例取消的语义自己维护，存在盲区 | 评估 Temporal（官方 LangGraph 插件）承接 durable execution | 重试、恢复、挂起由成熟编排层保证；同场景已有迁移先例 |
| 长期记忆 | langmem 双通道 | 热路径写入加延迟且迫使 agent 多任务 | LangMem 保留，写入全部走后台 | LangChain 官方明确取舍；零基建变更的成本获得延迟改善 |
| 重排模型 | gte-rerank-v2 | 已被同门 Qwen3-Reranker 全面超越（MTEB-R 69.8 vs 59.5） | Qwen3-Reranker-4B（自托管）/ Cohere（托管） | 纯收益升级，接口不变 |
| 评测 | 单元/契约测试 | 只测「没坏」，不测「好不好」 | 双层门禁：CI golden set（recall@k、faithfulness、引用事实支持率阈值断言）+ 线上 1–5% LLM-as-judge 抽样回流 | prompt/模型/检索变更有了质量回归防线；失败 case 自动回流形成数据飞轮 |
| 可观测 | 业务日志 | LLM 调用成本/延迟/链路不可见 | OTel GenAI 语义约定 + Langfuse 自托管 | token 成本可归因、慢调用可定位、跨 MQ 链路可追 |
| 消息队列 | RabbitMQ + DLQ | 中吞吐摄入场景维护一整个 broker | 评估 pgmq（PG 队列），发件箱模式不变 | 砍掉一套中间件运维面；发件箱与消费天然同库事务 |
| HITL | 4 个介入点 | 报告评审阻塞成文流程，打断心流 | 收敛为研究前（澄清+计划批准）+ 研究中（中断/转向）；报告质量改自动门禁 | 与 Gemini/OpenAI 产品形态收敛；门禁自动化不损失质量 |

### 10.4 为什么不是全盘推翻

调研证实 v1 的一批设计与 2026 年业界主流高度吻合，**原样保留**：双路混合检索 + RRF(k=60) 融合、Parent-Child 上下文扩展、事务性发件箱、PostgreSQL checkpointer、结构化输出策略（ProviderStrategy/ToolStrategy 分工）、HITL 本身。重构的范围精确限定在「被行业证据证伪的部分」，这是基于证据的取舍而非推倒重来。

### 10.5 面试陈述要点（30 秒版）

> 初版用 LangGraph 静态图把 10 个节点和两级循环固定下来，快速验证了产品命题，测试全绿。但实践中发现静态拓扑把检索、深读、反思的决策冻结了——简单查询被迫走全程，复杂查询被轮次卡死，且无法按子主题并行。2025 年 LangChain 官方、Anthropic、Gemini 相继公开了各自从静态流水线转向「阶段骨架 + supervisor 动态委派」的实践与复盘，我按这个收敛方向重构：研究阶段改为 supervisor 派发并行 researcher 子 agent（独立上下文、工具化检索、清洗回传），写作保持单次成文；同时根据 PwC 的实测研究把引用校验从链接有效性升级到句级事实支持率校验。检索链路经调研与业界主流一致，予以保留——重构范围是证据驱动的，不是推翻重来。

### 10.6 风险与控制

- **行为回归风险**：以 v1 测试基线（契约测试、State 语义、溯源断链回归）为重构防护网，逐模块迁移。
- **动态委派的不确定性**：预算与轮次硬上限兜底；supervisor 决策全部落 checkpoint 可回溯。
- **新基建引入风险**（Temporal/pgmq）：均标注为「评估」，各带保留现状的降级路径，不与主架构强绑定。
