## 2. 背景：为什么会纠结"两套向量库"

Phase 5 引入 langmem 长期记忆后，项目同时存在两个"能存向量的东西"：Milvus 和 PostgreSQL(pgvector)。
直觉反应是"重复建设、应该合并"——但这个直觉是错的，二者解决的是**不同形状的问题**。

---

## 3. 核心判断：Milvus 与 pgvector 不是重复建设

### 3.1 职责对比

| 维度 | Milvus（知识库） | pgvector（langmem 记忆） |
|------|------------------|--------------------------|
| 数据形态 | 文档 chunk 向量（海量、万~百万级） | 结构化记忆条目（每用户几十~几百条） |
| 写入模式 | 批量灌入、低频更新 | 高频小批量写入（每轮对话数次） |
| 读取模式 | 纯 ANNS 相似度检索 | 精确 KV 读写 + 语义检索 + 关键词检索 |
| 更新语义 | 重建/覆盖为主 | 条目级增删改（记忆会被 LLM 修正、合并、删除） |
| 一致性要求 | 最终一致即可 | 需要事务保障 |

### 3.2 为什么不能让 Milvus 兼任 langmem 的 Store

langmem 真正依赖的不是"向量数据库"，而是 LangGraph 的 **`BaseStore` 接口**。它需要一组**结构化 store 能力**：

| langmem Store 需要的能力 | Milvus 是否具备 | 说明 |
|---|---|---|
| 精确 KV 读写（`get/put/delete`，按 namespace 定位） | ❌ | Milvus 是 ANNS 检索库，不是 KV store |
| 语义检索（`asearch` 返回带 score 的条目） | ✅ | 唯一的交集 |
| 关键词/全文检索（依赖 `pg_trgm`） | ❌ | Milvus 无全文索引 |
| 条目级增删改 + 事务 | ❌ | Milvus 面向批量向量，不擅长频繁小写 |

> **补充**：知识库 embedding 与"记忆" embedding 是两个语义空间（前者文档 chunk，后者用户偏好/事实），
> 混存进同一 collection 反而会互相污染检索质量。即便强行合并，也应分 collection——那就已经是"两套"了。

## 4. 已确认的阻塞点：原 `postgres:16-alpine` 跑不通 P5-1

P5-1 的代码已经写好（`app/backend/infra/store_client.py`），但它原先连的库撑不住。**证据链**：

1. `store_client.py:56` 配置 `dims=1024`（DashScope `text-embedding-v3`），走 `AsyncPostgresStore`。
2. `app_main.py:205-206` 调用 `init_store(postgres_dsn=config.postgres_dsn)`
   → **与 checkpointer（`:137`）、业务表（`ensure_tables`，`:114`）共用同一个 DSN**。
3. `settings.py:29` 该 DSN 默认指向 `postgresql://root:postgres123@localhost:5432/mydb`
   → 原 `postgres` 服务镜像 `postgres:16-alpine`。
4. `store_client.py:72` 调用 `await store.setup()`，而 langgraph 的向量迁移首条语句就是建扩展：
   ```sql
   -- langgraph-1.0.3, langgraph/store/postgres/base.py:91-101 (VECTOR_MIGRATIONS[0])
   DO $$
   BEGIN
       IF NOT EXISTS (SELECT 1 FROM pg_extension WHERE extname = 'vector') THEN
           CREATE EXTENSION vector;
       END IF;
   END $$;
   ```
5. **官方 `postgres` 镜像不含 pgvector 扩展文件**，`CREATE EXTENSION vector` 会报
   `extension "vector" is not available` → `setup()` 失败 → P5-1 起不来。

**实测旁证**（本次调研）：

| 检查项 | 结果 |
|--------|------|
| `pgvector/pgvector:pg16` 冒烟验证 | ✅ PG **16.15**(Debian)，`vector **0.8.6**`（含 ivfflat/hnsw）+ `pg_trgm **1.6**`，`init_pgvector.sql` 由 entrypoint 自动执行成功 |
| `ankane/pgvector:latest` 扩展可用性（对照） | ✅ `vector 0.5.1` + `pg_trgm 1.6` 可建（PG 15.4），版本偏低且主版本不符，未采用 |
| langgraph 版本 | `1.0.3`（conda 环境 `llmdev`） |
| 原 middleware 容器运行状态 | 全部未运行（`docker ps` 为空） |
| 原 postgres 数据目录 | 69 MB（initdb 初始规模），已备份为 `postgres.bak-20260903` |

> 冒烟方式：以与 compose 完全相同的环境变量（`root` / `postgres123` / `mydb`）挂载
> `scripts/init_pgvector.sql` 启动临时容器，日志确认脚本已执行，`\dx` 列出 `vector` 与 `pg_trgm`。

## 5. 选型：为什么是 B（合并共库）

| # | 方案 | 代码改动 | 数据风险 | 结论 |
|---|------|----------|----------|------|
| **B** | **合并共库**：`postgres` 镜像换 `pgvector/pgvector:pg16` | **零改动**（DSN 不变） | 需清空旧 PGDATA | ✅ **已选定并落地** |
| A | 独立容器：新增 `pgvector` 服务（5433） | 需新增 `store_dsn` 并改 `app_main.py:205-206` | 零风险 | 已作备选，compose 中注释保留 |
| C | 让 Milvus 兼任 Store | 自研 `BaseStore` 适配层 | — | ❌ 不推荐（见 3.2） |

**选 B 的理由**：
- **代码零改动**：记忆、checkpointer、业务表共库分 schema——这正是 `Phase5_记忆重写.md` P5-1 步骤 2 的原始设计（"与现有 PG 共库，独立 schema"）。
- 只需维护一个 PG 实例，连接串只有一个。
- 主版本一致：`postgres:16-alpine` → `pgvector/pgvector:pg16`，都是 PG 16。

**B 的代价（已处理）**：alpine(musl) 与 debian 镜像的 PGDATA 不兼容，旧目录已**备份**为
`D:\docker\data\llmdev\postgres.bak-20260903`（重命名，非删除，确认无误后可自行清理）。

## 7. RabbitMQ 的定位：文档 chunk 异步向量化

**不是**记忆链路，用途是文档异步向量化：

```
document_service 上传切片
   └─> MQProducer (backend/infra/mq_client.py)
         └─> Topic exchange "chunk-sync"
               └─> queue "chunk-sync.queue"
                     └─> ChunkSyncConsumer (backend/infra/chunk_consumer.py:204)
                           └─> embedding ─> 写入 Milvus
```

**账号与代码默认值对齐**（三处默认值一致，均为 `admin/admin123456`）：
`settings.py:31`、`mult_agents/config.py:58`、`app_main.py:132`。
