## 0. 选材原则（先明确什么能讲、什么不能讲）

这道题考的不是"你修过多少 bug"，而是**你能不能识别出哪些是真正的技术约束**。所以选材只有一条标准：

> **难点必须来自客观约束，而不是来自我的疏忽。**

| 类型 | 例子 | 能不能讲 | 原因 |
|------|------|----------|------|
| ✅ **标准/协议约束** | 浏览器 `EventSource` 只支持 GET，不能带 body 和自定义头 | **能讲** | 这是规范限制，任何人在这个场景下都会撞上 |
| ✅ **框架/语言机制约束** | asyncio 单线程事件循环，同步调用会阻塞所有请求；`task.cancel()` 是协作式的 | **能讲** | 语言机制如此，不是写错 |
| ✅ **算法/模型的固有矛盾** | 向量检索"召回精度 vs 上下文完整性"天然互斥；LLM 会编造引用 | **能讲** | 领域固有难题，无标准答案 |
| ✅ **平台/环境差异** | Windows 默认事件循环与 psycopg async 不兼容 | **能讲** | 环境差异，Linux 上根本不出现 |
| ✅ **分布式一致性约束** | 跨系统（DB 事务 + 消息投递）没有原子性 | **能讲** | 分布式系统的经典约束 |
| ❌ **自己的代码缺陷** | 异常被吞、返回结构设计不当、链路没接上、字段没写 | **不讲** | 面试官会怀疑代码基本功 |
| ⚠️ **自己挖的坑但已形成机制** | 曾靠 grep 调用点挖出一批"写了没生效"的链路 | **慎讲** | 只能作为"我建立了什么质量机制"的佐证，且必须放在最后、一笔带过 |

**第 6 章「慎用区」**收录了那些不能当难点讲、但面试官主动问到工程质量时可以有限使用的素材。默认不主动提。

**讲述总纲**：每个难点都用同一句式开场——**"这个问题的本质是一个客观约束：……在这个约束下，常规做法不成立，所以……"**。先把约束立住，面试官才会认同这是难点。

## 1. 项目开场白

### 1.1 一句话定位

> 一个基于 LangGraph 的多智能体深度研报系统：用户抛一个研究问题，系统自主完成**意图识别 → 需求澄清 → 研究计划 → 双路并行检索（联网 + 本地知识库 RAG）→ 证据评审 → 分析 → 反思补搜 → 长文撰写**的完整闭环，全程 SSE 流式输出，中间有 3 个人工确认点，产出带引用溯源的研究报告。

### 1.2 60 秒版口述稿

> 我最满意的项目是一个**多智能体深度研报系统**，后端约 12000 行，我负责编排、检索链路、流式通信和前端消费的完整实现。
>
> 技术上分四层：前端 Vue3，后端 FastAPI，中间是 LangGraph 编排的 10 节点状态图，底层挂 PostgreSQL 做 checkpoint 和记忆、Milvus 做向量检索、RabbitMQ 做文档向量化管道。
>
> 它跟"调个 LLM 套壳"最本质的区别是：**它是一个有状态的长任务系统**。一次研究可能跑几分钟、迭代好几轮，而且**流式、可中断、可取消、可恢复这四件事必须同时成立**——这四件事单独做都不难，凑在一起就全是坑。
>
> 开发过程中我遇到的最有价值的问题，基本都来自客观约束而不是手误。比如：
>
> - 浏览器原生 `EventSource` 只支持 GET、不能带请求体，而我们的研究查询又长又敏感，只能放弃它、用 fetch + ReadableStream **手写一套 SSE 解析器**——那半包处理、心跳保活、重连全得自己接管；
> - 前端关掉连接，后端的 LLM 其实**还在跑、还在烧 token**，因为流式架构里"断开"和"停止"是两件事；
> - 还有 Windows 上异步连接池会稳定卡死 30 秒，同一份代码在 Linux 上完全正常。
>
> 想听哪个方向？我可以挑一个展开讲排查和设计过程。

**为什么这么收尾**：三个钩子全部是客观约束，且分属前端协议、异步并发、平台差异三个不同维度。面试官无论挑哪个，你都在展示"识别约束"的能力，而不是"修 bug"。

### 1.3 3 分钟版口述稿

> 定位是**多智能体深度研报系统**。要解决的问题是：通用大模型直接问"帮我研究一下 XX"，输出浅、没出处、还容易编。我们的做法是把它拆成一条**可控的研究流水线**。
>
> **架构四层**：
>
> 最上层 Vue3 前端。流式消费这块我没用原生 `EventSource`，而是用 `fetch` + `ReadableStream` 手写了一个 SSE 消费器——原因下面讲，这本身就是一个绕不开的约束。手写之后，半帧缓冲、心跳、断线重连这些可靠性问题就都归我管了。
>
> 第二层 FastAPI，对外是 `/stream`、`/resume`、`/cancel`，内部用纯 async generator 把事件一路 yield 到 HTTP 响应体。中间有 TaskRegistry 管运行中的任务，防止同一会话重复提交。
>
> 第三层是核心，LangGraph 编排的 10 节点状态图。意图识别做了"规则快速通道 + LLM 精判"两层——简单问题走直答通道，根本不进多智能体链路。复杂问题才进规划、检索、分析、反思、撰写。反思这里有个自环：分析节点产出信息缺口，反思节点基于缺口生成定向补搜计划回流检索，靠迭代计数和上限双保险防死循环。
>
> 第四层是基础设施：PostgreSQL 存 checkpoint 和长期记忆，是唯一事实源；Milvus 存向量；RabbitMQ 做上传后的异步向量化。
>
> **这个项目我认为最值得讲的是三件事**：
>
> 一是**在标准约束下自己实现协议**——SSE 用不了原生 API，就得自己把流式解析做对；
>
> 二是**异步语义的边界**——`asyncio` 是单线程事件循环，一个同步阻塞调用会拖死同进程所有用户；`task.cancel()` 又是协作式的，不是调用就能停。这些机制不搞清楚，系统在并发下就会表现得很"玄学"；
>
> 三是**让不可信的生成过程产出可验证的输出**——LLM 编造引用是模型固有缺陷，prompt 根治不了，必须靠工程手段兜底。

### 难点一：在"标准不支持"的前提下手写一套 SSE 流式协议

> 客观约束：**浏览器原生 `EventSource` 只接受 URL，不支持请求体、不支持自定义请求头**

**约束是什么（先把约束立住）**

`EventSource` 的构造函数签名是 `new EventSource(url, { withCredentials })`——只接受一个 URL。这是 SSE 规范有意为之的定位：客户端只表达"我要订阅这个流"，握手时不传业务数据。规范预期的传参方式是 URL path 或 query string。

但我们的 `/stream` 端点撞上了两条硬约束：

| 约束 | 具体表现 | 后果 |
|------|----------|------|
| **查询可能很长** | 研究类问题如"请调研当前 AI Agent 领域的前沿进展，包括主流框架、典型应用场景和落地挑战"有 40+ 中文字符；URL 编码后每个中文字符膨胀为 9 字节 → 单参数约 360 字节，加上 user_id / thread_id / tenant_id 轻松超过 2K | Nginx 默认 8K 尚可，但生产环境的 CDN / WAF 常限制在 2K 甚至更短 |
| **查询是敏感数据** | GET 的 URL 会进 Nginx access log、CDN 日志、浏览器 history | 用户研究意图属于隐私，不能留在访问日志里 |

结论：**必须用 POST + JSON body**。而一旦放弃 `EventSource`，就同时放弃了它的三个内置能力，全部要手写：

1. **帧解析**（含半包处理）
2. **自动重连**（原生的靠 `retry:` 字段）
3. **事件 ID 追踪**（原生的靠 `Last-Event-ID` 请求头）

**手写第一件事：半包 / 黏包处理**

这是流式解析的固有难题——TCP 是字节流，`reader.read()` 返回的 chunk 边界和 SSE 帧边界**没有任何关系**。一个 `data: {...}\n\n` 帧可能被切成两个 chunk 送达，也可能三个帧挤在一个 chunk 里。

```typescript
// agent_front/src/api/sse.ts
const reader = resp.body.getReader()
const decoder = new TextDecoder('utf-8')
let buffer = ''                      // 跨 chunk 的半帧缓冲

while (true) {
  const { done, value } = await reader.read()
  if (done) break
  buffer += decoder.decode(value, { stream: true })   // stream:true 保证多字节字符不被截断

  const frames = buffer.split('\n\n')
  buffer = frames.pop() || ''        // ← 最后一段可能是半帧，留到下一轮

  for (const frame of frames) {
    const line = frame.trim()
    if (!line.startsWith('data:')) continue    // 注释帧/event 帧/id 帧一律跳过
    try { onEvent(JSON.parse(line.slice(5).trim())) }
    catch { /* 单帧解析失败不中断整条流：向前兼容 */ }
  }
}
```

两个细节值得讲：
- **`decoder.decode(value, { stream: true })`**：不加 `stream: true` 时，一个多字节 UTF-8 字符（比如中文）如果正好跨在两个 chunk 边界上，会被解码成乱码。**中文场景下这是必踩的坑**。
- **`frames.pop()` 留半帧**：不能对每个 chunk 直接 `split` 后全量处理，否则最后一帧永远是残缺的、`JSON.parse` 必然失败。

**手写第二件事：心跳保活**

客观约束：**中间代理（Nginx / CloudFlare）默认 60 秒无数据就断开连接**。而 LLM 深度思考时可能 30 秒以上不吐 token——用户看到的是"卡住了然后报错"。

解法是利用 SSE 协议的一个特性：**以 `:` 开头的行是注释帧，浏览器会忽略它、不触发 `onEvent`，但它能让数据流保持活跃**。

```
: ping\n\n     ← 每 15 秒下发一次，间隔可配置
```

这个方案的好处是**零侵入**——不需要前端写任何特殊逻辑，心跳帧在解析层就被 `startsWith('data:')` 过滤掉了。对比 WebSocket 的 ping/pong 需要自己实现控制帧协议，SSE 的注释帧是白送的能力。

**手写第三件事：重连状态机**

原生的自动重连不能用了，得自建，而且**关键难点在于"判断该不该重连"**：

- 网络抖动断开 → 应该重连
- **用户主动点了取消 → 绝对不能重连**（否则用户取消了又自己跑起来）

实现上用指数退避（1s → 2s → 4s → … → 30s，上限 5 次），重连前先查状态可恢复性，若 `resumable` 则先拉服务端最新消息对齐（清掉半截的流式消息），再走 `/resume` 让 LangGraph 从 checkpoint 续跑，**已检索到的 sources / findings 全部保留**，不重复输出已生成的 token。

**后端侧：async generator 的全链路穿透**

前端手写解析器的另一半是后端要能稳定地"喂"。后端用 FastAPI 的 `StreamingResponse` 挂一个纯 async generator，LangGraph 的 `astream(stream_mode=["custom", "updates"])` **双通道消费**：

- `custom` 通道：节点内通过 StreamWriter 推送的 token / 进度 / 来源事件
- `updates` 通道：捕获节点级完成状态与 `__interrupt__` 中断信号

**协议设计：10 种事件 + 信封 + 三条不变式**

- `EventEnvelope(type, ts, data)` 统一信封，10 种语义事件覆盖 `run.started` → `run.completed` 的完整生命周期
- Pydantic 做**出口校验**——非法事件无法流出服务端；协议文档 `docs/event-protocol.json` 由 schema **单一来源自动导出**，前后端契约同源
- **三条不变式**（这是协议设计的核心，值得单独讲）：
  1. 流必须以 `completed` / `cancelled` / `error` 之一终止——保证前端永远不会"等一个不会来的结束"
  2. `delta` 顺序拼接即完整文本——保证流式和整段生成结果一致
  3. 前端**忽略未知事件类型**——保证协议可以向前兼容地演进

**收尾话术**

> 这个难点让我理解了一件事：**用现成的 API 时，那些"免费"的能力其实是协议在替你承担复杂度**。一旦因为约束放弃它，复杂度不会消失，只会转移到我这边——半包、心跳、重连，一个都跑不掉。所以我后来的判断标准是：放弃原生能力之前，先数清楚要接手多少件事。

**追问预案**

| 追问 | 应答要点 |
|------|----------|
| 为什么不用 WebSocket？ | 我们的流是**单向**的，全双工用不上；SSE 基于普通 HTTP，能直接复用现有鉴权、网关、日志链路，运维成本低；断线后靠 `thread_id` + checkpoint 续流，也不需要 WebSocket 的连接状态 |
| 半包只靠 `\n\n` 分割可靠吗？ | 在这个场景下可靠——服务端是唯一写入方，且保证每个帧以 `\n\n` 结尾。边界情况是"最后一个 chunk 正好落在 `\n` 和 `\n` 之间"，此时 `split` 得到的最后一段是空串或残缺帧，`pop()` 留到下一轮拼接即可 |
| 事件 ID 追踪为什么不需要？ | 因为续流不依赖 SSE 事件 ID，而依赖 LangGraph checkpoint。`Last-Event-ID` 只能做到"事件级重放"，而我们需要的是"状态级恢复"——后者粒度更粗但语义正确 |
| 协议怎么保证前后端不漂移？ | `docs/event-protocol.json` 由 Pydantic schema 自动导出，前端类型定义从同一份文件生成（`events.gen.ts`），契约同源，不存在手写两份导致漂移的问题 |

### 难点二：让"取消"真的停下来——流式架构里"断开"不等于"停止"

> 客观约束：**SSE 是单向无状态协议，客户端断开连接不会通知服务端停止工作；且 `asyncio` 的取消是协作式的**

**约束是什么**

这是一个**反直觉但客观**的陷阱：

> 用户点了"停止"，前端关掉 SSE 连接。但后端那个 async generator 里的 LLM 调用**还在跑**——token 还在生成、钱还在烧、CPU 还在占。

原因有两层：
1. **协议层**：SSE 没有"客户端主动终止"的语义。断开 TCP 连接对服务端来说只是一个写失败，不是一个业务信号。
2. **语言层**：`asyncio.Task.cancel()` 是**协作式**的——它只是往任务里投一个 `CancelledError`，而这个异常**只有在任务执行到 `await` 点时才可能被抛出**。如果任务正卡在一个同步阻塞调用里，取消请求会一直排队等。

**方案：三层配合**

**① TaskRegistry —— 让任务可被寻址**

```python
# thread_id → asyncio.Task 注册表
# 作用有三：可取消、可去重、可观测
```

- 注册：任务启动即登记，`done_callback` 自动清理
- **并发拦截**：同一 thread 重复提交直接 409，不允许并发 run（否则两个 run 抢同一份 checkpoint）
- 运行状态写 Redis，支撑多实例共享视图

**② `task.cancel()` —— 让取消落在 await 点上真正生效**

```
POST /cancel → TaskRegistry 取出 task → task.cancel()
→ CancelledError 在 generator 内部的 await 点抛出
→ 上游 LLM 请求被中断，token 消耗立即停止
→ 发 run.cancelled 事件，前端对齐终态
```

这里的关键认知是：**取消要生效，任务必须经常回到 await 点**。这反过来约束了实现——不能有长时间同步阻塞（这一点直接引出了难点五）。

**③ 多实例广播 —— 取消请求可能落在别的 worker 上**

用户点取消时，请求可能被负载均衡打到 A 实例，而任务实际跑在 B 实例上。A 上的 TaskRegistry 里根本没有这个 task。

解法：取消指令走 **Redis Pub/Sub 广播**，所有 worker 都收到，持有该任务的实例执行本地 `cancel()`，实现任意 worker 上的一致性终止。

**④ 前端乐观取消 —— UI 不能等后端**

前端调完 cancel 接口立即本地置 `cancelled` 状态，网络异常也不阻塞 UI；后端 `run.cancelled` 事件到达时兜底对齐。这是"乐观更新 + 服务端最终一致"的典型用法。

**收尾话术**

> 这个问题让我记住了异步编程的一条基本规律：**`cancel()` 是"请求取消"，不是"执行取消"**。它能不能生效，取决于任务多久回到一次 await 点。所以"取消能不能做得干净"其实不是取消逻辑本身决定的，而是**整个任务的阻塞特性**决定的——这也是为什么我后来专门去清了一遍同步阻塞调用。

**追问预案**

| 追问 | 应答要点 |
|------|----------|
| 前端直接关连接不行吗？ | 不行。关连接只是停止"接收"，服务端的生成过程不受影响。对 LLM 应用来说这是真金白银的成本问题，必须显式通知服务端 |
| 怎么保证取消不会留下脏状态？ | 取消发生在 await 点，此时 checkpoint 记录的是**上一个超级步的完整状态**，不存在"写了一半"的中间态。恢复时从最近 checkpoint 继续，语义正确 |
| 取消和恢复会不会冲突？ | 取消后任务从 TaskRegistry 移除，`/resume` 会从 checkpoint 重新起一个任务并登记。两者通过 TaskRegistry 的状态互斥，不会并发 |
| 多实例广播丢了怎么办？ | Pub/Sub 是 fire-and-forget，确实可能丢。兜底是 Redis 里的运行标记 + 前端重连后的状态对齐——最坏情况是取消延迟生效，不会导致任务永久失控 |

### 难点三：检索质量攻坚——三组"天然互斥"的约束

> 客观约束：**向量检索的"召回精度"与"上下文完整性"天然互斥；稠密向量与关键词检索各有盲区；两路分数量纲不可比**

**约束一：块切小了召回准，块切大了上下文全**

这是 RAG 最根本的矛盾，没有免费的解：

| 切分策略 | 向量质量 | 上下文完整性 |
|----------|----------|--------------|
| 小块（如 256 字） | ✅ 语义聚焦，向量表达精准 | ❌ 命中后拿到的上下文残缺，LLM 看不到完整论述 |
| 大块（如 2048 字） | ❌ 语义被稀释，向量区分度下降 | ✅ 上下文完整 |

**解法：Parent-Child 双层分块（small-to-big）**

```
父块 2048 字  ← 只用于提供上下文，不出向量
  └─ 子块 512 字（重叠 64）  ← 出向量，用于召回
```

- **子块出向量** → 召回精度按小块的标准来
- **命中子块后自动扩展回父块** → 送给 LLM 的上下文按大块的标准来

这个设计的价值在于：**把"召回精度"和"上下文完整性"从互斥关系解耦成了两个独立决策**。分块阶段一次投入，检索阶段两个诉求同时满足。

**约束二：稠密向量擅长语义泛化，弱于字面精确匹配**

用户查"XX-2000 型号的接口协议"，向量检索可能返回一堆"设备接口规范"的泛化内容，却漏掉真正写着 `XX-2000` 的那篇文档——因为专有名词、型号、编码这类 token 在语义空间里区分度很低。

**解法：双路召回 + RRF 融合**

```
Milvus 稠密向量召回（recall_k=20）   ← 负责语义泛化匹配
        +
PostgreSQL 关键词召回（recall_k=20） ← 负责专有名词/编码/型号的字面命中
        ↓
     RRF 融合重排
        ↓
  qwen3-rerank 专用模型精排
        ↓
    Top5 送入 LLM
```

关键词那一路的实现细节：PG 里用 `content_tsv` **生成列 + GIN 索引**做全文检索。生成列的好处是索引维护由数据库自动完成，不需要应用层同步。

**约束三：两路分数量纲不可比**

余弦相似度（0~1 的连续值）和关键词命中率（词频/覆盖率）**不在同一个量纲上**，直接加权求和需要反复调参，且换一个数据集就要重调。

**解法：RRF（倒数排名融合）只用排名，不用分数**

```
score(doc) = Σ  1 / (k + rank_i(doc))
```

好处是**天然免归一化、免调参**——不管两路的分数量纲差多少，只看相对排名。工程上极其稳定。

> 这里有个设计上的坑值得提：RRF 的前提是**"每路一个列表"**。如果实现时把多个查询变体的向量结果 `extend` 成一个列表再传进去，变体的顺序就会混进 rank 维度，查询改写带来的多路召回优势直接被抵消掉。

**约束四（认知层面）：打分函数的分母必须只包含"可能被命中的东西"**

这是我在这个方向上最深的一个认知，也是最值得讲的。

现象：用户用**一句完整的长问句**提问时，本地知识库恒返回 0 条。

根因在一个相关性打分公式上——它的定义是「命中词数 ÷ 查询词总数」，而分词时把**指令词**和**整句片段**也算进了分母：

```
查询：请对比《RAG 综述》与《HNSW 索引原理》两篇文档的核心观点，
      说明它们各自解决什么问题

切出的词表（8 项）：
  ['请对比', '综述', '索引原理', '两篇文档的核心观点',
   '说明它们各自解决什么问题', ...]
   ↑ 这一类词永远不可能出现在任何文档正文里 —— 分母被凭空撑大

HNSW 文档实际命中 2 个 → 2 / 8 = 0.25 < 阈值 0.35 → 被判定为不相关，丢弃
```

**关键在于：这不是阈值定高了，而是分母的构成错了。** 把阈值降到 0.2，长句能过了，但无关文档也会跟着混进来——因为问题的根源是分母里塞了永远不可能被命中的项。

解法：只统计"内容词"——新增指令词表从分母剔除，超过 6 字的 CJK 整句片段排除出分母，全是长片段时退化为 2-gram 兜底保证仍能算分。

修复后实测：

| 文档 | 得分 | 判定 |
|------|------|------|
| HNSW 索引原理 | 0.40 | ✅ 保留 |
| RAG 综述 | 0.40 | ✅ 保留 |
| 无关文档 | 0.00 | ❌ 正确丢弃 |

**阈值实验数据**（追问时用）

| 阈值 | 召回率 | 精确率 | 适用场景 |
|------|--------|--------|----------|
| 0.20 | 95% | 45% | 召回优先，噪声大 |
| **0.35（现）** | **78%** | **82%** | **平衡点** |
| 0.50 | 55% | 93% | 精确优先，可能漏召回 |

**收尾话术**

> 这件事给我的最大启发是：**如果一个问题调参就能解决，往往说明你还没找到根因。** 当时我的第一反应是调阈值，但冷静下来问自己——有没有一个阈值能同时让长查询和短查询都正确？没有。因为问题根本不在阈值。**分母里不该有永远不会被命中的项，这是打分函数的定义问题，不是参数问题。**

**追问预案**

| 追问 | 应答要点 |
|------|----------|
| 为什么用 RRF 不用加权求和？ | 加权求和需要先把两路分数归一化到同一量纲，而归一化方式本身又是个需要调参的超参（min-max? z-score?）。RRF 只用排名，换数据集不需要重调，工程稳定性优先 |
| rerank 为什么不用 LLM-as-reranker？ | 换成了专用重排模型 `qwen3-rerank`。专用模型延迟更低、筛选效果更稳，成本也更可控。LLM-as-reranker 的问题是要为每个候选跑一次生成，Top20 就是 20 次调用 |
| 文档怎么解析的？ | 只开放 MD 和 Word 两类。**先按标题层级做语义粗切分，再用递归字符切分结合中文分隔符做精细切分**——切分质量直接决定检索精度，这是 RAG 效果的地基 |
| 查询改写做了什么？ | 让 LLM 对原始提问生成扩展、精简、反问句式三种检索变体，多维度覆盖检索视角，缓解表述偏差导致的漏召回 |

### 难点四：让不可信的生成过程产出可验证的输出

> 客观约束：**LLM 编造引用是模型固有缺陷，prompt 无法根治**

**约束是什么**

这是 LLM 应用的**结构性缺陷**，不是"prompt 写得不够好"：

- 模型在生成时，如果上下文里没有明确可引用的证据，它会**倾向于补一个看起来合理的引用**，而不是说"我没有依据"
- 而且这个行为是**不可靠地随机**的——同一段 prompt，有时编有时不编
- 更麻烦的是编造的引用**格式上完全合法**，正则都挑不出来（因为它模仿的就是真引用的格式）

所以结论是：**不能指望模型自己不出错，只能在生成之后做校验。**

**方案：四重防御**

```
① 登记：检索到的每条证据先登记全局唯一 source_id
        ↓
② 约束：撰写时把"合法 id 集合"注入 prompt，明确只允许引用集合内
        ↓
③ 校验：生成后用正则逐条校验，非法角标直接剔除
        ↓
④ 度量：统计引用覆盖率（带角标论断占比），随报告输出，暴露质量
```

**① 全局编址体系**

```
WEB{iteration}_{query}-{n}     ← 联网来源
LOC{iteration}_{query}-{n}     ← 本地知识库来源
```

这个编址设计解决了三个问题：
- **可定位**：从 id 就能反查是哪一轮迭代、哪个查询、第几个来源
- **可去重**：跨迭代、跨通道的证据按多键（`url+title` / `doc_id+snippet`）自动合并，避免同一篇文档被引用多次
- **可校验**：格式固定，正则 `\[([A-Z]+\d+_\d+-\d+)\]` 能精确提取

**② prompt 侧约束**

撰写节点把合法 source_id 列表（截取前 80 个，避免 prompt 过长）注入上下文，并明确约束引用范围。

**③ 生成后校验（核心一环）**

```python
def _validate_and_fix_citations(content, valid_source_ids):
    pattern = r'\[([A-Z]+\d+_\d+-\d+)\]'
    def replace_citation(match):
        cid = match.group(1)
        return f"[{cid}]" if cid in valid_source_ids else ""   # 非法 → 直接移除
    fixed = re.sub(pattern, replace_citation, content)
    used = [cid for cid in _extract_citation_ids(fixed) if cid in valid_source_ids]
    return fixed, used
```

**这一步是整个防线的关键**：不管模型怎么编，只要 id 不在合法集合里，就会被物理删除。**这是"不可信生成"到"可信输出"的转换点**——安全边界从"相信模型"变成了"校验结果"。

**④ 引用覆盖率度量**

统计"带角标论断数 / 主要论断数"，随报告输出。这一步的价值是**把质量问题从"感觉"变成"数字"**——如果覆盖率只有 30%，说明报告里大部分论断没有依据支撑，这是可观测的退化信号，而不是等用户投诉。

**配套：参考资料区三级降级**

渲染参考资料时按优先级降级，保证任何情况下报告都有来源区：

1. 优先从正文中按**实际引用顺序**提取（保证正文角标和文末来源一一对应）
2. 正文无引用 → 降级到 `findings` 里的 `source_ids`
3. 再降级 → 全量来源表
4. 本地来源按 locator 去重展示（同一文件多个 chunk 只展示一次，避免参考资料区被同一篇文档刷屏）

**收尾话术**

> 这个难点的本质是：**当系统的某个组件天然不可靠时，架构上必须给它加一层"结果校验"，而不是试图让它变可靠。** 模型会编引用这件事，我改变不了；但我可以让"编出来的引用"在进入最终交付物之前被过滤掉。安全边界应该画在**结果**上，而不是**信任**上。

**追问预案**

| 追问 | 应答要点 |
|------|----------|
| 为什么不靠 prompt 解决？ | 试过，但 LLM 的行为是概率性的，prompt 只能降低概率、不能归零。而且 prompt 越长越容易被稀释，可靠性反而下降。工程上不能依赖"概率性的正确" |
| 校验会不会误删合法引用？ | 正则是格式匹配 + 集合校验两步。格式对但不在集合里 → 说明是编的，删掉；格式不对 → 说明模型没按规范写，也删掉（同时是 prompt 需要调整的信号） |
| 剔除后报告出现论断无引用怎么办？ | 这正是覆盖率指标的意义。覆盖率低说明证据不足，这个信号会暴露出来。更理想的做法是让它触发证据补充，目前是记录并输出 |
| 引用冲突怎么处理？ | `deep_dive` 节点产出三类审计标记：低置信 / 证据冲突 / 证据缺失。冲突本身作为一种结论被显式标注，而不是被模型悄悄调和 |

### 难点五：事件循环上的两处硬约束

> 客观约束：**asyncio 是单线程事件循环，任何同步阻塞会卡死同进程所有请求；Windows 默认事件循环与 psycopg async 不兼容**

**约束一：一个同步调用，拖死所有人的流**

**asyncio 的模型是：一个线程跑一个事件循环，所有协程在这个循环里协作式调度。** 这意味着——**任何一个协程里出现同步阻塞调用，整个进程的所有请求全部卡住**。

而我们的检索链路里，同步实现恰好特别多：

| 环节 | 实现 | 性质 |
|------|------|------|
| LLM 调用 | DashScope SDK 同步客户端 | 秒级 |
| 向量检索 | Milvus / pymilvus 同步接口 | 百毫秒级 |
| 关键词检索 | psycopg2 同步驱动 | 百毫秒级 |
| 精排 | rerank HTTP 请求 | 秒级 |

**后果非常反直觉**：用户 A 发起一次检索，用户 B 正在看的 SSE 流会**卡住不动**——因为循环线程被 A 的同步调用占住了，B 的协程根本没有机会被调度。

而且这个现象**在单用户测试时完全看不出来**，只有在并发下才暴露，排查时表现为"偶发卡顿"这种最难定位的症状。

**解法：把同步链整体移出事件循环**

```python
# 修复前：同步链直接跑在协程里 → 阻塞循环
# 修复后：
records = await asyncio.to_thread(web_search_records, query_text, 4)      # web_search.py
records = await asyncio.to_thread(search_knowledge_base, ...)             # local_rag.py
raw     = await asyncio.to_thread(...)                                    # tools.py
```

`asyncio.to_thread` 把同步调用丢到线程池执行，事件循环线程在 `await` 期间可以去调度其他协程。**这是"用线程池兜住同步依赖"的标准手法**——不需要把每个第三方 SDK 都改写成异步版本，代价可控。

> 这里有个和难点二的呼应：**阻塞不但影响并发，还影响取消**。同步调用期间任务回不到 await 点，`cancel()` 就投不进去。所以清掉同步阻塞是"取消能生效"的前提。

**约束二：Windows 上异步连接池稳定卡死 30 秒**

**现象**：本地开发时，异步连接池稳定卡 30 秒超时；**同一份代码在 Linux 和容器里完全正常**。

**排查路径**（讲方法）：

```
1. 超时值固定为 30s → 不像网络抖动（抖动不会这么稳定），像某个默认超时常量
2. 排除外部因素：凭据、网络、容器配置都正常，且 Linux 上同一套配置没问题
   → 问题不在配置，在运行环境
3. 对比两端差异 → 定位到事件循环实现不同
4. 结论：Windows 上 asyncio 默认使用 ProactorEventLoop，
   而 psycopg 的异步实现依赖 SelectorEventLoop 的 socket 语义
   → 连接建立后的事件通知收不到，只能等超时
```

**解法**：显式设置 `WindowsSelectorEventLoopPolicy`，并且在启动时**主动校验当前循环类型**、不是预期类型就明确告警：

```python
# app_main.py
asyncio.set_event_loop_policy(asyncio.WindowsSelectorEventLoopPolicy())
...
"""确保当前运行中的事件循环是 SelectorEventLoop（Windows 兼容 psycopg async）。"""
if not isinstance(loop, asyncio.SelectorEventLoop):
    logger.warning("当前事件循环为 %s（非 SelectorEventLoop）...", type(loop).__name__)
```

> 这个校验比修复本身更有价值——**同类问题在换 Python 版本、换启动方式（`uvicorn.run` / `uvicorn` CLI / gunicorn）时可能复发**，有校验就不会再次变成"卡 30 秒然后不知道为啥"。

**必须交代的代价（这一点最能体现工程判断力）**

> 这是**平台适配补丁，不是架构修复**。代价是 `SelectorEventLoop` 不支持 subprocess 等能力，如果后续功能需要用到，得重新评估。
>
> 我把它记录为"开发环境可用性修复"，而**没有把它当成通用方案**——因为它在 Linux 上根本不是问题，生产环境跑在容器里也不会遇到。**分清楚"架构问题"和"平台适配问题"，是我在这件事上学到的东西**：前者要设计，后者要隔离并标注。

**收尾话术**

> 这两件事合起来让我形成了一个习惯：**写完一个协程，先问一句"这里面有没有同步调用"。** 因为 asyncio 的错误不会报异常，它只会表现为"系统在并发下变慢"，这是最难被发现、也最容易被误判成"机器性能问题"的一类故障。

**追问预案**

| 追问 | 应答要点 |
|------|----------|
| `to_thread` 线程池会不会爆？ | 默认线程池有上限（`min(32, cpu+4)`）。对检索这种 IO 密集场景够用。如果成为瓶颈，下一步是给关键依赖做异步化封装，或者引入独立的执行器隔离不同优先级 |
| 为什么不全改成异步驱动？ | 成本收益不划算。第三方 SDK 异步化要改调用链、改异常处理、改测试，而 `to_thread` 一行就能解决。**优先用最小代价把问题隔离掉**，等它真的成为瓶颈再优化 |
| Proactor 和 Selector 的本质区别？ | Proactor 基于 IOCP，是真正的异步 IO 完成通知；Selector 基于 `select`/`epoll`，是就绪通知 + 同步读写。psycopg 的异步实现依赖后者的语义，在 Proactor 下事件通知对不上 |
| 生产环境会不会遇到？ | 不会——生产跑在 Linux 容器里，默认就是 Selector。这个问题只在 Windows 本地开发时出现。我保留了启动校验，是为了防止开发环境的行为差异再次被误判成业务 bug |

### 备用难点六：跨系统没有原子性——异步管道的一致性设计

> 客观约束：**数据库事务和消息投递是两个独立系统，不存在跨系统的原子提交**

**约束是什么**

文档上传后的处理链路是：**PG 落库（文档 + 切片）→ 投递 MQ → 消费端向量化入库**。

问题在于：**"数据写成功"和"消息发出去"是两个独立操作**。任何一段网络抖动、MQ 抖动，都会产生两种不一致：

- 数据落了库，消息没发出去 → **文档永远不被向量化**（用户看到上传成功，但检索不到）
- 消息发出去了，数据回滚了 → 消费者拿到一个不存在的文档 id

**为什么不用两阶段提交（2PC）？** 因为 2PC 要求 MQ 参与分布式事务，而 RabbitMQ **本身不支持 XA 事务**；即使支持，2PC 的阻塞特性和运维复杂度对这条链路来说完全不成比例。

**解法：事务性发件箱（Transactional Outbox）**

```
单个 PG 事务内：
  INSERT documents + chunks      ← 业务数据
  INSERT outbox_messages         ← 待发消息（同一事务）
COMMIT                           ← 原子性由数据库保证

事务提交后：
  投递 MQ → 成功则标记消息 sent
         → 失败则消息留在 outbox，等待补偿
```

核心思路是**把"发消息"这个不可靠的跨系统动作，转化为"写一张本地表"这个可靠的同库动作**，原子性由数据库事务天然保证。跨系统的那一步变成可重试的、幂等的后续动作。

配套的三件事：

| 机制 | 解决的问题 |
|------|-----------|
| 消费者启动期**补偿扫描** | 重投那些留在 outbox 里没发出去的消息 |
| 消费端 **content hash 幂等去重** | 重投/重复消费不会产生重复向量 |
| **死信队列（DLQ）** | 重试超限的消息不丢，可告警、可人工重放 |

还有**优雅降级**：MQ 不可用自动切同步向量化模式；向量库不可用则只存 MinIO + PG 并显式返回 failed，**原始文件绝不丢**。

**收尾话术**

> 这个设计的关键认知是：**跨系统的原子性买不到，只能"转化"。** 与其追求"两个系统同时成功"，不如把跨系统动作降级成一个可重试的本地事务，再用补偿和幂等兜住最终一致性。发件箱模式本质上是**把分布式问题转化成了单机问题**。

**追问预案**

| 追问 | 应答要点 |
|------|----------|
| 补偿扫描多久跑一次？ | 启动期扫描 + 定时扫描。因为 outbox 里的消息是"确定要发但没发出去"的，重发是安全的（幂等保护），所以扫描频率可以按业务容忍度设 |
| 消息顺序要不要保证？ | 不需要。每个切片独立向量化，彼此无依赖，乱序消费结果一致 |
| 为什么用 RabbitMQ 不用 Kafka？ | 这条链路的量级和语义都不需要 Kafka。我们要的是**可靠投递 + 死信 + 手动 ACK**，RabbitMQ 的 Topic Exchange + DLQ 语义更贴合，运维成本也更低 |

### 备用难点七：上下文窗口是硬约束

> 客观约束：**上下文窗口有限且昂贵，而研究会话天然是长对话**

**约束**：一次研究可能经过多轮澄清、多轮反思补搜，消息数会持续增长。全部塞进上下文，要么超限，要么成本和延迟失控。

**解法一：滚动摘要**

消息数超过阈值时，由 LLM 生成滚动会话摘要，同时保留最近 N 条原文。效果是**上下文窗口恒定可控**——不管对话多长，送入模型的信息量稳定在一个区间内。

**解法二：长期记忆双通道（langmem 官方推荐范式）**

```
热路径检索：研究开始前，按用户维度检索 top-5 相关记忆注入 plan 节点
            → 让规划阶段就带上用户的偏好和历史主题

后台异步提取：任务完成后 asyncio.create_task 异步沉淀
            → 不阻塞主流程，异常只记日志，零影响
```

`namespace=(memories, {user_id})` 做用户级隔离，支持多租户。记忆条目通过 `GET /memories` 对用户可见、可审计。

**收尾话术**

> 上下文窗口是不可协商的硬约束，所以策略不是"怎么塞更多"，而是"**怎么决定丢什么**"。滚动摘要丢的是细节、留的是结论；长期记忆存的是跨会话的偏好，而不是单次对话的原文。**分清楚哪些信息是"这次要用"、哪些是"以后要用"，是设计记忆系统的前提。**

## 2.5 难点补充（评测体系与依赖治理，2026-09 迭代）

> 完整版见 `面试-评测体系与指标来源.md`。这里只留**面试可直接讲**的 STAR-C 骨架。

### 难点八：传递依赖的版本漂移，让整条检索链路静默失效

> 客观约束：**`requirements.txt` 只能声明直接依赖，而真正发网络请求的是传递依赖。**

- **C**：我声明的是 `ddgs>=9.0`，但底层发请求的是它的依赖 `primp`。
  传递依赖的版本不在我的声明范围内，环境重建时可能落到有 bug 的补丁版本。
  **更麻烦的是失效形式有误导性** —— 报错是 TLS 层的
  （`cannot decrypt peer's message` / `tls handshake eof`），指向网络或代理，而真因在依赖。
- **A**：用 `uvx` 起同一个包 —— uv 会为它建**隔离环境**并装最新依赖，
  等于**免费拿到一个"干净对照组"**。同一调用在对照组成功、在项目环境失败，
  就把问题锁定到了依赖版本。
- **对比实验**（同一 `ddgs 9.16.0`，仅 `primp` 版本不同）：

  | primp | 结果 |
  |------|------|
  | 2.0.0 | 连跑 6 次**全失败（0/6）** |
  | 2.0.1 | **3/3 成功**，每次 2.6–4.0s |

- **C（代价）**：修复只是补一行 `primp>=2.0.1`，**但诊断成本远高于修复成本**。
- **L**：我把教训固化成规则 —— **连续 `0/N` 失败时，先把依赖版本对齐到"已知可用"的
  对照组，再怀疑网络与配置**。这次我先后误判为"代理干扰 TLS""引擎封锁指纹"，全错，
  就是跳过了这一步。

### 难点九：同一 Python 环境里两个库对底层包版本互斥

> 客观约束：**Python 没有依赖隔离机制，同一环境里互斥的版本约束无法同时满足。**

- **C**：`ddgs` 的 MCP 模式要求 `mcp>=2.0`；而 `mcp 2.x` 会把 `starlette` 拉到 `1.6.0`，
  我的 `fastapi 0.123` 要求 `starlette<0.51`。实测后果是
  `TypeError: Router.__init__() got an unexpected keyword argument 'on_startup'`，
  **后端直接不可用**。
- **A**：不把 MCP 依赖装进项目环境，改为**用 `uvx` 把 MCP 服务器作为子进程启动**，
  通过 MCP 协议通信 —— `uv` 自动为子进程建隔离环境，项目环境零影响。
- **C（代价）**：多一层进程间通信、多一个配置文件、uv 缓存未预热时首次启动约 1 分钟。
  取舍是**值得** —— 换来项目依赖树不被污染。
- **反向印证**：在 Java 项目（SpringAI）里用同一个 MCP server 完全没这个问题，
  因为那边它天然就是独立进程。**这是 Python 生态特有的约束。**

### 难点十：外部搜索引擎的速率限制 vs 内部的自适应检索计划

> 客观约束：**第三方搜索引擎有速率限制，这是不可协商的外部约束。**

- **C**：而"自适应检索"的设计目标恰恰是**多轮 + 每轮多查询** ——
  一次研究实测发出 **17–44 次**请求。两者天然冲突。
- **现象**：连续请求实测**无间隔 15 次只成功 2 次**（前 2–3 次成功后急剧退化）；
  评测里两阶段失败率均约 **75%**。
- **更隐蔽的是它对结论的污染**：improved 做更多检索 → 触发更强限流 →
  产出率反而更低（0.745 → 0.371），**优化带来的收益被外部限流吃掉了**。
- **A**：模块级节流器（锁 + 时间戳），保证两次请求至少间隔 1.5s。
  用**模块级而非实例级**，因为并发检索时也要保证只有一个请求在飞。
- **C（代价）**：串行化会拉长总耗时。取舍是**用时间换成功率** ——
  检索失败导致的证据缺失，代价远高于多等几秒。

### 难点十一：评测对照的有效性 —— 指标差异可能来自环境而非代码

> 客观约束：**评测要对比改动前后，但两次运行之间的外部依赖可用性不受控。**

- **真实事故**：某一轮评测里 baseline 阶段 20 次 web 检索**全部失败**（0 条证据），
  而 improved 拿到 18 条。两阶段**检索条件根本不同**，指标差异无法归因于代码。
  而**从报告 JSON 上看不出来**，只会看到"baseline 引用覆盖率低"，
  很容易被误读成"改动有害"。
- **A**：加对照有效性守卫 `retrieval_health` —— 按阶段统计检索产出率，
  零产出即标 `degraded`，控制台直接打印"本轮对照无效"。
  细节：「没检索过」与「检索全失败」必须区分，否则空跑的阶段会误报。
- **C（代价）**：评测脚本多一层统计。取舍是**它拦下了一轮本来会被误读的无效对照**。
- **L**：**评测里最容易犯的错不是算错指标，而是在两组条件不同的情况下比较指标。**

### 难点十二：指标会饱和 —— 触顶的指标测不出改进

> 客观约束：**任何度量都有量程，接近上界时失去分辨力。**

- **案例一**：`key_point_coverage` 两个阶段都是 1.0。根因是**要点判别力不足** ——
  写成"框架名 + 通用概念"（LangGraph / 状态机），提到名字就得分。
  改为"只有读懂正确来源才可能命中"的具体机制/版本/数字。
- **案例二**：`citation_coverage` 52% vs 53% 几乎不动。把完整报告落盘后**逐句分类**，
  证明未带角标的句子里约 **80% 是分析推演与结构性标记**
  （"第三，记忆机制从无状态向有状态升级"），**本就不该带角标** ——
  ~50% 是结构性天花板。
- **⭐ 这里我推翻过自己**：此前我用"28.4% → 62.1%"论证该指标"对检索质量高度敏感"。
  **那个判断是错的** —— 那次跨越测的是"**有没有证据**"，不是"**检索有多深**"。
  修正后才定位到它的真实性质，降级为护栏指标。
- **C（代价）**：必须落盘完整报告才能逐句分类（原先只存 500 字预览）。
  取舍是宁可多存一份文件，也要能回答"这个指标的量程在哪"。

### 难点十三：MCP 协议的序列化语义 —— "返回列表"不等于"一个 JSON 数组"

> 客观约束：**MCP 的内容模型是内容块列表；函数返回 `list[dict]` 时，
> 序列化结果是"每条结果一个内容块"，而不是"一个包含数组的内容块"。**

- **现象**：按"函数返回什么、协议就传什么"的直觉去解析，**真实结果被全部丢掉** ——
  而日志里明明打印出了正确内容（`payload={'title': 'LangGraph State Machines...'}`）。
- **A**：逐块解析，块是 dict 就追加、是 list 就展开，两种都兼容，并加单测锁住格式。
- **L**：改动很小，但揭示的边界重要 —— **跨进程/跨协议调用时，
  不要假设"函数签名"等于"线上格式"**。协议语义类的问题只靠读文档很容易漏，
  **必须用真实调用验证**。

## 3. 通用回答骨架（STAR-C）

**C = Constraint（约束）**。把约束放在最前面，是这份文档和普通 STAR 最大的区别。

```
C 约束  一句话说清客观约束是什么（"EventSource 只支持 GET"）
        并且点明：在这个约束下，常规做法为什么不成立
T 任务  你的职责边界
A 动作  ┌ 约束的具体表现（带数字）
        ├ 为什么不能用常规方案（讲取舍）
        ├ 你的方案（讲设计）
        └ 代价是什么（讲代价，这一步最能建立信任）
R 结果  量化：性能、通过率、修复前后对比
L 反思  这个约束让我形成了什么判断标准
```

**可以直接背的"约束开场句"**

- "这个问题的本质是一个标准约束——浏览器 `EventSource` 只接受 URL，不支持请求体。"
- "这里的约束在协议层：SSE 是单向无状态协议，客户端断开不会通知服务端停止工作。"
- "这是模型层面的固有缺陷：LLM 编造引用是概率性行为，prompt 只能降低概率、不能归零。"
- "这是分布式系统的经典约束：数据库事务和消息投递之间没有原子性。"
- "这是运行环境的差异：同一份代码在 Windows 和 Linux 上的事件循环实现不同。"

**三句可以直接背的"反思句"**

- "用现成 API 时，那些免费的能力其实是协议在替你承担复杂度；一旦放弃它，复杂度不会消失，只会转移到我这边。"
- "`cancel()` 是请求取消，不是执行取消——它能不能生效，取决于任务多久回到一次 await 点。"
- "如果一个问题调参就能解决，往往说明你还没找到根因。"

**没准备过的问题的兜底话术**

> "这个约束我没遇到过。如果让我判断，我会先确认三件事：一是这个约束是规范层面的还是实现层面的（能不能绕开）；二是常规方案在这里失效的具体原因是什么；三是代价能不能被隔离到一个可控的范围内。"

## 4. 追问防御区

### Q1 为什么用 LangGraph，不自己写状态机？

> 自己写至少要处理四件事：状态持久化与恢复、中断/恢复语义、并行分支的状态合并、流式事件透传。LangGraph 把 checkpoint、`interrupt`/`Command`、reducer 合并、`astream` 双通道都做成了一等公民。
>
> **我的判断是：这套东西自己写能写，但写不对的地方会很隐蔽**——比如并行写入的合并顺序、恢复时的状态一致性。所以我选择把精力放在业务节点和检索质量上。
>
> 代价我也清楚：框架抽象带来调试成本。我确实踩过 `astream` v1/v2 差异、`__interrupt__` 事件识别这类坑，都需要读源码才能定位。

### Q2 流式为什么用 SSE 不用 WebSocket？

> ① 我们的流是**单向**的，全双工用不上；② SSE 基于普通 HTTP，能复用现有鉴权、网关、日志链路；③ 断线后靠 `thread_id` + checkpoint 续流，不需要 WebSocket 的连接状态。
>
> 代价是原生 `EventSource` 不支持 POST 和自定义头，所以前端用 `fetch` + `ReadableStream` 手写解析器——半帧缓冲、`: ping` 心跳、指数退避重连全部自己接管。这笔账我认为是划算的，因为换来的是"研究查询不进 access log"。

### Q3 状态为什么存 PostgreSQL 而不是 Redis？

> 定位不同：**PG 是事实源，Redis 是热缓存**。中断现场、研究状态必须持久——服务重启、多实例部署、用户可能几十分钟后才回来确认，都不能丢。Redis 的持久化语义和内存成本不适合承担这个角色。
>
> 实现上是三级降级链 `AsyncPostgresSaver → AsyncRedisSaver → InMemorySaver`，降级链的意义是开发环境可以零依赖跑起来。

### Q4 并行节点同时写 State 会不会冲突？

> 不会。并行分支（`web_search ∥ local_rag`）写入的字段挂了 `operator.add` reducer，LangGraph 在合并时按 reducer 语义累加，**不需要应用层加锁**。
>
> 这也是选 LangGraph 的一个实际收益：状态合并是框架级的关注点，不是每个节点各写一遍。State 按会话/研究/进度三组分类组合继承，17+ 字段挂 reducer。

### Q5 这个项目里你个人的贡献边界是什么？

> 需要区分清楚：**编排框架（LangGraph）、模型能力（DashScope）、中间件（PG / Milvus / RabbitMQ）是选型和集成，不是我实现的**。我实现的是：
>
> ① 10 节点状态图的拓扑设计与条件路由；② State 的分组结构与 reducer 设计；③ 整套 SSE 事件协议与前后端流式链路（含手写解析器）；④ 混合检索链路（双路召回 + RRF + rerank + Parent-Child 分块）；⑤ 引用溯源与幻觉防御；⑥ 任务生命周期管理（注册表、取消、多实例广播）；⑦ 文档向量化的异步管道与一致性保障。
>
> 一句话概括我的角色：**我是那个把"能跑的 demo"变成"在并发、中断、失败下行为可预期"的系统的人。**

### Q6 如果重做，你会改什么？

> 三件事：
> ① **把阻塞检查变成机制**。现在是我人工清了一遍同步调用，更好的做法是在 CI 里加一条静态检查，禁止在协程路径上直接调用已知的同步 SDK。
> ② **协议层加版本协商**。目前靠"前端忽略未知事件类型"实现向前兼容，更严谨的做法是在 `run.started` 里带上协议版本，让前端能做能力探测。
> ③ **引用覆盖率从"输出指标"变成"触发动作"**。现在覆盖率低只是记录下来，理想情况是它应该自动触发证据补充或降级提示。

### Q7 系统的瓶颈在哪？

> 诚实说，瓶颈在**串行的 LLM 调用次数**。一次完整研究要经过意图 → 澄清 → 规划 → 检索 → 分析 → 反思 → 撰写，每步都是一次或多次 LLM 调用，总延迟累加。
>
> 已经做的优化：① 意图识别"规则快速通道 + LLM 精判"，简单问题直接短路；② 简单问答走直答通道不进多智能体；③ 检索阶段 web 与 local **并行**；④ 按节点分温度调优（路由 0.0 / 评审 0.2 / 规划分析 0.3 / 检索撰写 0.4）。
>
> 还能做的：query 改写与多路召回并行化、rerank 流式化、热点查询的检索结果缓存。

### Q8 你简历上这些指标是怎么测出来的？数据从哪来？

> 三层，都可以展开：
>
> ① **数据集**：50 道题的 Golden Set（30 道走完整研报链路 + 20 道直答），
> 版本化在 JSON 里。核心不是题量，是**要点的判别力** —— 要点必须是"只有读懂正确来源
> 才可能命中"的具体机制/版本/数字，否则两个版本都满分，指标失去分辨力。
>
> ② **指标分两层**：规则型（纯函数、零依赖、可离线）当**回归哨兵**，
> LLM-as-Judge 做语义终评。判官本身不确定，所以**多轮取中位数**，
> 轮数是成本旋钮。规则型会低估同义表述，所以**不替代语义评估**。
>
> ③ **对照设计**：同题跑两组配置（`max_iterations=1` vs `2`），
> 抵消题目难度差异；并且有**对照有效性守卫** —— 外部依赖可用性不受控，
> 所以把"检索产出率为 0"变成显式机器判定，避免在两组条件不同的情况下比指标。

### Q9 50 道题够吗？

> **不够，这是当前明确的短板。** 50 题是"改动前后可比"的最小集合，
> 不是统计意义上充分的样本。而且我实际只跑了前 5 题 —— n=5 仍然偏小，
> 只够排除明显的方差。
>
> 举一个真实的例子说明为什么必须扩样本：单题测出来幻觉率 improved 差了 9 倍，
> 我差点就去调提示词了；扩到 5 题之后发现是 **n=1 的方差**，均值基本持平。
> **n=1 时噪声和信号分不开。**
>
> 补法：扩到能覆盖不同领域/难度分层，每题至少跑 3 次取分布而不是单次。

### Q10 规则型指标会不会误判？

> 会，而且我在代码注释里明确写了这个局限：规则型指标**会低估同义表述**
> （要点写"状态机"而报告写"有向图"，字面匹配不到），
> 因此**不替代语义评估**。
>
> 所以我把它定位成**哨兵**而不是结论 —— 它的价值是"分数掉了说明一定有问题"，
> 而不是"分数高说明一定好"。能用规则算的绝不用判官，但语义维度只信判官。

### 5.1 ⚠️ 系统指标：旧数字不可用，以实测为准

**旧行（`研究完备性 89%、幻觉率 6%、引用准确率 94%`）已删除。** 核实后确认：
这三个数字**拼自不同时间点的 n=1 单次运行**，其中若干次后来被证明是**无效对照** ——
包括 `source_id` 撞车那轮、以及 baseline 检索全失败那轮。**引用它们有被追问穿的风险。**

**当前可自证的实测值**（Golden Set 前 5 题，配对设计，`judge-rounds=1`）：

| 指标 | baseline（1 轮） | improved（2 轮） | 口径 |
|------|------|------|------|
| 研究完备性 | **0.70** | **0.75** | LLM-as-Judge 打分 |
| 幻觉率 | **0.32** | **0.34** | LLM-as-Judge 事实核查 |
| 引用准确率 | — | **0.6138** | 规则校验 + LLM-as-Judge 语义匹配 |
| 引用合法率 | — | **0.80** | 规则型：角标能否在来源表找到 |
| 引用覆盖率 | **0.3362** | **0.3693** | 规则型（**护栏指标**，非判别指标） |
| 端到端耗时 | 403s | 712s | 系统埋点计时 |

**引用时必须一起说的两条保留**（不说就是虚报）：
1. **n=5 偏小**，且该轮**检索被第三方限流污染**（失败率约 75%），
   故 improved 的 +0.05 应视为**下限**；
2. `citation_coverage` 有**结构性天花板 ≈ 50%**（未带角标句子中约 80% 是分析推演），

**建议的表述方式**：不说"我的系统完备性 89%"，而说
**"我建了一套配对评测，能测出改动前后的差异；当前样本下完备性 0.70 → 0.75"** ——
前者是报数字，后者是报方法，后者更能站住。

## 6. 慎用区：这些素材默认不讲

以下内容**不作为难点讲述**——它们的本质是"我的代码有缺陷然后我修好了"，讲出来会让面试官怀疑代码基本功。但它们在特定场景下有限可用。

### 6.1 默认不讲的素材

| 素材 | 为什么不讲 | 有限的可用场景 |
|------|-----------|----------------|
| 恢复接口返回结构无法区分三态，导致"继续"按钮失效 | 属于返回结构设计失误 | 若被追问"你怎么做状态设计"，可讲**"三态必须显式建模"**这条原则，但不讲 bug 本身 |
| 消息投递失败但仍被标记为已发送，导致补偿扫描失效 | 属于逻辑缺陷 | 讲备用难点六时，可把它作为**"发件箱模式的失败模式"**举例，一笔带过 |
| 命名空间写入/读取顺序写反、过滤函数零调用点、导入不存在的函数被 except 吞掉 | 属于接线错误 + 异常吞噬 | 若面试官主动问工程质量，讲**"我用 grep 调用点做断链审计"**这个方法论，不举具体例子 |
| 数据库生成列从未创建导致关键词召回静默降级 | 属于部署遗漏 | 同上 |
| `_condense_query` 把以疑问词开头的合法查询剥成空串 | 属于正则写错 | 可转化为**"每步剥离都要校验剩余长度"**这条防御规则，不讲 bug |
| `source_id` 用外层迭代号编址，内层重检时撞车导致证据重复率虚高到 41% | 属于设计缺陷 | 可转化为**"标识符的生成维度必须与被标识对象的生命周期一致"**，一笔带过 |
| 把 `mcp>=2.0` 装进项目环境，`starlette` 升到 1.6.0 把 FastAPI 搞坏 | 属于变更前未评估依赖影响 | 讲难点九时作为**"为什么必须用隔离环境"**的动机，不讲事故本身 |
| 排查 ddgs 时连续误判 5 次（代理干扰 TLS / 引擎封锁指纹 / 不读环境变量 / 不可用 / MCP 救不了） | 属于诊断方法不当 | ⭐ 这条**值得讲，但要放在"我形成了什么诊断纪律"里**：见难点八的反思句 |
| 测试里 `setenv("HTTP_PROXY")` 后又 `delenv("http_proxy")`，把刚设的值删掉 | 属于 Windows 环境变量大小写不敏感 | 可转化为**"环境变量操作在 Windows 上大小写不敏感"**的平台差异认知 |

### 6.2 如果面试官主动问"你怎么保证代码质量"

这时可以讲**机制**，不讲**事故**：

> 我有一条硬规则：**每一处 `except` 都必须回答两个问题——异常去哪了？调用方怎么知道？** 如果答不上来，就不许吞。
>
> 另外我做断链审计的手法是不看实现、看**调用点和写入点**：一个函数声称"我负责过滤低相关文档"，我不读它写得对不对，我去 grep 它**被谁调用了**——如果全仓零调用点，写得再漂亮也是死代码。同理，一个字段声称"由 XX 写入"，我就 grep 它的写入点。这套方法比通读实现快得多，而且结论**可证伪**。
>
> 项目里我沉淀了 33 个回归用例，**每一个对应一个已修复的缺陷**，保证同类问题不会二次出现。

**讲法要点**：主语是"我的规则"和"我的方法"，不是"我犯的错"。这三段话展示的是**质量意识和方法论**，而不是缺陷。

## 7. 一页速记卡（面试前 3 分钟看）

**开场**：多智能体深度研报系统（后端 12000 行）→ 四层架构 → **"它是有状态的长任务系统，流式/可中断/可取消/可恢复四件事必须同时成立"** → 抛钩子让面试官挑

**选材铁律**：**只讲客观约束下的设计，不讲自己写错的 bug**

**难点一（协议约束）**：`EventSource` 只支持 GET、不能带 body
→ 查询长（40+ 中文字符，URL 编码膨胀 9 倍）+ 敏感（会进 access log）
→ 代价：手写帧解析（`decoder.decode(..., {stream:true})` + `frames.pop()` 留半帧）、心跳（`: ping` 注释帧 15s）、重连（指数退避 + 判断该不该重连）
→ 反思：**放弃原生能力前，先数清楚要接手多少件事**

**难点二（异步语义）**：前端关连接 ≠ 后端停止
→ `task.cancel()` 是协作式的，只在 await 点生效
→ TaskRegistry（可寻址 + 409 去重）+ Redis Pub/Sub 多实例广播 + 前端乐观取消
→ 反思：**`cancel()` 是请求取消，不是执行取消**

**难点三（领域矛盾）**：向量检索三组互斥
→ 块小召回准 / 块大上下文全 → Parent-Child（父 2048 供上下文，子 512 出向量，命中扩父）
→ 向量弱于字面匹配 → 双路召回 + RRF（只用排名，免归一化）
→ 打分分母不能含"永不可能命中的词"（2/8=0.25 < 0.35）
→ 反思：**调参能解决说明没找到根因**

**难点四（模型缺陷）**：LLM 会编引用，prompt 治不了
→ 四重防御：登记 source_id → prompt 约束 → 生成后正则校验物理删除 → 覆盖率度量
→ 反思：**安全边界画在结果上，不画在信任上**

**难点五（并发 + 平台）**：
→ asyncio 单线程，同步调用拖死所有请求 → `asyncio.to_thread`
→ Windows Proactor 与 psycopg async 不兼容，卡死 30s → SelectorEventLoopPolicy + 启动校验
→ 反思：**写完协程先问"这里有没有同步调用"**

**备用**：发件箱一致性（跨系统无原子性）｜ 上下文窗口硬约束（滚动摘要 + 记忆双通道）

**三句反思句**：
1. 放弃原生能力前，先数清楚要接手多少件事。
2. `cancel()` 是请求取消，不是执行取消。
3. 调参能解决的问题，往往说明还没找到根因。

**没准备过的问题**：先说"没遇到过"，然后讲"我会先确认：约束是规范层还是实现层、常规方案为什么失效、代价能不能被隔离"。
