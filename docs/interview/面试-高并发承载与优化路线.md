# 面试专题：上万用户并发承载与优化路线

> 对应问题：「如果有上万个用户正在同时使用你的系统，你这个系统怎么能扛住这么高的并发？或者说你后面有怎么优化的思路？」
>
> **使用说明（诚信边界）**
> - 本文所有瓶颈定位均标注了可自证的代码位置或库源码位置，面试现场可打开编辑器自证。
> - 所有性能数字为**基于架构参数的推算**，不是压测实测值。文中已明确区分「实测」与「推算」，请勿把推算当实测讲。
> - 本系统**未做过压测**，也未在生产环境跑过多副本。任何"能扛多少"的表述都应带这个前提。
> - 本文只讲客观约束导致的瓶颈，不讲代码缺陷类问题。

---

## 第 0 章：先拆题——「一万用户」不是「一万 QPS」

这是这道题的第一道分水岭。**如果直接回答"加机器/加缓存"，说明没有理解这个系统的负载形状。**

本系统与普通 Web 系统的根本差异：

| 维度 | 普通 Web 系统 | 本系统 |
|------|--------------|--------|
| 单请求时长 | 毫秒~百毫秒 | **分钟级**（10 节点、多轮 LLM 调用） |
| 连接性质 | 短连接，请求-响应 | **SSE 长连接**，全程保持 |
| 单请求成本 | 一次 DB 查询 | **20~30 次 LLM 调用** |
| 瓶颈位置 | 数据库 / 带宽 | **LLM 配额 / 串行化资源** |

### 换算口径

设 1 万在线用户，按 5% 同时发起研究任务（经验值，可现场说明是假设）：

| 指标 | 推导 | 量级 |
|------|------|------|
| 并发研究任务 | 10000 × 5% | **500 个** |
| 常驻 SSE 连接 | 每个任务 1 条，平均 3 分钟 | **500 条**（若 1 万人都在看，则 1 万条） |
| LLM 调用速率 | 500 × 25 次 ÷ 180 秒 | **约 70 次/秒** |
| checkpoint 写入速率 | 500 × 13 次 ÷ 180 秒 | **约 36 次/秒** |
| 搜索 query 速率 | 500 × 5 ÷ 180 秒 | **约 14 次/秒** |

**关键结论**：这个系统的"并发"压力不在 HTTP 层，而在**两个串行化资源**（checkpoint 连接、线程池）和**一个外部配额**（LLM API）。

> 如果面试官问的是"1 万用户**同时点下按钮**"，那答案很直接：当前架构不可能扛住，必须改成任务队列架构。要主动区分这两种口径，而不是含糊回答。

## 第 1 章：当前架构会按什么顺序崩

### 瓶颈 1：checkpoint 写入是全局串行的（最硬的结构性天花板）

**现象**：所有并发任务的 checkpoint 读写排队在同一条 PG 连接、同一把锁上。

**证据链（可现场打开自证）**：

1. `app/mult_agents/runtime.py:80` — 项目这样创建 checkpointer：
   ```python
   _checkpointer_context = AsyncPostgresSaver.from_conn_string(config.postgres_dsn)
   ```

2. `langgraph/checkpoint/postgres/aio.py:73` — `from_conn_string` 内部建的是**单条连接**，不是连接池：
   ```python
   async with await AsyncConnection.connect(
       conn_string, autocommit=True, prepare_threshold=0, row_factory=dict_row
   ) as conn:
   ```

3. `langgraph/checkpoint/postgres/aio.py:363` — 所有 DB 操作统一走 `_cursor()`，而 `_cursor()` 第一句就是抢全局锁：
   ```python
   async with self.lock, _ainternal.get_connection(self.conn) as conn:
   ```

4. `langgraph/checkpoint/postgres/aio.py:51` — 这把锁是**实例属性**，一个实例一把锁：
   ```python
   self.lock = asyncio.Lock()
   ```

**客观约束归因（关键）**：这不是代码写错，是 langgraph 的**设计约束**。单条 `AsyncConnection` 在 psycopg 中不支持多协程并发使用，库必须加锁串行化。构造器其实接受连接池（`aio.py:44` 有 `isinstance(conn, AsyncConnectionPool)` 分支），但**锁依然存在**——传入池只是把"单连接排队"变成"池内取连接 + 仍然抢同一把锁"。

**这意味着**：checkpoint 吞吐的绝对上限 = 1 / 单次写入耗时，与并发数无关。按单次写入 5~10ms 估算，上限约 **100~200 次/秒**。36 次/秒的推算需求看似有余量，但它是**单点**——任何一次慢查询、任何网络抖动，会线性拖慢**所有**并发任务，没有隔离。

**追问防御**："为什么不用 Redis checkpointer？" —— 项目已实现降级链（`runtime.py:91` 有 `AsyncRedisSaver` 分支），但 Redis checkpointer 同样有串行化约束，且持久化与查询能力弱于 PG。换存储不解决串行问题。

---

### 瓶颈 2：默认线程池只有 12 个槽位

**现象**：搜索、RAG 检索、向量化全部抢同一个线程池，池子大小由 CPython 默认策略决定。

**证据链**：

1. 全仓 grep `ThreadPoolExecutor` / `set_default_executor` — **零命中**，说明没有自定义 executor。
2. 项目共有 4 处 `asyncio.to_thread`：
   - `app/mult_agents/nodes/web_search.py:47` — Web 搜索
   - `app/mult_agents/tools.py:84` — ddgs provider
   - `app/mult_agents/tools.py:155` — SearXNG provider
   - `app/mult_agents/nodes/local_rag.py:42` — 本地向量检索

**客观约束归因**：`asyncio.to_thread` 使用事件循环的默认 `ThreadPoolExecutor`，其 `max_workers = min(32, (os.cpu_count() or 1) + 4)`（CPython 标准库策略）。8 核机器 → **12 个线程**。这是语言运行时的既定行为，不是配置疏忽。

**算一下**：14 次/秒的搜索需求 × 每次约 2 秒（ddgs 走公网） = **需要 28 个并发槽位**，但只有 12 个。搜索请求会排队，而排队直接体现为**用户端 SSE 卡顿**（因为搜索在关键路径上）。

**注意一个隐藏的放大效应**：`web_search_node` 内部是 `for query_index, item in enumerate(queries)` **串行循环**（`web_search.py:40`），每个 query 一次 `to_thread`。也就是说一个任务会**多次占用**槽位。500 并发任务 × 5 query，槽位争抢远比 14 次/秒的表面数字激烈。

---

### 瓶颈 3：上传路径同步阻塞整个事件循环（杀伤最大、修复最便宜）

**现象**：一个用户上传文档，**同进程所有 SSE 流全部停摆**。

**证据链**：

`app/backend/router/document_router.py:84-89`：
```python
content = await _read_within_limit(file)
result = service.upload_and_ingest(      # ← 同步调用，没有 to_thread
    file_content=content,
    filename=filename,
    user_id=current_user.user_id,
)
```

`upload_and_ingest`（`document_service.py:173`）内部全同步：MinIO 上传 → 文档解析切块 → PG 三表事务写入 → MQ 投递。

**客观约束归因**：MinIO Python SDK 与各文档解析库（pdf/docx loader）**本身只有同步实现**，生态里没有成熟的异步替代。所以"在 async 路由里调用同步库"是一个必须显式处理的边界——处理方式就是把整段挪进线程池。

**为什么说它杀伤最大**：文件上限 20MB（`MAX_FILES_PER_BATCH`/`MAX_FILE_SIZE_BYTES`），解析 + 切块耗时在**数百毫秒到数秒**。这段时间内 asyncio 单线程无法切换，500 条 SSE 流的心跳都会延迟，前端会误判连接断开。**一个用户的正常操作，能让所有人卡住。**

**为什么说修复最便宜**：改成 `await asyncio.to_thread(service.upload_and_ingest, ...)` 即可，一行。**这是投入产出比最高的一项优化。**

---

### 瓶颈 4：PG 连接总数封死了 worker 数量

**现象**：单进程连接池合计已占 PG 连接数的 1/4，"加 worker"这条路走不了几步。

**证据链**（单进程连接池清单）：

| 来源 | 配置 | 位置 |
|------|------|------|
| 业务 Repository 池 | `min_size=2, max_size=10` | `postgres_client.py:195-197` |
| ChunkRepository 池 | `min_size=1, max_size=5` | `postgres_client.py:716-718` |
| PostgresStore 池 | `min_size=2, max_size=10` | `store_client.py:72` |
| checkpointer | 单连接（见瓶颈 1） | `runtime.py:80` |
| **合计** | **约 26 条** | |

**客观约束归因**：PostgreSQL 的 `max_connections` 是**服务端全局资源**（默认 100），连接数与内存成正比，不能无限开。这是分布式系统的资源守恒约束——每个副本都要占一份，副本数 × 每副本连接数 ≤ 服务端上限。

**推论**：`100 ÷ 26 ≈ 3.8`，即**最多 3~4 个 worker 就把 PG 连接打满**。而瓶颈 1 的解法恰恰是"多 worker 摊薄串行锁"——**两个瓶颈互相锁死**。要水平扩展，必须先做连接收敛（PgBouncer）或提高 `max_connections`。

---

### 瓶颈 5：LLM API 配额——唯一无法靠架构解决的

**现象**：约 70 次/秒的 LLM 调用需求，超出典型商用 API 的默认配额。

**客观约束归因**：这是**外部服务的商务配额**，不是技术问题。加机器、加缓存、改架构都无法突破。只能通过**减少调用量**或**提升配额**解决。

**这一类瓶颈在面试中最有价值**——因为它证明你理解"架构能力有边界，边界外的事要靠需求侧解决"。

**当前系统的放大因素**（可主动交代）：10 个节点各自独立调用 LLM，且 `reflect` 循环最多 3 轮（`config.json` 的 `max_iterations: 3`），意味着最坏情况下 LLM 调用次数是线性的 3 倍。

---

### 附带：一个必须先修的正确性问题

**TaskRegistry 的并发判定是进程内的**，多 worker 后会失效。

`app/backend/service/task_registry.py:64`：
```python
self._tasks: dict[str, RunningTask] = {}
```

`app/backend/router/research_router.py:120-125`：
```python
registry = get_task_registry()
if registry.is_running(payload.thread_id):     # ← 只查本进程字典
    raise HTTPException(status_code=409, ...)
```

**后果**：多 worker 下，同一个 thread 的两个请求落到不同 worker，**两边都通过 409 检查**，会同时跑同一个 thread → 两个 graph 同时写同一份 checkpoint → 状态互相覆盖。

**注意**：Redis 里其实已经写了标记（`task_registry.py:110` 的 `cancel:{thread_id}`），但**只用于取消兜底，没有被用于并发判定**。要水平扩展，必须先把这里改成 Redis 原子 `SET NX` 抢锁。

这个点回答得好会加分：它说明你想到了"水平扩展不只是性能问题，还是正确性问题"。

## 第 2 章：优化路线（分四阶段，按投入产出比排序）

### 阶段 0：消除不该有的阻塞（成本最低，收益最大）

| 动作 | 位置 | 预期收益 |
|------|------|---------|
| 上传路径改 `to_thread` 卸载 | `document_router.py:85` | 消除最大的事件循环阻塞源 |
| 为 `to_thread` 配专用 executor | `app_main.py` lifespan 内 `loop.set_default_executor(...)` | 线程池从 12 提升到 64+，且与 CPU 密集任务隔离 |
| 后台记忆提取加背压 | `memory_service.py:165` 的 `create_task` | 当前 fire-and-forget **无上限**，高并发下会堆积大量 LLM 任务 |
| `web_search_node` 的 query 循环改并发 | `web_search.py:40` 的 `for` 循环 | 单任务内 5 个 query 从串行改 `asyncio.gather`，关键路径缩短 |

**这一阶段不改架构、不动部署，是回答"你后面怎么优化"时最该先讲的。**

### 阶段 1：拆串行锁（需要动部署）

1. **checkpointer 改用池模式**：`AsyncPostgresSaver(pool)` 替代 `from_conn_string`。
   - **必须说清**：锁仍在（`aio.py:363`），收益只是"连接不复用单条"，**不是银弹**。
   - 诚实的表述是"这一步收益有限，真正的解法在下一步"。
2. **多 worker / 多副本**：每个进程独立 checkpointer 实例，串行度被 N 摊薄。
   - **前置条件**：先修好上面的 TaskRegistry 跨进程判定，否则会出正确性 bug。
3. **PG 连接收敛**：前置 PgBouncer（transaction 模式），或把 `max_connections` 提到 500+。

### 阶段 2：接入层无状态化

1. `--workers N` 或 K8s 多副本（当前 `Dockerfile:62` 是 `--workers 1`）。
2. 网关层做 SSE 连接收敛；`X-Accel-Buffering: no` 响应头已具备（`research_router.py:142`）。
3. 前端 SSE 走 HTTP/2 —— 浏览器对同域 HTTP/1.1 有 **6 连接上限**，这是前端的硬约束。

### 阶段 3：削 LLM 调用量（唯一能突破瓶颈 5 的方向）

1. **合并节点调用**：10 个节点各自调 LLM，`web_search` 的"整理证据"和 `analyze` 有语义重叠，可合并。
2. **分级降级**：高峰期把 `qwen-plus` 降到 `qwen-turbo`，或跳过 `reflect` 循环（`config.json` 的 `hitl_enabled` / `max_iterations` 已是热配置，可动态调）。
3. **准入控制 + 排队**：加全局 `asyncio.Semaphore`，超过阈值直接返回"当前繁忙"，**而不是让所有人一起慢**。当前系统完全没有这个机制。
4. **结果级缓存**：ddgs 已有 Redis 缓存（`tools.py:74-94`，TTL 3600s），可把缓存粒度从"搜索结果"上移到"相似 query 的完整报告"。

### 阶段 4：架构级重构（真要做到 1 万并发才需要）

把"研究任务"从 **HTTP 长连接** 改成 **任务队列 + 状态订阅**：

```
现在：  客户端 ──SSE 长连接──> FastAPI（执行 + 流式）        ← 接入与执行耦合
目标：  客户端 ──SSE 订阅状态──> FastAPI（只接单 + 转发）    ← 无状态，可无限扩展
                    │
                    └──> 任务队列（Celery/Arq）──> Worker 池（按队列长度弹性伸缩）
```

- API 层完全无状态 → 可无限水平扩展
- 执行层与接入层解耦 → 独立伸缩，故障隔离
- **代价（必须讲）**：失去"token 级流式"的实时感，前端交互需要重做（改为订阅进度事件）；项目现有的 10 种事件协议需要重新设计流式边界。

## 第 3 章：诚实结论

**当前架构能扛多少？**

按现在的实现，单进程可稳定支撑的并发研究任务量级在**几十个**，不是几百个。瓶颈是 checkpoint 串行锁 + 线程池 12 槽位。

**到 1 万用户需要什么？**

| 层面 | 需要做的事 |
|------|-----------|
| 架构 | 从"单进程 async"改成"无状态 API + 任务队列 + 多副本 worker" |
| 中间件 | PgBouncer 连接收敛、PG 提配、Redis 承担跨进程并发判定 |
| 外部 | 买够 LLM 配额（这是硬成本，无法用技术绕过） |
| 前端 | SSE 走 HTTP/2，交互模型从"流式等待"改成"任务订阅" |

**这不是优化，是接入层重写。** 说清楚这一点，比含糊地说"我们会做水平扩展"更有说服力。

## 第 4 章：话术版本

### 60 秒版

> 这个系统跟普通 Web 系统不一样：一次研究请求是分钟级的，占用一条 SSE 长连接、二三十次 LLM 调用，所以不能用 QPS 的视角看。我会先把"一万用户"拆成实际负载——按 5% 同时发起算，是 500 个并发任务，折算下来约 70 次/秒的 LLM 调用和 36 次/秒的 checkpoint 写入。
>
> 按这个量算，当前架构会按顺序崩在四个地方：第一是 LangGraph 的 checkpoint 写入，库本身用单连接加全局锁，所有并发任务的 checkpoint 是串行的；第二是 asyncio 默认线程池只有 12 个槽位，搜索和 RAG 全抢这一个池子；第三是文档上传在 async 路由里同步跑，一个用户传文件会让整个进程的 SSE 流停摆；第四是 PG 连接数，单进程就占了 26 条，最多撑 3 到 4 个 worker。
>
> 优化我会分四步：第一步最低成本——把上传挪进线程池、给 to_thread 配专用 executor、后台任务加背压；第二步多 worker 摊薄 checkpoint 串行度，但前置要先修 TaskRegistry 的跨进程并发判定，否则会出正确性 bug；第三步接入层无状态化；第四步如果真要做到一万并发，得把长连接改成任务队列加状态订阅，API 层才能无限扩展。
>
> 还有一个瓶颈是买不来的——LLM 的 API 配额。这个只能靠减少调用量解决，比如合并节点、高峰期降级模型、加结果级缓存。

### 180 秒版（展开用）

在 60 秒版基础上，每个瓶颈补三件事：**代码位置**（可现场自证）、**客观约束归因**（为什么不是写错）、**量化影响**（算给面试官看）。参考第 1 章。

## 第 5 章：追问防御

| 追问 | 回答要点 |
|------|---------|
| "你怎么知道是 checkpoint 瓶颈？压测过吗？" | **必须诚实**：没压测过，这是**读库源码得出的结构性推断**——`aio.py:363` 的全局锁是确定的事实，不是猜测。要补压测才能给准确数字。 |
| "换成 Redis checkpointer 不就解决了？" | 不解决。Redis checkpointer 同样有串行化约束（单连接语义），且持久化/查询能力弱于 PG。串行是"checkpoint 语义需要有序写入"带来的，不是 PG 特有的。 |
| "为什么不上 Celery？" | 已经是演进方向（阶段 4），但它是架构级改动，会牺牲 token 级流式体验。要按量级决策——当前量级不值得付这个代价。 |
| "加机器不就行了？" | 三个理由不行：checkpoint 锁是进程内串行，加机器只在多副本时有效；PG 连接数是全局资源，加副本会先打满 PG；LLM 配额是外部商务约束，加机器无效。 |
| "你说的这些优化，做了几个？" | **诚实回答**：都还没做，这是优化路线不是已完成项。当前部署是单 worker（`Dockerfile:62`）。 |
| "那你怎么保证现在能用？" | 当前定位是单租户/小规模场景，几十个并发任务的量级下这些瓶颈都还没触发。架构里已经预留了多副本能力（Redis Pub/Sub 取消广播、崩溃恢复扫描），只是没启用。 |
| "1 万条 SSE 连接本身扛得住吗？" | Python asyncio 处理万级空闲连接是可行的（每条连接内存开销在几十 KB 量级），但**活跃流**的写入才是压力点。真正的约束是上游 Nginx 的 `worker_connections` 和浏览器端 HTTP/1.1 的 6 连接上限。 |

## 第 6 章：一页速记卡

```
【拆题】1 万用户 ≠ 1 万 QPS
  → 5% 同时发起 = 500 并发任务
  → 70 次/秒 LLM ｜ 36 次/秒 checkpoint ｜ 14 次/秒 搜索

【崩溃顺序】
  1. checkpoint 串行锁   runtime.py:80 + aio.py:363（库设计，非写错）
  2. 线程池 12 槽位      无自定义 executor，min(32, cpu+4)
  3. 上传阻塞事件循环     document_router.py:85（修复最便宜）
  4. PG 连接数 26/100    最多 3~4 worker
  5. LLM 配额            外部硬约束，加机器无效

【优化四阶段】
  0. to_thread 卸载 + 专用 executor + 背压       ← 先讲这个
  1. 多 worker 摊薄锁（前置：修跨进程并发判定）
  2. 接入层无状态化 + HTTP/2
  3. 削 LLM 调用量（合并/降级/缓存/排队）
  4. 长连接 → 任务队列 + 状态订阅（架构级，讲代价）

【必答的诚实点】
  · 没压测过，瓶颈是读库源码的结构性推断
  · 当前部署单 worker，优化路线尚未落地
  · 一万并发是接入层重写，不是调优

【加分点】
  · 水平扩展不只是性能问题，还是正确性问题（TaskRegistry 跨进程判定）
  · LLM 配额是唯一买不来也优化不掉的瓶颈
```
