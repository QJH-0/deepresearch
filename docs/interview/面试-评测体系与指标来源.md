# 面试专题｜评测体系：数据集从哪来、指标怎么测、结论凭什么可信

> 这份文档回答一类高频追问：**「你简历上写的这些指标，是怎么测出来的？数据从哪来的？」**
>
> 面试官问这句话时，真正在考三件事：
> 1. 你的**数据集**是自己编的还是有构造依据；
> 2. 你的**指标**是拍脑袋还是有定义、能复现；
> 3. 你的**结论**有没有被「对照不成立」污染过 —— 这一条最容易露馅。
>
> 选材原则同 `面试-最满意项目与难点攻克.md`：**难点必须来自客观约束，不能来自自身疏忽。**

---

## 1. 数据集怎么构造

### 1.1 为什么必须有 Golden Set

做优化（自适应检索、多轮研究、查询策略）必须回答「到底变好还是变坏」。
LLM 应用没有单元测试那种确定性的对错，**没有固定题集就没有可比性** ——
同一处改动，换一道题就可能得出相反结论。

所以第一步不是改代码，而是先把「拿什么测」固定下来。

### 1.2 结构

`app/test/golden_set.json`，**50 道题**，改 JSON 即可增删题、不必动 Python：

| 字段 | 说明 |
| --- | --- |
| `query` | 调研问题原文 |
| `type` | `multiagent`（走完整研报链路，30 题）\| `direct`（直答快路径，20 题） |
| `key_points` | 期望报告覆盖的要点 —— **本文件的核心** |
| `expected_sources` | 可选。期望被引用的来源（域名/URL 片段）。留空则该题不计入来源召回指标 |

两类题分开统计，因为它们的评价维度不同：`multiagent` 看报告质量，
`direct` 看响应时延。

### 1.3 `key_points` 的判别力要求（这里踩过坑，也是最能讲的点）

**教训**：最初的要点写成「框架名 + 通用概念」（`LangGraph` / `状态机` / `工具调用`），
结果**连只跑 1 轮迭代的 baseline 都拿满分** —— 指标触顶，测不出任何改进。

好要点必须满足：**只有真正找到并读懂正确来源才可能命中**。

```
✅ 「LangGraph 用 checkpointer 支持断点续研」   ← 需要读到具体机制
✅ 「AutoGen v0.4 重构为异步 actor 模型」       ← 需要读到具体版本变更
❌ 「LangGraph」                                ← 提到名字就得分
❌ 「多智能体」                                  ← 任何一篇都写
```

建议每题 4–6 条，其中至少一半是「具体机制 / 版本 / 数字 / 对比结论」。

> **面试话术**：「评测集的关键不是题目数量，是**要点的判别力**。
> 我一开始也栽在这上面——要点写成通用概念，两个版本都满分，指标完全失去分辨力。
> 后来定了条规则：要点必须是**只有读懂正确来源才可能命中**的具体机制或数字。」

### 1.4 为什么 `expected_sources` 是可选的

来源召回是「检索召回的底线」，但**需要人工标注**（知道这个领域该引哪些站）。
不是所有题都值得标，所以设计成可选：**留空则该题自动不计入该指标的聚合**，
避免用空值稀释分母。

## 2. 指标怎么算：两层设计

### 2.1 规则型层（`app/mult_agents/eval_metrics.py`）

**纯函数、零外部依赖、可离线单测。** 定位是**回归哨兵**——
改一处代码后立刻能看出证据有没有变脏、检索有没有变浅、引用有没有失效。

| 指标 | 回答的问题 |
| --- | --- |
| `evidence_duplication_rate` | State 里有没有重复证据堆积（reducer 语义是否正确） |
| `retrieval_rounds` | 检索深度是多少（自适应检索是否生效） |
| `citation_legality` | 正文引用角标是否都能在来源表里找到 |
| `citation_coverage` | 引用密度（**护栏指标**，见 §3.3） |
| `key_point_coverage` | 报告字面覆盖了多少期望要点 |
| `expected_source_recall` | 期望来源是否真被引用（需人工标注） |

**关键取舍**：规则型指标会**低估同义表述**（要点写「状态机」而报告写「有向图」，
字面匹配不到）。所以它**不替代语义评估**，只作为「改动是否引入退化」的快速哨兵。
这个边界要主动讲出来 —— 面试官最想听的就是你知不知道自己指标的局限。

### 2.2 LLM-as-Judge 层（`app/test/eval_metrics.py`）

需要真实模型，做语义级评估：完备性、幻觉率、引用准确率。

**核心问题：LLM 判官本身不确定。** 同一个报告判两次可能给不同分。

**方案：多轮取中位数。**

```python
def judge_with_consensus(judge_func, judge_llm, *args, rounds=3):
    scores = [judge_func(judge_llm, *args)["score"] for _ in range(rounds)]
    median = sorted(scores)[len(scores) // 2]
    return next(r for r in results if r["score"] == median)
```

**轮数是成本旋钮**：正式跑用 3 轮求稳，跑大样本时降到 1 轮。

> **面试话术**：「LLM 判官是不确定性的来源，所以我不取单次结果，
> 而是多轮取中位数。轮数是可调的——小样本求稳用 3 轮，大样本为了跑得完用 1 轮，
> 这是**统计稳定性与成本之间的显式取舍**。」

### 2.3 为什么要分两层

| | 规则型 | LLM-as-Judge |
| --- | --- | --- |
| 成本 | 零（纯函数） | 每指标每次调用模型 |
| 确定性 | 完全确定 | 不确定，需多轮共识 |
| 语义能力 | 弱（同义表述会漏） | 强 |
| 用途 | **快速回归哨兵** | **质量终评** |

改代码时先跑规则型（秒级、免费）判断有没有退化，再跑 LLM-as-Judge 做终评。
**不混用**：规则型分数不能当质量结论，只能当报警器。

## 3. 怎么保证「对照」真的成立（最能体现方法论的部分）

### 3.1 配对设计

同一批题、同一套 key_points，跑两组配置：

- **baseline**：`max_iterations=1`（单轮检索 + 成文）
- **improved**：`max_iterations=2`（自适应重检 + 多轮研究）

同题两配置 → **抵消题目难度差异**，差异归因于配置。

### 3.2 ⭐ 对照有效性守卫：`retrieval_health`

**这是本次最值得讲的方法论改进。**

**客观约束**：评测要对比「改动前 / 改动后」，但两次运行之间的**外部依赖可用性不受控**
—— 搜索引擎可能超时、限流、被封。

**真实事故**：某一轮评测里，baseline 阶段的 20 次 web 检索**全部失败**（拿到 0 条证据），
而 improved 阶段拿到 18 条。两阶段的**检索条件根本不同**，
指标差异无法归因于代码改动。但**从报告 JSON 上看不出来** ——
只会看到「baseline 引用覆盖率低」，很容易被误读成「改动有害」。

**方案**：把「对照是否成立」变成机器判定，而不是靠人盯日志。

```python
def _web_yield(results):
    queries = sum(web_query_count)
    kept = sum(web_kept_count)
    return {
        "yield_rate": kept / queries if queries else None,
        "degraded": bool(queries) and kept == 0,   # 检索过但一条没拿到
    }
```

输出进摘要：

```json
"retrieval_health": {
  "baseline": {"web_queries": 20, "web_kept": 0, "yield_rate": 0.0, "degraded": true},
  "improved": {"web_queries": 28, "web_kept": 18, "yield_rate": 0.6429, "degraded": false},
  "degraded_phases": ["baseline"]
}
```

`degraded_phases` 非空时，控制台直接打印「**本轮对照无效：baseline 阶段一条 web 证据都没拿到**」。

**一个容易忽略的细节**：「没检索过」与「检索全失败」必须区分 ——
前者 `yield_rate` 为 `None`、不报 degraded；否则空跑的阶段会误报。

> **面试话术**：「我加了对照有效性守卫。因为评测里最容易犯的错不是算错指标，
> 而是**在两组条件不同的情况下比较指标**。搜索引擎是外部依赖，可用性不受我控制，
> 所以我把『产出率为 0』变成显式的机器判定，而不是靠人去看日志里有没有报错。
> 这个守卫后来真的拦下了一轮无效对照。」

### 3.3 ⭐ 指标天花板识别：`citation_coverage`

**约束**：任何度量都有**量程**。当被测对象的得分接近量程上界，指标失去分辨力。

**现象**：baseline 与 improved 的引用覆盖率几乎不动（52.0% vs 53.0%），
而报告长度和带角标句子数都在涨。

**排查方法**：把完整报告落盘（原先只存 500 字预览），**逐句分类**未带角标的句子。

| 类型 | 句数 |
| --- | --- |
| 标题/小标题 | 13 |
| 过渡与总结（综上/因此/首先…） | 7 |
| 有数据/事实但无角标 | 5 |
| **分析推演** | **35** |

「分析推演」的真实样本：

```
- 这种分布式协作模式不仅提高了任务处理的并行度，还通过相互校验机制提升了可靠性
- 第三，记忆机制从无状态向有状态持久化升级
```

**这些句子本就不该带角标** —— 是报告自己的综合、推断与结构标记，不指向任何单一来源。
一篇深度研报必然包含大量这类论述。

**结论：~50% 是结构性天花板，不是检索缺陷。** 该指标降级为**护栏指标**
（骤降说明链路故障，但不能衡量检索深度）。

**⭐ 这里还有一个「推翻自己」的细节，讲出来很加分**：
我此前用「代理故障那轮 28.4% → 修复后 62.1%」论证它「对检索质量高度敏感」。
**那个判断是错的** —— 那次跨越测的是「**有没有证据**」，不是「**检索有多深**」。
两者被混为一谈。修正后才定位到它的真实性质。

> **面试话术**：「指标不是算出来就完了，还得知道它的**量程在哪**。
> 我用逐句分类证明了引用覆盖率有结构性天花板——未带角标的句子里约 80% 是分析推演，
> 本就不该带角标。所以它只能当护栏指标，不能用来衡量检索深度。
> 顺带说，我一开始还误判过它——把『有没有证据』的差异当成了『检索深度』的差异，
> 后来做逐句分类才发现。」

### 3.4 指标互相矛盾时怎么办（真实案例，很好的追问素材）

某一轮 n=1 的结果：**完备性 improved 更好（0.9167→1.0），但幻觉率 improved 差了 9 倍**
（0.0333→0.3）。两个指标指向相反。

**处理**：不下结论、不回退代码，**先扩样本**。

扩到 5 题后：幻觉率 **0.32 vs 0.34，基本持平** —— **那个「恶化 9 倍」是 n=1 的方差**。

> **面试话术**：「指标互相矛盾时，我不会挑一个支持我结论的用。
> 我遇到过一次：单题测出来幻觉率差 9 倍，差点就去调提示词了。
> 扩到 5 题之后发现是方差 —— **n=1 时噪声和信号分不开**。
> 这件事之后我给自己定了个规矩：单题结果只用来发现异常，不用来下结论。」

## 4. 面试官追问与答法

**Q1：这些指标是行业标准吗？**

不全是。引用合法性、证据重复率是**针对本项目架构**设计的（对应 reducer 语义、
引用链路），不是通用指标。完备性、幻觉率这类是业界常用的 LLM-as-Judge 维度。
**我在选指标时的原则是：每个指标必须能回答一个具体的工程问题**，
不能回答问题的指标不加。

**Q2：为什么不用 RAGAS 这类现成框架？**

两个原因：一是我的核心指标（证据重复率、引用合法性）对应的是**本项目的 State 语义**，
通用框架没有；二是我需要**零依赖、可离线跑**的哨兵层，现成框架大多要起模型或中间件。
不过语义层我是用 LLM-as-Judge 的思路，和 RAGAS 的做法一致。

**Q3：50 道题够吗？怎么保证代表性？**

**不够，这是当前明确的短板。** 50 题是「改动前后可比」的最小集合，
不是统计意义上充分的样本。而且我实际只跑了前 5 题 —— n=5 仍然偏小，
只够排除明显的方差（比如那个 9 倍的幻觉率差异）。

**面试里主动说这个短板比被问出来好。** 补法是：把 Golden Set 扩到能覆盖
不同领域/难度分层，并且每题至少跑 3 次取分布而不是单次。

**Q4：LLM-as-Judge 本身不可靠，你怎么信它？**

不完全信。三条约束：
① **多轮取中位数**，不取单次；
② 判官只用于**语义维度**（完备性、幻觉率），能用规则算的绝不用判官；
③ 判官结果与规则指标**交叉验证** —— 两者背离时以规则型为准（规则型是确定的）。

**Q5：规则型指标会不会误判？比如同义表述。**

会，而且我在代码注释里明确写了这个局限：
「规则型指标会低估同义表述（要点写『状态机』而报告写『有向图』），
因此**不替代语义评估**」。所以我把它定位成**哨兵**而不是结论 ——
它的价值是「分数掉了说明一定有问题」，而不是「分数高说明一定好」。

**Q6：这些数字能复现吗？**

能。三个条件：
① 题集是版本化的 JSON 文件；
② 每组结果的原始 JSON 与**完整报告正文**都落盘（`output/eval_reports/`）；
③ 每个指标都有单元测试，含**人为漂移验证**（故意改坏实现，确认断言会失败）。

**Q7：如果重做，你会改什么？**

三件事：
① **扩样本 + 重复测量**，而不是单次 n=1；
② **修 `key_points` 的判别力** —— 现在有一半题目的要点还是通用概念，指标会触顶；
③ 把「对照有效性」的检查做得更前置 —— 现在是我事后加的守卫，
应该在**跑之前**就检查环境（比如先探一次搜索引擎可用性）。

## 5. 本次改动可写入「难点攻克」的清单

以下每条都用 **STAR-C**：**C（客观约束）前置 → 方案 → 代价与取舍**。

### 难点 A：传递依赖的版本漂移，让整条检索链路静默失效

**C — 客观约束**：
`requirements.txt` 只能声明**直接依赖**（`ddgs>=9.0`），而真正发起网络请求的是
**传递依赖** `primp`。传递依赖的版本不在声明范围内，环境重建时可能落到有 bug 的补丁版本。
更麻烦的是**失效的表现形式具有误导性** —— 报错是 TLS 层的
（`cannot decrypt peer's message` / `tls handshake eof`），指向网络或代理，
而真因在依赖版本。

**A — 方案**：
用 `uvx` 起同一个包 —— uv 会为它建**隔离环境**并装最新依赖，
等于**免费拿到一个「干净对照组」**。同一条调用在对照组里成功、在项目环境里失败，
就把问题锁定到了依赖版本。

**对比实验（同一 ddgs 9.16.0，仅 primp 版本不同）**：

| primp | 结果 |
| --- | --- |
| 2.0.0 | `DDGS(proxy=…).text()` **连跑 6 次全失败（0/6）** |
| 2.0.1 | **3/3 成功**，每次 2.6–4.0s |

**C — 代价与取舍**：
- 修复只是补一行 `primp>=2.0.1`，但**诊断成本远高于修复成本**；
- 我把教训固化成规则：**连续 `0/N` 失败时，先把依赖版本对齐到「已知可用」的对照组，
  再怀疑网络与配置**。这次我先后误判为「代理干扰 TLS」「引擎封锁指纹」，
  全错 —— 就是跳过了这一步。

### 难点 B：同一 Python 环境里两个库对底层包版本互斥

**C — 客观约束**：
`ddgs` 的 MCP 模式要求 `mcp>=2.0`；而 `mcp 2.x` 会把 `starlette` 拉到 `1.6.0`，
项目的 `fastapi 0.123` 要求 `starlette<0.51`。**Python 没有依赖隔离机制**，
同一个环境里这两个约束无法同时满足 —— 实测后果是
`TypeError: Router.__init__() got an unexpected keyword argument 'on_startup'`，
**后端直接不可用**。

**A — 方案**：
不把 MCP 依赖装进项目环境，改为**用 `uvx` 把 MCP 服务器作为子进程启动**，
通过 MCP 协议通信。`uv` 自动为子进程建隔离环境，项目环境零影响。

**C — 代价与取舍**：
- 代价：多一层进程间通信、多一个配置文件、uv 缓存未预热时启动慢（实测首次约 1 分钟）；
- 取舍：**值得** —— 换来的是项目依赖树不被污染；
- 反向印证：在 SpringAI 里用同一个 MCP server 完全没这个问题，
  因为那边它天然就是独立进程。**这是 Python 生态特有的约束。**

### 难点 C：外部搜索引擎的速率限制 vs 内部的检索计划

**C — 客观约束**：
第三方搜索引擎有**速率限制**，这是不可协商的外部约束。
而「自适应检索」的设计目标恰恰是**多轮 + 每轮多查询** ——
一次研究实测发出 **17–44 次**请求。两者天然冲突。

**现象**：连续请求实测 **无间隔 15 次只成功 2 次**（前 2–3 次成功后急剧退化）；
评测里两阶段失败率均约 **75%**（baseline 76/102、improved 126/167）。
更隐蔽的是**它对结论的污染**：improved 做更多检索 → 触发更强限流 →
产出率反而更低（0.745 → 0.371），**优化带来的收益被外部限流吃掉了**。

**A — 方案**：
模块级节流器（锁 + 时间戳），保证两次请求至少间隔 1.5s。
用**模块级而非实例级**，因为并发检索时也要保证只有一个请求在飞。
加间隔后 12 次里成功 6 次（从 2/15 提升）。

**C — 代价与取舍**：
- 代价：串行化会拉长总耗时（1.5s × N 次查询）；
- 取舍：**用时间换成功率** —— 检索失败导致的证据缺失，代价远高于多等几秒；
- 未解：1.5s 仍不够（6/12），还可加大间隔、启用结果缓存、或减少每轮查询数。

### 难点 D：评测对照的有效性 —— 指标差异可能来自环境而非代码

（详见 §3.2，这里给 STAR-C 骨架）

**C**：评测要对比改动前后，但两次运行之间的**外部依赖可用性不受控**。
**A**：`retrieval_health` 守卫，把「产出率为 0」变成显式机器判定，
并区分「没检索过」与「检索全失败」。
**C**：代价是评测脚本多一层统计；取舍是**它拦下了一轮本来会被误读的无效对照**。

### 难点 E：指标会饱和 —— 触顶的指标测不出改进

（详见 §3.3，这里给 STAR-C 骨架）

**C**：任何度量都有量程，接近上界时失去分辨力。
**A**：两个案例 ——
① `key_point_coverage` 两阶段都 1.0 → 根因是要点判别力不足（通用概念），
改为「只有读懂正确来源才可能命中」的具体机制；
② `citation_coverage` 52% vs 53% 几乎不动 → 逐句分类证明 ~80% 未带角标句子
是分析推演与结构标记，**本就不该带角标**，~50% 是结构性天花板。
**C**：代价是必须落盘完整报告才能做逐句分类（原先只存 500 字预览）；
取舍是**宁可多存一份文件，也要能回答「这个指标的量程在哪」**。

### 难点 F：MCP 协议的序列化语义 —— 「返回列表」不等于「一个 JSON 数组」

**C — 协议约束**：
MCP 的内容模型是**内容块列表**（`content: [block, ...]`）。
一个返回 `list[dict]` 的工具，序列化后是**每条结果一个内容块**，
而**不是一个包含数组的内容块**。按「函数返回什么、协议就传什么」的直觉去解析，
会把真实结果全部丢掉 —— 而日志里明明打印出了正确内容。

**A — 方案**：逐块解析，块是 dict 就追加、是 list 就展开，两种都兼容。
并加单元测试锁住这个格式。

**C — 代价与取舍**：
- 这个坑的价值不在修复本身（改动很小），而在**它揭示的边界**：
  跨进程/跨协议调用时，**不要假设「函数签名」等于「线上格式」**；
- 我把它写进了测试的 docstring —— **协议语义类的问题，只靠读文档很容易漏，必须用真实调用验证**。

## 6. 数字与事实备忘

**数据集**
- Golden Set 50 题：`multiagent` 30 + `direct` 20
