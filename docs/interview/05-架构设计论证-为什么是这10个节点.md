# 架构设计论证：为什么是这 10 个节点？少一个行不行？

> 更新日期 2026-09-19（按最新代码核实，所有结论都追到 `app/mult_agents/` 的源码事实）
>
> 这是面试官最爱问的一类问题：「你搞这么多节点，是不是过度设计？合成三个行不行？」
> 答这类问题的关键不是背节点清单，而是**能说出每个节点的「去掉代价」和「合并代价」**。

---

## 一、先给结论

**10 个节点里，3 个是硬必需的（去掉链路直接断），4 个是成本/质量必需（去掉功能降级但能跑），3 个是可选增强。**

| 节点 | 定性 | 一句话判据 |
| --- | --- | --- |
| `plan` | 🔴 硬必需 | `write` 强制按它产出的 `outline` 成文；检索词也来自它的 `search_plan` |
| `deep_dive` | 🔴 硬必需 | `source_index` 只在它这里产出，引用校验依赖它 |
| `analyze` | 🔴 硬必需 | `findings` 是 `write` 的输入；且它承担「是否继续研究」的判定 |
| `write` | 🔴 硬必需 | 交付物本身 |
| `web_search` | 🟡 功能必需 | 唯一的外部证据来源（去掉只剩本地知识库） |
| `local_rag` | 🟡 功能必需 | 唯一的内部证据来源（去掉只剩联网） |
| `intent` + `direct_answer` | 🟡 成本必需 | 简单问题不进多智能体链路 |
| `retrieve_grader` | 🟢 可选增强 | 去掉就是回退到「检索完直接进裁判」 |
| `clarify` | 🟢 可选增强 | 去掉就是「不澄清直接规划」 |

> 注意 `web_search` 与 `local_rag` 单独看都是「可去掉一路」，但两路都去掉就没有证据了——所以是**二选一必需**。

---

## 二、判据：一个节点该不该独立存在？

我用三条标准判断，不靠感觉：

1. **依赖断裂测试**：去掉它，下游节点会不会拿不到必需的输入？（硬必需）
2. **代价不对称测试**：它做的事，放在别的节点里做会不会更贵？（成本/质量必需）
3. **结构化复杂度测试**：合并后，单次结构化输出的 schema 会不会臃肿到失败率显著上升？（抗合并）

第 3 条是本次迭代才意识到的——**单次结构化输出能承载的字段数是有限度的**，这直接决定了 `deep_dive` 与 `analyze` 不能合并。

---

## 三、依赖链：谁消费谁的产出（这是硬约束的证据）

从源码核实（`grep "state.get("` 各节点）：

```
plan ──┬─→ outline ────────────────────────→ write（强制按此成文）
       ├─→ sub_questions ──→ web_search / local_rag / retrieve_grader / analyze / write
       └─→ search_plan ────→ web_search / local_rag（检索词来源）

web_search ─→ web_evidence ─┐
local_rag ──→ local_evidence ┴→ retrieve_grader（判定）→ deep_dive

deep_dive ─┬─→ evidence_pool ──→ analyze
           ├─→ audit_flags ───→ analyze / write
           └─→ source_index ──→ write（引用校验的合法 ID 集合）★只有这里产出

analyze ───→ findings ─────────→ write（结论映射）
```

**关键证据**：`source_index` 在整个代码库里只有两个产出点——`deep_dive.py:81-96` 与其降级路径 `_fallbacks.py`。**没有任何其他节点产出它**。而 `write.py:81` 用 `state.get("source_index")` 构造 `valid_source_ids`，没有它就没有合法引用集合，报告会退化成「零引用」并被质量门禁的 `no_citation` 告警拦下。

所以 `deep_dive` 的**槽位**是硬必需的（它的 LLM 部分有确定性降级，但产出槽位无法跳过）。

## 四、逐个节点：职责 / 去掉会怎样 / 能否合并

### `intent` + `direct_answer` —— 成本必需，不是功能必需

**职责**：规则初判 + LLM 决策，把「1+1 等于几」这类问题短路到直答通道。

**去掉会怎样**：功能不坏，但每个简单问题都要跑完 plan → 双路检索 → 裁判 → 分析 → 成文，几十秒出一句「2」。这是**纯粹的成本浪费**。

**为什么分成两个节点而不是一个**：`intent` 只做路由（无用户可见输出），`direct_answer` 产出用户可见正文。合并的话，一个节点要同时承担「写路由决策」和「写正文」，而这两件事的流式行为完全不同（前者不该推 token 给用户）。

**能不能少**：可以整体砍掉，代价是成本。也可以只砍 `direct_answer`（intent 判 direct 时也走完整链路）——但那毫无意义。

> 面试金句：这不是为了炫技，是因为**多智能体链路的单位成本太高**——一轮研究几十秒、十几次 LLM 调用。用一次极便宜的判定（flash 型号，temperature 0）拦住本不该进来的请求，是整个系统性价比最高的一处优化。

---

### `clarify` —— 可选增强

**职责**：规则快速通道（短 query / 「最近的」「一些」等模糊词）+ LLM 置信度自评，必要时发起澄清；轮次上限 2。

**去掉会怎样**：直接进 plan。对模糊问题（「帮我调研一下最新的 AI 进展」）会带着歧义跑完整轮流程——**跑完才发现方向不对，这比多问一句贵得多**。

**为什么它可去**：`clarify` 判定不需要澄清时会直接放行（`needs_clarification=False` → 进 plan），且 LLM 调用失败时也是**静默放行**而不是卡死。所以它天生就设计成「能跳过」。

**为什么没合并进 plan**：两者的 HITL 交互时机不同——`clarification` 与 `plan_approval` 是两个独立的 interrupt 点。合并会让 plan 的 schema 同时承载「澄清问题」和「研究计划」，且用户得同时回答两类问题，交互变糟。

---

### `plan` —— 🔴 硬必需

**职责**：产出 `objective` / `sub_questions` / `outline`（章节大纲）/ `search_plan`（检索词）/ `budget`。

**去掉会怎样**：
- 检索节点没有检索词，只能拿原问题去搜（`_build_queries` 有 fallback：`{"query": state["query"]}`）——**检索覆盖面塌掉**
- `write` 没有 `outline`，只能自由发挥章节结构

**为什么 `outline` 不能省**：这不是格式偏好。源码里写得很直白——

```python
def _render_outline_for_prompt(outline: list) -> str:
    """大纲来自 plan 节点，HITL 下是用户批准过的那一版
    —— 报告结构必须与之一致，否则用户批准的是一份、拿到的是另一份。"""
```

**HITL 开启时，`plan` 产出的大纲是用户点过「同意」的契约。** 写报告时擅自改结构，等于违约。这是为什么 `plan` 不可省，也不可合并。

---

### `web_search` / `local_rag` —— 二选一必需，且刻意分开

**职责**：一路走联网 Provider 链，一路走 Milvus + PG 混合检索；各自做去重、相关性过滤、LLM 整理成结构化证据。

**去掉一路**：功能降级（只剩内部知识库 / 只剩公网信息），链路不断。**两路都去掉**：没有证据，整个系统失去意义。

**为什么分成两个节点而不是一个？** 这是最值得讲清的一个：

| 维度 | 分开（现状） | 合并成一个 |
| --- | --- | --- |
| 并发 | LangGraph 原生并行边，`plan` 扇出两条边，框架调度 | 节点内自己 `asyncio.gather` |
| 失败隔离 | 一路挂掉独立降级，另一路照常产出 | 需要自己写 try/except 包住每一路 |
| schema | 各自独立的 `WebSearchDraft` / `LocalRagDraft` | 一个 schema 要兼容两种证据类型 |
| 来源前缀 | `WEB{批次}_…` / `LOC{批次}_…` 天然分开 | 需要在节点内判断来源类型 |

**诚实结论**：合并**技术上可行**，而且能少一次超步。没合并的理由是「并行边是框架原生能力，比自己 `gather` 更简单，且失败隔离是白送的」。**这不是强论证，属于工程取舍**——如果面试官追问，我会承认这一点，并说真要优化时合并是一号候选（见第六节）。

---

### `retrieve_grader` —— 可选增强，但价值具体

**职责**：在检索之后、裁判之前，判定「这一轮证据够不够」，不够就改写检索词再搜（上限 2 轮）。

**去掉会怎样**：直接进 `deep_dive`。功能不坏——外层 `analyze` 仍会发现证据不足并触发补搜。**但代价高得多**：要跑完 `deep_dive`（一次带工具的 LLM 调用）才走到 `analyze`，才发现该换个词搜。

**这就是它存在的全部理由：判定时机的代价不对称。**

```
没有 grader：检索 → deep_dive（贵）→ analyze 才发现不足 → 回检索
有了 grader：检索 → grader（便宜）→ 发现不足 → 立刻重检          ← 省掉一次 deep_dive
```

**它和 `analyze` 都判「够不够」，为什么不合并？** —— 这是最好的追问，答案在源码注释里：

> 「本节点判『**这一轮**检索够不够，不够就换个词再搜』—— 检索阶段内部循环；『跨轮次还要不要继续研究』由 `analyze` 的 `next_action` 决定。**两者层级不同，不要混用。**」

更精确地说：**两者看到的输入不同**。grader 看的是原始证据摘要（`evidence_for_prompt`），便宜；analyze 看的是裁判后的 `evidence_pool` + `audit_flags` + 历史研究笔记，贵但准。用贵的判定替代便宜的判定，是在浪费那次 `deep_dive`。

**降级设计也印证了它的定位**：grader 失败时是**放行**而不是重试——

```python
"""裁判失败时放行而不是重试。重检需要新的检索词，而检索词正是裁判的产出
—— 裁判都失败了，循环没有可用输入，继续转只会空烧检索配额。"""
```

---

### `deep_dive` —— 🔴 硬必需（槽位不可跳过）

**职责**：证据评分（域名先验 + LLM 融合）、去重、冲突审计，产出 `evidence_pool` / `audit_flags` / `source_index`。

**唯一带工具的节点**：`fetch_url` 绑给它，用于核实可疑证据原文。

**去掉会怎样**：`source_index` 无人产出 → `write` 的 `valid_source_ids` 为空 → 报告零引用 → 被质量门禁告警，且**引用溯源体系整个失效**。

**它的 LLM 部分可降级**（`_fallback_audit` 用确定性规则构造），但**产出槽位必须存在**。

**为什么 `fetch_url` 只给它**：「哪些证据可疑、要不要读原文」是运行时才知道的，符合 agent 的适用判据；而检索是路径可预测的，直调更可控更便宜。

---

### `analyze` —— 🔴 硬必需

**职责**：① 结论映射（`findings` + `claim_map`）② 完备性评估（`needs_more_research` + `missing_gaps`）③ 缺口→补检词（`gap_queries`）。

**去掉会怎样**：`write` 拿不到 `findings`，只能直接看证据池成文——结论的组织工作被推给写作模型，而写作模型同时要兼顾结构、引用、文风，**质量会明显下降**。

**它已经合并过一次**：原来的 `reflect` 节点就并进了这里。理由写得很清楚——

> 「缺口与补检词本就出自同一次判断。合并的理由：分成两次调用会让模型先说出缺口、再被要求根据自己刚写的缺口出词 —— 多一次调用，还多一次信息损失。」

**为什么不再往前合并 `deep_dive`？** 见下一条。

---

### `deep_dive` + `analyze` 为什么不合并（抗合并的核心理由）

两者合并后，一次结构化输出要同时承载：

```
evidence_pool（每条含 8 个字段）+ audit_flags + findings + claim_map
+ missing_gaps + gap_queries + analysis_summary + next_actions
```

**单次结构化输出的复杂度有上限。** 字段越多、嵌套越深，模型漏字段或格式出错的概率越高；而一旦失败，整轮这一大坨工作全部作废——**失败 blast radius 太大**。

分成两次，每次失败只影响一层的产出，且各自有独立的降级路径（`_fallback_audit` / `_fallback_analysis`）。

> 这是我在这次迭代里才真正想清楚的一条：**节点拆分的边界，不只看职责是否内聚，还要看单次结构化输出的失败成本。**

---

## 五、诚实盘点：哪些节点其实可以合

我不打算把这 10 个节点说成「每个都不可或缺」——那是经不起追问的。真实情况：

| 合并项 | 可行性 | 我为什么没做 |
| --- | --- | --- |
| `web_search` + `local_rag` | **高** | 并行边是框架原生能力，失败隔离白送；合并要自己 `gather` + 处理两套 schema。**真要优化时这是一号候选** |
| `intent` + `clarify` | 中 | 一个是纯路由（无 interrupt），一个是交互（有 interrupt）。合并会让路由分支与 HITL 时机纠缠 |
| `deep_dive` + `analyze` | **低** | 单次结构化输出过重，失败 blast radius 太大 |
| `retrieve_grader` + `analyze` | **低** | 两者看到的输入不同（原始摘要 vs 裁判后证据池），合并会浪费那次 `deep_dive` |
| `analyze` + `write` | **不可行** | 如果 `analyze` 判定要继续研究，`write` 已经跑了一半——回环与成文不能耦合 |

## 六、如果只留 5 个节点，我会怎么砍

```
intent（含直答短路）
  → plan（含澄清，把 clarify 并回 plan 的提示词里）
  → retrieve（web + local 合并，节点内 asyncio.gather）
  → judge（deep_dive + analyze 合并）
  → write
```

**砍掉的与代价**：

| 砍掉 | 代价 |
| --- | --- |
| `retrieve_grader` | 检索不足只能等 `judge` 发现，每次多跑一次 LLM 裁判 |
| `clarify` | 模糊问题带着歧义跑完整轮 |
| 双路检索分开 | 要自己写并发与失败隔离 |
| `deep_dive` / `analyze` 分开 | 单次结构化输出过重，失败时整块作废 |

**我的判断**：5 节点版本能跑，但在「证据质量」和「失败隔离」上明显更弱。10 个节点不是堆数量，是**把四种不同的失败模式拆到了不同的槽位**——检索失败、检索不足、证据质量差、结论不足，各自有独立的发现点与降级路径。

## 七、面试话术

### 60 秒版

> 10 个节点不是堆出来的，每个都有明确的去掉代价。
>
> 硬必需的有三个：`plan` 产出的大纲是 HITL 下用户批准过的契约，报告必须按它写；`deep_dive` 是 `source_index` 的唯一产出点，没有它引用溯源整个失效；`analyze` 产出的 `findings` 是写作的输入，而且它承担「要不要继续研究」的判定。
>
> 有两个是我会主动承认可以合的：`web_search` 和 `local_rag` 流程几乎对称，合并能少一次超步，没合是因为 LangGraph 的并行边自带失败隔离，比自己 `gather` 省事——真要优化时这是一号候选。
>
> 还有一个值得讲：`retrieve_grader` 和 `analyze` 都在判「够不够」，但不是重复——grader 看原始证据摘要，便宜，在昂贵的裁判之前拦住；analyze 看裁判后的证据池，贵但准。这是**判定时机的代价不对称**，不是设计重复。

### 追问：你怎么证明不是过度设计？

> 用「去掉代价」和「合并代价」两条来证明，而不是背职责清单。
>
> 我还能说出一个反例：`deep_dive` 和 `analyze` 我**没有**合并，理由是单次结构化输出的复杂度有上限——字段越多，模型漏字段的概率越高，而一旦失败这一整块工作全作废。这个理由是我这次才想清楚的：**节点拆分不只看职责内聚，还要看单次结构化输出的失败成本。**
>
> 以及我已经主动合并过一次：原来的 `reflect` 节点并进了 `analyze`，因为缺口和补检词出自同一次判断，分两次调用会多一次信息损失。**能合的我合了，没合的都说得出代价。**

### 追问：节点多了会不会慢？

> 会，而且我已经为此付过代价。加内层重检后超步数超过 LangGraph 默认的 `recursion_limit=25`，`max_iterations=2` 就会撞顶导致整轮失败，所以 `recursion_limit` 现在由配置推算。
>
> 缓解手段是**并行**而不是砍节点：`web_search` 和 `local_rag` 并行；简单问题走 `direct_answer` 短路；判定节点用 flash 型号、长文才用 max。真正要提速时，合并双路检索是一号候选。

## 八、一页速记卡

```
硬必需（去掉链路断）
  plan      → outline 是 HITL 契约；search_plan 是检索词来源
  deep_dive → source_index 唯一产出点；唯一带工具的节点
  analyze   → findings 是 write 输入；承担「是否继续研究」判定
  write     → 交付物

功能必需（二选一）
  web_search / local_rag → 双路证据；刻意分开是为了并行 + 失败隔离

成本必需
  intent + direct_answer → 简单问题短路，性价比最高的一处优化

可选增强
  retrieve_grader → 便宜地在裁判前发现检索不足（判定时机的代价不对称）
  clarify         → 避免带着歧义跑完整轮；天生可放行跳过

可以合但没合（诚实盘点）
  web_search + local_rag —— 一号候选，合了要自己 gather + 处理两套 schema

不能合（有硬理由）
  deep_dive + analyze   → 单次结构化输出过重，失败 blast radius 太大
  grader + analyze      → 输入不同，合并浪费那次 deep_dive
  analyze + write       → 回环与成文耦合，判定要继续时 write 已跑一半
```
