# 发现：`citation_coverage` 有结构性天花板，不能用来衡量检索深度

- 日期：2026-09-19
- 触发：排查「多跑一轮为何不提升引用覆盖率」
- 结论：**推翻我此前「`citation_coverage` 是当前最可信判别指标」的判断**

## 起因

| | 带角标 | 主要论断 | 覆盖率 |
| --- | --- | --- | --- |
| baseline（1 轮） | 26 | 50 | 52.0% |
| improved（2 轮） | 35 | 66 | 53.0% |

报告变长、带角标句子也变多，**但比率几乎不动**。当时提出两种可能：
(a) 覆盖率是 write 提示词层面的模型常数；(b) 未带角标的句子本就不该带。

为判定，给评测加了报告落盘（`output/eval_reports/`），拿到完整正文后逐句分类。

## 证据：未带角标的句子是什么

对 baseline 报告（6644 字，106 个主要论断）逐句分类：

| 类型 | 句数 |
| --- | --- |
| 标题/小标题 | 13 |
| 过渡与总结（综上/因此/首先…） | 7 |
| 有数据/事实但无角标 | 5 |
| 其他（分析推演） | 35 |
| **未带角标合计** | **54**（占 51%） |

「分析推演」类的真实样本：

```
- 这一转变的核心驱动力在于大模型能力的边界拓展，使得 Agent 能够从简单的
  问答交互进化为具备独立执行能力的智能实体
- 这种分布式协作模式不仅提高了任务处理的并行度，还通过相互校验机制
  提升了最终输出的可靠性
- 第三，记忆机制从无状态向有状态持久化升级
```

**这些句子本就不该带角标** —— 它们是报告自己的综合、推断与结构标记，
不指向任何单一来源。一篇深度研报必然包含大量这类论述。

## 结论

**~50% 是结构性天花板，不是检索缺陷。** 覆盖率在 21.8% ~ 62.1% 区间波动，
反映的是「报告里有多少句子是事实陈述」，而不是「检索有多深」。

### 我此前的判断错在哪

我曾用「代理故障那轮 28.4% → 修复后 62.1%」论证它「对检索质量高度敏感」。
那次跨越测的是**「有没有证据」**（代理坏了 → 一条 web 证据都没有 → 无角标可打），
**不是「检索有多深」**。两者被混为一谈。

## 影响与后续用法

1. **降级为护栏指标**：它仍有用 —— 覆盖率**骤降**说明检索或引用链路出了问题
   （正是它抓出了代理故障）。但**不能**用它判定「B 阶段有没有收益」。
2. **B 阶段的收益仍缺判别指标**。回到原点：需要 Golden Set 的 `key_points`
   具备判别力（见 `app/test/golden_set.json` 的 `_readme`）。
3. 已顺带补上报告落盘（`output/eval_reports/`）—— 这次分析正是靠它完成的，
   此前评测只存 500 字预览，根本做不了逐句分类。

## 未做但可选的方向

`citation_coverage` 的分母目前是「长度 > 15 字的句子」，比提示词里的「主要论断」
宽得多。理论上可以缩小分母（剔除结构标记句、纯推演句），但「是不是主要论断」
需要语义判断 —— 确定性规则做不准，加一次 LLM 调用又与本指标的定位
（廉价、无人工标注、可批量跑）冲突。**暂不做，先按护栏指标用。**
