## 九、第二批：P1-5 HITL 协议拆分（独立提交）

第一批把 P1-5 列为「需跨模块联动、单独立项」，第二批已实施。

### 根因
`kind` 被当作「中断类型的唯一标识」使用，但实际标识的是「协议族」。
`clarify` 与 `analyze` 是两个语义不同的中断点却共用 `kind="clarification"`，
而 `_validate_resume_payload` 只按 `kind` 派发校验，于是：

- **analyze 分支**：载荷 `{node, missing_gaps, analysis_summary, message}` 被
  `ClarifyResumePayload` 校验（要求必填 `answers`）→ 422，HITL 分支不可达
- **clarify 分支**：router 校验通过后 `Command(resume={kind, answers})`，
  而 `interrupt()` 返回的是**这个 dict**，节点却按 list 消费
  （`isinstance(answers, list)`）→ 用户答案被 `str(dict)` 字符串化成一段文本

### 15.3 新发现的代码级根因：`enable_dynamic_field` 未开启

`langchain_milvus` 的 `enable_dynamic_field` **默认为 False**，此时它会从「首批写入的 metadata」
推断出真实列；对**已存在**的集合不再走建表流程，于是 `key not in self.fields` 的 metadata
被静默丢弃（`vectorstores/milvus.py:1289`）。实测对比：

| enable_dynamic_field | 新建集合字段 | metadata 去向 |
| --- | --- | --- |
| 默认 False | `['text','pk','vector','doc_id','section_path']` | 推断成真实列 |
| 显式 True | `['text','pk','vector']` | 存入 `$meta` 动态字段 |

修复：`RAGSystem` 构造子块/父块向量库时显式传 `enable_dynamic_field=True`。
这是第四批最重要的代码修复 —— 不改它，重索引也照样写不进 metadata（第一次重索引即因此失败）。

## 十七、第六批：JWT 全站鉴权（P0-2）

用户决策：鉴权方案采用 JWT。这是审查报告里最后一个 P0 项。

### 设计

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 令牌格式 | JWT HS256（PyJWT） | 用户指定；无状态、便于 SSE 场景携带 |
| 用户来源 | 环境变量 `AUTH_USERS`（`user:pass[:role]`） | 项目没有用户表；接入真实用户体系只需替换 `authenticate()` |
| 密钥缺失 | **fail-closed**：拒绝签发/校验并返回 503 | 不降级为放行；与 admin 端点此前的 fail-open 形成对照 |
| 登录失败 | 一律 401 且文案相同 | 不泄露账号是否存在 |
| 身份来源 | **只来自令牌的 sub** | 请求体/查询参数中的 user_id 全部移除 |
| 管理端点 | `require_admin`（role=admin） | 取代原先基于 `ADMIN_TOKEN` 的自建校验，全站一种机制 |
| OpenAPI 文档 | 仅 development 暴露 | 非开发环境不暴露接口清单 |

### 改动

- 新增 `backend/auth/`：`security.py`（签发/校验/口令比对）、`deps.py`（`get_current_user` / `require_admin`）
- 新增 `backend/schemas/auth.py`、`backend/router/auth_router.py`（`POST /api/v1/auth/login`、`GET /api/v1/auth/me`）
- 请求 schema 移除 `user_id`：`ResearchRequest` / `ThreadRenameRequest` / `ThreadPinRequest` / `DocumentBatchDeleteRequest`
- 17 个 research 路由 + 8 个 document 路由全部挂认证依赖；`user_id` 一律取自令牌
- `admin_router` 切到 `require_admin`，删除 `ADMIN_TOKEN` 机制与 `MiddlewareSettings.admin_token`
- **补齐 IDOR**：`ChunkRepository.delete_document` 增加 `user_id` 过滤
  （此前单条删除完全没有归属校验，可越权删除他人文档）
- `requirements.txt` 增加 `PyJWT>=2.8`；`.env` 生成随机 `JWT_SECRET` + 本地开发账号；`.env.example` 补文档

### 验收

- 后端全量：**552 passed, 2 skipped**（新增 `app/test/test_auth.py` 33 例）
- 两条结构性守卫：
  1. 遍历 `app.routes` 断言**所有 `/api/` 业务路由**都挂了认证依赖（新增端点漏挂会失败）
  2. 断言四个请求模型都不含 `user_id` 字段
- **真实服务端到端验证**（uvicorn 起服务 + httpx 实测）：公开端点 200 / 未认证 401 /
  错误口令与不存在用户同为 401 且文案一致 / 篡改令牌 401 / 带令牌 200 /
  普通用户访问管理端点 403 / 管理员 200 /
  **请求体注入 `user_id: "someone-else"` 被忽略，响应身份为令牌内的 `user01`**

### 验证过程中发现的两个既有启动问题（非本次改动引入，未修）

1. **Windows 下用 `uvicorn app_main:app` 启动会让异步 PG 连接池失效**：
   uvicorn 在**创建事件循环之后**才导入 app 模块，因此 `app_main.py` 在导入期设置的
   `WindowsSelectorEventLoopPolicy` 为时已晚，`AsyncPostgresStore` 反复报
   `Psycopg cannot use the 'ProactorEventLoop'`。
   `python app_main.py`（及 `start_backend.bat`）走的是 `__main__` 分支，策略在
   `asyncio.run` 之前生效，因此不受影响 —— 但 README 恰恰推荐了会出问题的命令。
2. **RabbitMQ `chunk-sync-dlq` 队列参数冲突**：`PRECONDITION_FAILED - inequivalent arg
   'x-queue-mode'`，导致 MQ 消费者启动失败、向量化降级为同步模式。
