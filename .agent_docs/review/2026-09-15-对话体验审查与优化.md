# 对话体验审查与优化文档

> 审查范围：对话页（流式输出、中间过程呈现、内容排版）
> 对照基准：DeepSeek 网页版的对话交互
> 结论：发现 6 个问题，其中 4 个已修复并实机验证，2 个列为待办

## 一、结论速览

| # | 问题 | 严重度 | 状态 |
| --- | --- | --- | --- |
| 1 | 回答不是打字机式输出，整段一次性吐出 | 高 | ✅ 已修 |
| 2 | 意图路由器的原始 JSON 混进回答气泡 | 高 | ✅ 已修 |
| 3 | 每个节点各占一个气泡，一轮对话堆出一列气泡 | 高 | ✅ 已修 |
| 4 | 中间过程散落在消息流与页面底部，无折叠卡片 | 高 | ✅ 已修 |
| 5 | 过程内容只有节点名、没有细节，无可读内容 | 中 | ✅ 已修 |
| 6 | 13 个组件共 ~146 处硬编码色值，与设计系统打架 | 中 | ⏳ 部分（对话链路已清） |
| 7 | 输入框 placeholder 过长被截断 | 低 | ⏳ 待办 |
| 8 | 长任务缺少耗时/进度感知（网络检索慢时尤其明显） | 中 | ⏳ 待办 |

## 二、根因分析

### 2.1 「一大块吐出」不是前端问题，是模型没有流式

**实测数据**（`output/probe_stream.py`，记录每个 `message.delta` 的到达时刻）：

| | 修复前 | 修复后 |
| --- | --- | --- |
| 增量事件数 | **2 个** | **13+ 个** |
| 单增量字符数 | 平均 86.5，最大 **112** | 平均 8.6，最大 12 |
| 到达间隔 | 2078ms | **78ms** |

**根因**：`models.py` 构建 `ChatTongyi` 时未开启流式：

```python
llm = ChatTongyi(model=model, temperature=temperature)   # 默认 streaming=False
```

`streaming=False` 时，`agent.astream(stream_mode="messages")` 不会逐 token 产出，
而是把整段响应作为一个 chunk 返回 —— 后端「看起来在流式」（事件类型、协议都对），
实际只有一次大块推送。前端再怎么优化渲染也没用。

**修复**：`ChatTongyi(..., streaming=True)`。

> 这类问题的特征：协议正确、链路正确、日志正常，唯独体感不对。
> 只看代码会得出「已经实现了流式」的错误结论，**必须实测事件时序**。

### 2.2 结构化输出泄漏到用户可见的消息流

**现象**：回答气泡的第一个增量是 `{"route":"direct","reason":"用户问候并请求简单自我介...`
—— 意图路由器的原始 JSON。

**根因**：`_invoke_json_agent` 是所有**结构化输出节点**的公共入口，它把模型的
每个增量都推成 `{"type": "token"}`：

```python
writer({"type": "token", "node": node, "text": text})   # text 是 JSON 片段
```

而 `token` 事件的语义是「用户可见的正文增量」。**7 个节点**（intent / plan /
web_search / local_rag / deep_dive / analyze）全都经此路径，因此每个节点的 JSON
都可能混进消息流。

**修复**：`_invoke_json_agent` 不再推送 `token`（JSON 是拼装过程，属实现细节），
只保留 `reasoning`（思考）与进度状态。用户可见的正文只来自两个节点：
`write`（报告）与 `direct_answer`（直答）。

### 2.3 一轮对话堆出一列气泡

**根因**：消息 ID 按 `{run_id}:{node}` 生成，**每个节点各建一个气泡**。
一轮深度研究有 8~10 个节点，于是出现一列「头像 + 空气泡」，
中间过程与答案混在一起，视觉上无法区分主次。

**修复**：渲染时按「轮」分组（`utils/turns.ts`）——用户提问开启一轮，
**带正文的助手消息才是答案**，其余助手消息都归入过程卡片。

### 2.4 过程信息散落两处

**修复前**：中间过程拆在两处 —— 每个节点气泡里内嵌一个 `ThinkingBlock`，
外加页面底部一个游离的 `AgentTimeline`。用户既看不出顺序，也看不出归属。

**修复后**：合并为一张 `ProcessCard`，挂在对应轮次上：
运行中默认展开、出结果自动收起；用户手动操作过则以用户操作为准。

### 2.5 过程步骤只有节点名、没有内容

**根因链**（三层各丢一次信息）：

1. 后端 `_status_frame()` 只发 `node + label + phase`，
   节点自报的进度文案（`{"node":"intent","message":"意图判定完成: direct"}`）**被丢弃**
2. 前端 `appendThinkingLog()` 在没有助手消息时直接 return —— 直答路径下
   intent 的状态日志无处挂载，**被丢弃**
3. 于是过程卡片只剩节点名，没有任何可读内容

**修复**：

- 事件协议 `agent.status` 增加 `detail` 字段，透传节点进度文案
- 过程步骤改以 **agent 状态时间线**为准（每次运行完整记录、不受消息是否存在影响），
  `thinkingLogs` 仅作补充
- 时间线按轮切分：用户消息记录发送时刻的时间线长度作为本轮起点

## 三、与 DeepSeek 的对照

| 维度 | DeepSeek | 本项目（修复前） | 本项目（修复后） |
| --- | --- | --- | --- |
| 答案输出 | 打字机式逐字 | 整段一次性 | ✅ 逐 token（78ms/次） |
| 思考过程 | 「深度思考」折叠卡片，运行中展开 | 每个节点一个气泡 | ✅ 折叠卡片，运行中展开、结束自动收起 |
| 过程内容 | 结构化步骤 + 可读文案 | 原始 JSON + 节点名 | ✅ 步骤行（状态点 + 节点名 + 状态 + 细节） |
| 正文与过程 | 严格分离，正文只放答案 | 混在同一列气泡 | ✅ 正文只放答案 |
| 折叠交互 | 可手动展开/收起 | 无 | ✅ 支持，且尊重用户操作 |

**设计取舍**：本项目的「过程」比 DeepSeek 更值得展示 —— 多智能体的检索次数、
命中条数、证据保留量都是用户关心的信息。因此卡片头显示「共 N 步」，
步骤行保留细节文案，而不是像 DeepSeek 那样只显示思考文本。

## 四、遗留问题（建议排期）

### P1：组件级硬编码样式与设计系统冲突

13 个组件共 **~146 处硬编码色值、~1000 行 scoped 样式**，与 `assets/theme.css`
的令牌体系并存。scoped 样式优先级更高，导致**设计系统被局部覆盖**，
界面呈现新旧两套风格混杂。

已处理：`MessageItem` / `ProcessCard` / `LoginView` 及本轮涉及组件。
待处理：`MarkdownRender`（16 处）、`SourceList`（11 处）、`ClarifyCard`（9 处）、
`PlanApprovalCard`（11 处）、`ReportReviewCard`（9 处）、`EvidenceGapCard`（11 处）、
`Composer`（6 处）、`RollbackMenu`（1 处）。

**建议**：逐个把这些组件的 scoped 样式改为引用令牌变量；能由 `theme.css` 统一承担的
直接删除组件内样式。

### P2：长任务缺少耗时与进度感知

一次深度研究耗时可达 10 分钟以上（网络检索是瓶颈）。当前只有节点级状态，
用户看不到「还剩多久」「卡在哪一步」。过程卡片已有步骤与状态，可在此基础上
补充每步耗时与总耗时。

### P3：输入框 placeholder 过长

`输入你的问题，Enter 发送，Shift+Enter 换行` 在默认宽度下被截断成
`输入你的问题，Enter 发送，S...er 换行`。建议缩短为「输入问题，Enter 发送」。

### P4：历史会话的过程卡片数据缺失

从服务端加载的历史会话没有 `agentTimeline`（时间线是前端运行时状态），
此时过程步骤回退到按消息推导 —— 若后端不返回过程数据，历史会话将没有过程卡片。
**建议**：后端持久化过程步骤，或在 `threads/{id}/messages` 响应中附带。
